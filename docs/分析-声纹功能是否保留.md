# 分析：声纹（说话人区分）功能是否该保留

> **状态：分析稿，待决策（未改代码）**。
> 起因：用户判断「记录声纹的能力不适用于此模型，反而增加延迟，貌似不需要」。
> **结论：该判断基本成立**——但要说清「哪一半成立、哪一半还有用」，以及代价到底多少。

## 1. 这个功能到底做了什么（三层，可分别取舍）

| 层 | 代码 | 作用 | 实测表现 |
| --- | --- | --- | --- |
| **① 换人切分** | `PlanSpeakerSpans` → 头尾预判 + pyannote 分段 | 把**一段音频按说话人切成多片**分别识别 | ⛔ **合成素材上段数恒为 0**（真人未测，但见 §3 的结构性理由） |
| **② 贴标签** | `AttachSpeaker` → CAM++ 嵌入 + 声纹库匹配 | 给整条字幕标「说话人 A/B/C」，用户命名一次后沿用 | ✅ **这一层是有效的**（同人相似度 0.69 / 异人 0.09，可区分） |
| **③ 声纹库** | `data/v2-speakers.json` | 记住用户命名的名字 | ✅ 有效（便携、可删） |

**关键**：**用户要的「谁说的」主要靠 ②+③**；① 只是顺带试着把混在一段里的两个人拆开。
而 ① 恰恰是**最贵、且从未产出结果**的那一层。

## 2. 代价（全部实测，2026-09-16 本机）

| 项 | 成本 | 备注 |
| --- | ---: | --- |
| 头尾预判（每句必做） | **33~50 ms** | 与音频长度基本无关 |
| 整句嵌入（每句必做，贴标签用） | **26~50 ms** | ② 层，不是浪费 |
| 手动嵌入（5.6 s 单语） | 46 ms | 同上 |
| **pyannote 切分（疑似换人才跑）** | **38 ms（≤10 s）→ 207 ms（11 s）→ 384 ms（13 s）→ 975 ms（18.4 s）** | ① 层，**从未产出结果** |
| **每句合计（开标签）** | **约 +130 ms**（长段可到 **+630 ms**） | 关标签 = **0**（代码里是 bool 短路） |
| 声纹模型体积 | **29.8 MB**（pyannote 1.5 + CAM++ 28.3） | 随包发布 |
| 其他 | 一个持久化文件 + 一个 UI 开关 + 约 25 条测试 | — |

> 官方文档原写「开启后每句约多 50 ms」——**那个数只算了 ② 层（整句嵌入）**，
> 漏了 ① 层的预判（33~50 ms/句）与长段切分（最高 1 秒）。**实测应为 +130 ms 起。**

## 3. 为什么说「不适用于此模型」成立

**① 换人切分的前提，被识别模型本身否掉了：**

- 现在用的 **SenseVoice 是批式识别**：先把一段音频切出来，再整段识别；
- 所以「谁说的」只能靠**外挂 pyannote** 去切；
- 而 pyannote 在**长段上要 0.9~1.0 秒**——想靠它改善切分，**代价比它要解决的问题还大**；
- 实测上它也确实**一次都没切成功**（合成素材）。

**② 标签这一层，其实是「没有切分时的替补」：**

同一段音频如果混了两个人、而**识别只能出一个结果**，那么贴上去的标签**必然只代表其中一个人**——
**标签本身可能是错的**（内容来自 A，标签贴到 B）。
也就是说：**① 失效时，② 的正确性也跟着打折**。

**③ 而「谁在说话」这件事，在 VRChat 里本来另有更直接的来源：**

| 来源 | 说明 |
| --- | --- |
| **VRChat 自身** | 谁在说话有嘴型/名牌高亮，玩家自己看得见 |
| 说话人分离（diarization） | 已有 pyannote，但它同样是「按段」的，救不了批式识别的根本问题 |

**结论**：这个功能在**当前识别模型下**的期望收益，远低于它 130 ms/句 + 30 MB + 一套测试与 UI 的代价。

## 4. 但有一处不能一刀切：②③ 还是能用的

| 如果全部移除 | 后果 |
| --- | --- |
| 单人连续说话（VRChat 最常见） | 没有损失——反正一段只会有一个人 |
| **两人交替说话**（A 一句、B 一句，各自成段） | **会丢掉「这句话是谁说的」**——现在能给 A 标 A、给 B 标 B，命名后跨会话沿用 |
| 用户已命名的声纹库 | `data/v2-speakers.json` 作废 |

**三个方案：**

| 方案 | 做什么 | 每句成本 | 保留的能力 |
| --- | --- | ---: | --- |
| **A. 全部移除** | 删 ①②③、模型、开关、测试、文档 | **0** | 无（且丢掉已有命名） |
| **B. 只删「换人切分」（①）** ⭐ | 删 `PlanSpeakerSpans`、pyannote 调用与相关参数；保留 ②③ | **约 +45~100 ms**（只剩整句嵌入） | **谁说的**（标签 + 命名沿用） |
| C. 保持现状 | 不改 | +130 ms（长段 +630 ms） | 标签 + 一个从未生效的切分 |

**我建议 B**：

1. **砍掉 ① 直接省下**：预判 33~50 ms/句、长段切分 200 ms~1 s、pyannote 模型 1.5 MB、一整段从未生效的逻辑；
2. **保留 ②③**：它真的能用（实测可区分同人/异人），而且是「标签」这个用户可见功能的**唯一实现**；
3. 这条改动**不碰识别与翻译链路**，风险低，可单测覆盖。

## 5. 唯一还没测的点（决定 B 够不够）

**① 在真人快速接话上到底行不行，至今没测过**（我只有合成素材）。**如果真人是有效的**，砍掉它就损失了一个真实能力。

**测它只需要一段录音**：两个真人各说一句、中间不重叠（手机录即可，10~20 秒）。

| 结果 | 动作 |
| --- | --- |
| 段数 > 0 且切分点正确 | ① **值得保留**（但要接受长段 0.9 s 的代价）→ 维持方案 C，并考虑只对长段启用 |
| 段数 = 0 或切分点错 | ① **确认无效** → 执行方案 B |

## 6. 建议

| 选项 | 说明 |
| --- | --- |
| **1. 直接执行 B**（半天） | 不等录音：反正 ① 现在**产出恒为 0**，删掉不损失任何**当前可见**的行为（只损失一个理论上可能存在的能力） |
| **2. 先给录音再决定** | 更稳妥，但要你花两分钟录一段 |

**我倾向 1**：删掉一个「从未产出结果、且每次都要付费」的机制是明确的净收益；
真要是以后发现真人接话能切，按 `SpeakerIdentifierOptions` 的默认值加回来也不难（参数与调用点都有记录）。
