- **D2**：术语库卡片删掉保存按钮与重复「启用」文字，标题行与其它卡片对齐；补齐删除后的自动保存触发点。
- **D3**：F7 成为「他人语音 → 字幕」总开关，语音页「打开字幕」按钮删除；任何启停路径结束后窗口可见性 = 识别运行状态。
- **D4**：字幕浮窗去掉易误会的「麦克风」标识，字幕水平居中。
- **D5**：根因是 `SubtitleSpeechSession` 把他人语音译文写进共享预览状态；已改为独立通道。
- **D6**：字幕浮窗样式改造 + 渐进式字幕（分段渐进上屏）落地。
- **D7**：大字幕窗口消息列表改为顶部对齐，高度跟随内容时窗口顶边固定、向下生长。
- **D8**：DeepL / Google 两个提供商删除；老配置回落到仍可用的档案。
- **D9**：三个快捷键改为「点击即录制」的按键捕获框（X 图标随之消失）；后续修正：清空后的快捷键不再在其它页面回落默认值。
- **D10**：输入浮窗默认宽度按 DPI 换算，不再出现高 DPI 下过窄。
- **D11**：OSC 载荷带原文（与 VRChat Chatbox 的显示契约对齐）。

## D14 · 两个人同时说话：识别层只会跟住一路，另一路整段丢失（**已知硬上限，不修**）

- **现象**：两段不同语种的真人语音按 50% 增益叠加（模拟两人同时讲话）送进内置 SenseVoice，结果只保留其中一路，另一路**整段消失**：

  | 合成音频 | 识别结果 | 丢失 |
  | --- | --- | --- |
  | 中文 5.6 s + 日语 5.6 s 完全重叠 | 「うちの中学は別当生で持ってきない場合は50円の学校販売のパ。」 | 中文整段 |
  | 英语 4.6 s + 韩语 4.6 s 完全重叠 | 「The tribal chieftain called for the boy and presented.」 | 韩语整段 |
  | 中文 5.6 s + 日语后半段插入（半重叠） | 「开饭时间早上9点至下午5点。」 | 日语整段 |

- **影响**：VRChat 里两人抢话是常态。被压住的那一路**不会产生任何字幕**——用户看到的不是「翻译错了」，而是「什么都没出现」。
- **根因**：SenseVoiceSmall 是**单说话人**模型，输入是混合音轨，模型只能跟一路音素；换翻译引擎、调延迟、加中文跳过都无效。
- **可走的方向**（未选型，未排期）：
  1. 用已打包的 pyannote 分割 + CAM++ 声纹先做**说话人分离**，把混合音频切成单说话人片段再分别识别；
  2. 等 sherpa-onnx 的多说话人流式模型（如 streaming zipformer + 说话人分离）。
- **现状**：**不修**。完整档案（现象 / 根因 / 五个无效方向 / 三条可选路线 / 复现方法）见
  [多人语音识别问题档案.md](多人语音识别问题档案.md)；实验数据见 [实验报告-识别与翻译.md](实验报告-识别与翻译.md) §4.4。
- **证据**：`artifacts/mix_zh_ja_over.wav`、`artifacts/mix_en_ko_over.wav`、`artifacts/mix_zh_ja_half.wav`；
  原始记录 `artifacts/asr-matrix.json`（每段 × 5 语言模式 × 10 次）。复现：`pwsh -File artifacts\bench-asr.ps1`。

## D15 · 中文/粤语也送去翻译：白等 100~600 ms，大模型还会改写原意（**已决定：不做**）

- **现象**：他人语音识别出的文本若是纯中文（含粤语书面语），当前代码照常调用翻译服务：
  - 机翻（腾讯 / 阿里通用 / 阿里专业）：**原样返回**，白等 99~108 ms；
  - 大模型（DeepSeek 413 ms / 小米 591 ms）：会**改写原文**，例如「开饭时间早上9点至下午5点。」
    → 小米「用餐时间为上午9点至下午5点。」（chrF2 64.6，用户看到的是被改过的句子）。
- **曾考虑的方案**：`含汉字 且 不含 假名(ぁ-ヿ) / 谚文(가-힣) / 拉丁字母(A-Za-z)` → 跳过翻译，直接复用原文。
  该判定在 27 条评测集 + 4 段音频上**全部判定正确**（见 [实验报告-识别与翻译.md](实验报告-识别与翻译.md) §6.3）；
  若写成「含汉字就跳过」则会把日语/韩语/混说句误判，实测质量从 chrF2 78.6/86.7 **掉到 35.4**。
- **用户决定（2026-09-16）：不实现，保持「一律送翻译」**。理由：
  1. 实测延迟与语种关系不大——纯中文 99~108 ms（机翻）本来就在同一量级，省下的时间不值得为它加一条语言相关分支；
  2. 软件以后可能要扩展给其他语种的人使用，语言相关的特判越多越难改。
- **接受的代价（明确记录，避免以后当成新 bug 再查一遍）**：
  - 机翻档：中文条目**原样返回**，用户看到的字幕与对方原话一致，只是白等 99~108 ms；
  - 大模型档（DeepSeek 93.7 / 小米 64.6 chrF2）：中文条目会被**轻微改写**——例如「这个图好像有人掉线了」
    → DeepSeek「这张图里好像有人掉线了。」。**意思不变、措辞会变**。这个代价已写进引导页推荐文案，
    在意「字幕与原话逐字一致」的用户可按文案选机翻档。
- **状态**：**不做**（decision closed）。若将来真要加，§6.3 的判定规则可直接复用。

## D16 · 长音频（>12 s）被截断，三语连说只认出最后一段（**待排期**）

- **现象**：18.4 s 的「中文 + 英语 + 韩语」连说音频，识别结果只剩末段韩语 + 一句英文残片
  （`presented 조금만 생각을 하면서 살면 훨씬 편할 거야.`）。
- **对照**：13.4 s 的「中文 + 静音 + 日语」两段连说**能**完整识别（中文只截断成「开饭」）。
- **根因**：`SileroVadSegmenter` 有 `MaxSegmentSeconds = 12 s` 上限，超过就切分；
  但这次实验直接把长音频整段喂给识别器（绕过了 VAD 分段），所以暴露的是**识别器单段上限**。
  软件内的真实路径会先过 VAD 分段，因此**实际影响待确认**——需要按 VAD 分段路径再测一次。
- **状态**：待排期。先确认真实路径是否也丢内容，再决定是否改。

## D17 · `VrchatProcessSwitchingTests` 偶发失败（**已修复**）

- **现象**：全量测试（并行套件）**偶发** 1 条失败：
  `VrchatProcessSwitchingTests.A_published_target_switches_the_capture_and_its_exit_switches_back`。
  同一天两次全量运行一次全绿一次该条失败；**单独重跑该测试类必过**。
- **真实根因（2026-09-16 定位）**：**不是**进程枚举竞争——该测试全程使用假进程源、假采集与脚本延时，
  不碰真实进程枚举。竞态在**测试断言与生产代码的异步间隙**：`AdaptiveLoopbackAudioCapture.InstallAsync`
  先 `SetState`（旧的等待条件在此即满足），再于异步间隙里停掉并释放旧采集；测试等到 SourceKind 翻转
  就断言 `DisposeCount == 1`，线程池紧张时读到中间态的 0 → 偶发失败。单独跑时释放几乎总在断言前完成。
- **修复（只动测试，生产代码零改动，`1a4a8dd`）**：
  1. 等待条件加强到「换流完全落地」：SourceKind 翻转**且**新采集已启动**且**旧采集全部释放完毕（`InstallSettled`）；
  2. `changes` 断言改为锁内快照（写入侧本就加锁，读侧原来是无锁读）；
  3. `FakeLoopbackCapture` 计数改 `Interlocked`、`IsStarted` 改 `volatile`（跨线程轮询的可见性）；
  4. `ProcessTestWait.UntilAsync` 超时可选化（默认仍 5 秒），本测试用 10 秒。
- **验收**：全量套件连跑 **5 次**全绿（76 + 119 + 185 = 380 条/次）。
  单跑该类循环**不能**作为验收——单跑无线程池饥饿，全绿证明不了修复。
- **状态**：已修复。
