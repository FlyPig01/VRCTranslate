## 4. 已修复的方案全文（D28~D30，实施记录含内）

### D28 · 他人语音结果错误进入 OSC → 已二次修复

**实施记录**：`16ebd2a` 只阻止了 echo、失败和同文结果进入 OSC，但仍把“有效译文”发到游戏。用户再次确认产品契约后，管线进一步收紧：`OtherPlayerCaptionPipeline` 删除 `IChatboxOutput`、具体输出字段和构造参数，Desktop 同时删除 `AppStateChatboxOutput`。他人语音管线现在从类型上只能翻译并更新 `IOtherPlayerSubtitleSurface`，无法调用 OSC。

#### 已确认根因

最初的 `SubtitleSpeechSession` 会发送 `translated.TranslatedText`；第一轮修复仍保留了“有效译文可以发送”的职责。无论载荷是原文还是译文，这都违背“识别他人语音只用于本地字幕”的产品边界。

历史上原文出现还会被三种情况放大：默认 `local-test / echo` 原样返回、配置恢复前误用临时 echo 路由，以及真实服务返回同文结果。

D11 的“OSC 消息带原文”只适用于**手动输入和自身语音**。他人语音的识别原文和翻译结果都只进入本地字幕浮窗，不发送到 VRChat Chatbox，也不新增用户开关。

#### 修复方案

1. 他人语音结果由 Application 层 `OtherPlayerCaptionPipeline` 处理；管线只依赖翻译端口和 `IOtherPlayerSubtitleSurface`，不得声明 Chatbox/OSC 输出端口。
2. Desktop 组合根在提交工作项前等待 `AppState.Ready`，一次性取得本句的路由快照并交给管线；Application 层不反向依赖 Desktop。运行中切换默认档案只影响下一句。
3. 真实翻译成功时将完整译文填入本地字幕，不使用 OSC 的 144 UTF-16 长度裁剪；echo、失败、取消、空译文或同文结果保留原文并结束等待态。
4. 手动输入和自身语音继续保留第一译文/第二译文/原文格式及“OSC 消息带原文”开关，不受本次修改影响。
5. 静态架构测试禁止 `OtherPlayerCaptionPipeline` 出现 `IChatboxOutput`、`SendChatboxAsync` 或 `TrimForOsc`，并禁止 Desktop 恢复 `AppStateChatboxOutput`。

#### 验收矩阵

| 输入结果 | 本地字幕 | OSC |
| --- | --- | --- |
| 真实译文且不同于原文 | 原文先出现，随后补完整译文 | 0 次 |
| `local-test / echo` 或未配置真实服务 | 显示原文 | 0 次 |
| 翻译失败、超时、取消或空译文 | 保留原文并结束等待态 | 0 次 |
| 服务返回与原文相同 | 显示一份文本，不重复 | 0 次 |

### D29 · 多人轮流/快速接话时字幕被静默丢弃 → 已修复（`16ebd2a`）

**实施记录**：`_processingResult` 丢弃规则已删除；每句分配单调 `captionId` 并同步发布 Pending 字幕；`Channel` 工作队列 + 会话 worker，翻译并发 2、按 `captionId` 顺序回填；单句失败只终态该句；队列满载给终态 + 诊断事件；每次 Start 新 generation+CTS+队列，Stop/Restart/音源边界（VRChat 进程切换）结束写端、取消并等待 worker，旧 generation 不回填。最终验证又发现相邻结果同时完成时，账本虽在锁内排序，写入提交队列却在锁外，后一个线程仍可能先写入；现已把排序与入队合并到同一临界区，并增加 10 轮、每轮 32 句的并发完成压力测试。`SpeechCaptureProcessingOptions` 把 `SplitAtSpeakerChanges` 与 `AttachSpeakerLabels` 解绑：他人语音固定切分、标签开关只控制命名、自身语音两者全关，切分模型不可用/抛错降级整段。

#### 已确认根因

这不是一个问题，而是两个会叠加的实现错误：

1. `VoiceSessionHost.OnResultReady` 在 `_processingResult == true` 时直接 `return`。上一句翻译的 195~700 ms 内，下一句不会进入 `_processingGate`，而是被静默丢弃。pyannote 将一个 VAD 段切成 A/B/C 三片时，第一片开始翻译后，后两片尤其容易命中这个分支。
2. 提交账本在锁内按 `captionId` 取出结果，却在释放锁后写入 `Channel`。A/B 几乎同时完成时，B 线程可能先写入，字幕实际按 B/A 回填。
3. `LocalSpeechCaptureSession.PlanSpeakerSpans` 用 `SpeakerLabelsEnabled` 同时控制“按换人点切音频”和“显示说话人名字”。用户关闭标签时，已经由真实双人录音证明有效的换人切分也被关闭；默认行为因此最不适合多人对话。

#### 修复方案

1. 删除结果入口的 `_processingResult` 丢弃规则。每个识别结果先分配单调递增的 `captionId` 并立即发布 Pending 字幕，再写入该次会话专属的有序工作队列。
2. 用 `Channel` 和会话 worker 取代“事件里启动未跟踪任务 + 布尔锁”。翻译最多并发 2 条，提交阶段按 `captionId` 排序；慢请求不会阻塞识别，快请求也不会越过前一句回填字幕。
3. 单条失败只将对应字幕结束为“无译文”，随后条目继续处理。队列若达到内部上限，必须把对应字幕明确结束为不可用并记录诊断，禁止静默丢句；不增加用户配置。
4. 每次 Start 创建新的 generation、`CancellationTokenSource` 和队列；Stop、Restart、音源 generation 变化时完成写端、取消并等待 worker。旧 generation 的翻译返回后不得回填字幕。
5. 增加会话级 `SpeechCaptureProcessingOptions`，至少拆成 `SplitAtSpeakerChanges` 和 `AttachSpeakerLabels`：他人语音固定开启前者，后者仍跟随用户的标签开关；自身语音两者均关闭。
6. 换人切分模型不可用或执行失败时降级为整段识别。它只改善先后说话，不承诺恢复真正同时重叠的第二路声音。

#### 自动测试要求

1. 人为阻塞 A 的翻译后连续送入 A/B/C：三条 Pending 字幕必须立即出现，最终一条不少；翻译按 C/B/A 完成时，字幕仍按 A/B/C 回填。
2. B 翻译失败不能阻塞 A/C；队列满载时每个已发布字幕都有明确终态。
3. Stop、Restart 和音源切换后，旧任务不得回填新会话或发通知。
4. 标签关闭时仍调用换人切分，但不调用声纹命名；标签开启时，两个测试说话人必须得到不同身份，文本、身份和 `captionId` 一一对应。
5. 自身语音不调用多人切分；切分模型不可用或抛错时仍产生整段字幕。
6. D28 由管线无 OSC 依赖的架构门禁固定；自身输入、自身语音各保留端到端 OSC 回归测试。
7. `Invoke-V2Validation.ps1` 禁止他人字幕管线重新出现 Chatbox/OSC 类型与调用。
8. 并发压力测试同时放行 32 句翻译并连续运行 10 轮，回填顺序必须始终与 `captionId` 一致。

### D30 · 快捷键开启字幕后窗口未回到顶层 → 已修复

**根因**：窗口创建时虽然设置了 `OverlappedPresenter.IsAlwaysOnTop`，但隐藏、最小化或被其它窗口覆盖后，重新调用 `AppWindow.Show(false)` 不能可靠地把现有 HWND 放回 Windows 的最上层窗口带。

**修复**：字幕通过快捷键显示或从最小化恢复后，调用原生 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_SHOWWINDOW)`。窗口恢复到最上层，但不夺走 VRChat 的键盘焦点，也不改变用户保存的位置和大小；兼容显示路径使用同一逻辑。

**回归测试**：原生窗口冒烟先用 `HWND_NOTOPMOST` 主动撤销字幕窗置顶，再通过真实快捷键重开并检查 `WS_EX_TOPMOST` 已恢复；前台窗口断言同时保证字幕出现后当前前台窗口不变。

| 检查项 | 结果 |
| --- | --- |
| sherpa-onnx 自带分离模型能拆两个人声吗 | ❌ 不能。只提供 **Spleeter / UVR**，都是**音乐伴奏分离**；两路都是人声时不会拆开 |
| sherpa-onnx 分离接口本机可用吗 | ❌ 用官方 `spleeter-2stems` 模型报 `ComputeStft: Invalid channel 1. Max 1`（1.13.8） |
| 换人声专用模型（SepFormer） | ⚠️ 需 Python + PyTorch 栈（与「纯 .NET + onnxruntime」冲突），无 ONNX 版本可嵌入 |
| 就算能分离，延迟可接受吗 | ❌ 按训练块推理（块长 4 s）⇒ 字幕至少晚**数秒** |

**结论：当前版本不做**，维持「保一路」；这不是“所有未来技术路线永久不可行”。重启条件见 [能力边界与决策记录.md](能力边界与决策记录.md) §6.3、§9。

### D24 · 是否引入流式识别 → ❌ 已否决（代价超过收益）

它是 `[批式固有]` 两条（字幕疏、文本大块）**唯一**的解法，但**代价超过收益**，决定不做。

| 常见误解 | 核查结果 |
| --- | --- |
| 「流式只能走云端」 | ❌ 本机 sherpa-onnx 1.13.8 已导出 `OnlineRecognizer` / `OnlineStream`；模型侧有日语 ReazonSpeech 流式、中英双语 streaming zipformer |
| 「本地流式要换技术栈」 | ❌ 用 sherpa-onnx 自家流式，C# + onnxruntime 一行都不用改 |

**真理由**：① 流式模型**一模型一语种或双语**（未发现中英日韩四语合一），而场景是「语种不确定、随时换」；② 准确率先退一步；③ 切成短句**反而丢掉翻译上下文**；④ CAM++ 说话人标签要按时间轴重做；⑤ 出字即最终，无法二次修订。
**成本账**：识别上云按音频时长计费，典型 **≈110 元/月**（每天 2 小时），是翻译费（≈3 元/月）的 **13~143 倍**。

完整记录（含实价表与三条重启前置条件：隐私 / 计费上限 / 国内可选性）见 [能力边界与决策记录.md](能力边界与决策记录.md) §7。
