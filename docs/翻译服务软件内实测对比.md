# 翻译服务软件内实测对比（DeepSeek vs 小米 MiMo）

日期：2026-09-15 · 本机 · **通过软件本身真实测试**（不是直连 API 的旁路脚本）

配套阅读：`docs/DeepSeek翻译实测.md`（2026-09 直连 API 的那一轮，方法与本文不同，**结论不要混用**）。

## 0. 为什么要重测

上一轮「小米比 DeepSeek 快 27%」的结论来自**旁路脚本**：我用 PowerShell 直接 POST 两家的
`/chat/completions`，只翻译**一句话、一个目标语言**。这和软件的真实链路不是一回事：

| 差异点 | 旁路脚本（旧） | 软件真实链路（本文） |
| --- | --- | --- |
| 每句请求次数 | 1 次 | **2 次**（依次翻译到英语 + 日语，看 `TranslationService.TranslateManyAsync`） |
| 参数 | 我自己拼的请求体 | 软件自己拼的请求体（系统提示、thinking、temperature 都按代码走） |
| 计时起点 | 发请求前 | **按下 Enter 的那一刻** |
| 计时终点 | 收到 HTTP 响应 | **UDP 报文到达**（即真正发给 VRChat 聊天框那一刻，含 144 字符截断） |
| 网络环境 | 同一个 PowerShell 进程/连接 | 软件自己的 `HttpClient`，每次翻译新建连接 |

结论：**旧数据只说明「单次调用」的快慢，不能代表用户在软件里感受到的延迟**。所以本轮全部走软件。

## 1. 测试方法（可复现）

- **被测对象**：`src/VrcTranslate.Desktop` 的 Debug 版真实进程，UI Automation 驱动，走用户真实操作路径。
- **流程**：隔离数据目录（`VRC_TRANSLATE_DATA_DIR`，没有任何缓存的矩形 / 旧设置）→ 预先写好该提供商的
  档案与路由 → 启动软件 → 找到输入浮窗 → 写入待翻译文本 → 把浮窗置前台 → `keybd_event` 发送 Enter →
  **计时开始** → 软件「翻译 → 格式化 → OSC 发送」→ 脚本用 UDP 监听收 `/chatbox/input` 报文 → **计时结束**。
- **样本**：7 句 VRChat 口语（英 / 日 / 韩 / 中 → 英语 + 日语），与 `DeepSeek翻译实测.md` 同一批语料。
- **轮次**：每个提供商**跑两轮**（14 次/家），两轮在同一时间窗内交替完成，避免时段偏差。
- **目标语言**：英语 + 日语（软件自身语音的出厂默认），所以每句 = 2 次 API 调用。
- **其它**：关闭思考模式、`temperature=0.1`（软件对非 reasoner 模型的固定策略）；小米用 `mimo-v2.5`（非 pro）。

- **两家都能用**：中 / 日 / 韩 / 英 译向都正确、无漏译、无解释性废话（都遵守了「只输出译文」）。
- **差异在措辞习惯**：DeepSeek 更偏口语（「单挑boss了」「麦克风卡了」）；小米更书面（「有点卡顿」「一人挑战」），
  日语侧小米偏敬语（「〜だね」「〜ます」），DeepSeek 偏随意（「〜な」）。**没有对错，看口味。**

  不是模型的问题）；小米那轮的日语译文同样吃满了上限。

| 项 | DeepSeek `deepseek-flash` | 小米 `mimo-v2.5` |
| --- | --- | --- |

| 输出 | 4 元（空闲）/ 8 元（高峰）每百万 tokens | 官方未公开查证 |
| 实测 tokens/句 | 39.6 输入 + 7.4 输出 | 45.4 输入 + 8.6 输出 |
| 折算单句（单目标） | ≈ 0.00007 元（空闲）/ 0.00014 元（高峰） | ≈ 0.00004 元起 |
| 折算每月 1 万句 | ≈ 0.7 ~ 1.4 元 | ≈ 0.4 元起 |

**结论：价格不是决定因素**——两家都是"每月几毛到几块钱"，差一倍也还是忽略不计。
真正影响体验的是延迟，而延迟上 **DeepSeek 明显更好**。

## 5. 结论

1. **默认继续用 DeepSeek**（这也是软件当前的出厂默认）。软件内实测它比小米快 **56~61%**，
   且更稳（两轮几乎一致，小米抖动近一倍）。
2. **小米可以作为备选**：它的优势是**输入单价更低**和"多一个可用服务"（某家限流/涨价时切换），
   但**不要在追求低延迟时选它**——按本机数据它每句会多等约 1 秒。
3. **上一轮旁路脚本的"小米快 27%"结论作废**：那是单次调用、单目标语言的测法，
   换成软件真实链路（每句两次调用、含 OSC 发送、计时从按键算起）后结论反转。
   这也说明**测翻译延迟必须在软件里测**，旁路数据不能代表用户感受。
4. **软件侧可优化点（下一步可选）**：现在每句是**串行两次调用**（英语→日语），
   如果改成并行，理论端到端能接近减半（约 900 ms → 更接近单次调用时间）。
   这是独立于"选哪家"的优化，收益可能比换提供商更大。

## 5.1 后续核查：思考模式是否真的关了？以及"为什么这么慢"

用户在看到"小米 2553 ms"后追问：**调用小米时确定关闭了思考模式吗？为什么这么慢？** 核查结果如下。

### (1) 思考模式确认关闭——以响应字段为证

判据不是"我发没发参数"，而是响应里有没有 `reasoning_content`：

| 场景 | reasoning 长度 | 输出 tokens | 耗时 |
| --- | --- | --- | --- |
| 小米 `mimo-v2.5`，`thinking=disabled`（软件默认） | **0**（连续 7 次全 0） | 12 | 629 ~ 1505 ms |
| 小米 `mimo-v2.5`，`thinking=enabled`（对照） | **788 字** | **186** | **4307 ms** |
| DeepSeek，`thinking=disabled` | **0** | 11 | 436 ~ 1032 ms |
| DeepSeek，`thinking=enabled`（对照） | **396 字** | **106** | 1374 ms |

开思考时三项指标（reasoning 内容、输出 tokens、耗时）同时暴涨 → **开关真实生效**，不是被服务端忽略。

### (2) 慢的根源：每句发**两次**请求，而且**串行**

同一句话、**单次调用**、连接复用下的原始数据：

| 服务 | 单次调用（4 次） | 中位 |
| --- | --- | --- |
| DeepSeek `deepseek-flash` | 436 / 481 / 837 / 997 ms | ≈ **660 ms** |
| 小米 `mimo-v2.5` | 629 / 782 / 1052 / 1173 ms | ≈ **920 ms** |

而软件里一句要翻**两个目标语言**（英语 + 日语，见 `AppState.SelfTranslationTargets`），
`TranslationService.TranslateManyAsync` 里是 **foreach 串行**：

```
用户感知延迟 ≈ 单次调用 × 2 + OSC 发送
DeepSeek: 0.66 × 2 ≈ 1.6 s   ← 与软件实测中位 1590 ms 吻合
小米:     0.92 × 2 ≈ 2.5 s   ← 与软件实测中位 2553 ms 吻合
```

**结论：慢的主因是"每句两次串行请求"这个架构，不是某一个模型慢。**

### (3) 口径更正：第 2 节的"慢 61%"要这样读

| 口径 | DeepSeek | 小米 `mimo-v2.5` | 谁快 |
| --- | --- | --- | --- |
| 单次调用（连接复用，本小节实测） | 中位 ≈ 660 ms | 中位 ≈ 920 ms | DeepSeek 快约 1.4 倍，但**区间高度重叠**（436~997 vs 629~1173） |
| 软件内端到端（每句 2 次串行调用） | 中位 1590 ms | 中位 2553 ms | DeepSeek 快 61%（**含"两次串行"的放大**） |
| 最早那次旁路单次（每次新建连接） | 926 ms | 680 ms | "小米快 27%" —— **三重缺陷**：每次重建 TLS、仅 5 句样本、口径与软件不同，作废 |

所以要分清两句话：**"小米比 DeepSeek 慢"成立，但差距是 1.4 倍量级，不是 61%**；
**"61%" 描述的是用户在当前架构下的实际感受**（因为它把两次串行都算进去了）。

### (4) 由此得到的优化优先级

```
现在（串行）：  英语 ────► 日语 ────► 发送           ≈ 1.3 ~ 1.6 s
改成并行：      英语 ────┐
                         ├──► 发送                   ≈ 0.7 ~ 0.9 s
                日语 ────┘
```

并行化对**两家都有效**，收益（约减半）远大于"从小米换回 DeepSeek"（约 1.4 倍，且只在模型层面）。
详见 `docs/并行翻译实施方案.md`。

### (5) 句内并行实施后的实测对比（2026-09-15 深夜）

按方案把 `TranslateManyAsync` 从"foreach 串行"改成"一次识别/输入里的多个目标**同时**发请求"
（细节见 `docs/并行翻译实施方案.md`），用**同一套软件内测法**（UI Automation 驱动真实进程、
计时从 Enter 到 OSC 报文）重跑同一批 7 句：

| 提供商 | 改前中位 | **改后中位** | 变化 | 改后区间 |
| --- | --- | --- | --- | --- |
| DeepSeek `deepseek-flash` | 1590 ms（n=14） | **1031 ms**（n=7） | **-35%** | 776 ~ 1224 ms |
| 小米 `mimo-v2.5` | 2553 ms（n=14） | **1356 ms**（n=14，两轮合并中位） | **-47%** | 1101 ~ 1966 ms |

改后 DeepSeek 逐句原始值（ms）：974 / 776 / 1031 / 1081 / 984 / 899 / 1224。
小米改后跑了两轮：第一轮 1282 / 1518 / 1616 / 失败 / 1626 / 1408 / 1580（中位 1580，其中 1 句未收到报文），
第二轮 1231 / 1511 / 1234 / 1132 / 1101 / 1356 / 1966（中位 1356，7 句全部成功）；
合并两轮 13 个有效样本的中位为 **1356 ms**。

**读数**：

1. 两条链路的收益一致（-35% / -38%），说明瓶颈确实是"两次调用串行"，而不是某家服务；
2. 改后 DeepSeek 的中位约 **1 秒**，比改前小米的 2.5 秒快了 2.4 倍——**架构优化大于换服务商**；
3. 区间也收窄了（改前 1290~2227 / 1797~3656，改后 776~1224 / 1282~1626），字幕节奏更稳。
4. 小米那一轮有 1 句未收到报文（`no datagram`），已重跑一轮核对，属偶发（见下）。

**关于"语音能不能并行"**：自身语音走的是同一个 `TranslateSelfAsync` → `TranslateManyAsync`，
所以**同一处改动就让语音链路一起受益**；他人语音字幕只有一个目标语言（中文），
本来就只有一次调用，**没有并行收益**——这一点用户问得对。

## 6. 局限（勿过度解读）

- 单机、单一网络环境、单一时间窗（两轮相邻），**没有跨天/跨地域采样**；
- 样本量小（每家 14 次），只够看中位与抖动趋势，不足以下"某家长期更快"的结论；
- 小米的免费额度、输出单价未从官方页面查证（官网价格页需登录），成本表中小米部分按公开报道估算；
- 小米 `mimo-v2.5-pro`、思考模式、并发请求、术语库注入、超长文本均未纳入本轮；
- 首句含 TLS 建连开销（每次翻译新建连接），两家的第一句都偏慢，本条对结论影响很小但存在。
