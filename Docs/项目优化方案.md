# VRCTranslate 2.0 全面重构方案

## 1. 结论

当前版本不适合继续在 Qt 页面、OCR 悬浮球、语音悬浮球和多层配置上做局部修补。建议以 **VRCTranslate 2.0** 作为一次产品级重构：重新设计用户流程、重新定义运行时架构、重新实现 Windows 前端，并把现有 Python/Qt 版本降为旧版兼容与迁移工具。

目标不是把原有页面搬到另一种语言，而是交付一款 Windows 原生、默认无悬浮球、按任务操作、安装后不依赖 Python 的新软件。首个 V2 版本不实现 OCR，只在指南中说明可使用 QQ 的 `Ctrl+Alt+F` 调用系统的屏幕翻译；以后是否增加集成能力再单独评估。

核心方向：

- 正式软件改为 **C# + .NET 10 + WinUI 3 + Windows App SDK**，采用 VRC-Fisher 已验证的 Windows 原生路线；
- 运行端移除 Python、PySide6、PyInstaller 和 Python OCR/语音适配器；
- 主界面只保留“运行、翻译、语音、指南、设置”五类页面；
- OCR 只保留一条外部工具说明，不设置 OCR 页面、模型、浮窗或快捷键；语音改为快捷键启动的任务流，取消常驻语音悬浮球；
- 将“服务档案、路由、模型、显示参数”隐藏到任务预设背后，普通用户只选择场景和目标语言；
- 用统一的状态卡、字幕覆盖层和错误中心替代多个互不相同的浮窗；
- 以一次性配置迁移和明确的 V2 数据格式取代对旧 UI 的长期兼容。

## 2. 参考 VRC-Fisher 得出的技术判断

已检查的参考项目：

- [`VRC-Fisher/README.md`](https://github.com/FlyPig01/VRC-Fisher/blob/main/README.md)：正式软件为 C#，用户端不需要 Python、CUDA 或 Miniconda；
- [`VRC-Fisher/docs/architecture.md`](https://github.com/FlyPig01/VRC-Fisher/blob/main/docs/architecture.md)：采用 `Desktop → Infrastructure → Application → Core`，捕获、推理和控制不运行在 UI 线程，只保留最新帧；
- [`VRC-Fisher/docs/archive/technical-stack-decision-2026-08-14.md`](https://github.com/FlyPig01/VRC-Fisher/blob/main/docs/archive/technical-stack-decision-2026-08-14.md)：选择 WinUI 3、Windows Graphics Capture、ONNX Runtime DirectML、Inno Setup，并明确不采用 WPF、Avalonia、Electron、PyInstaller；
- `VRC-Fisher/app/src/VrcFisher.Desktop/Pages/`：页面按运行、模型、指南、设置拆分；
- `VRC-Fisher/app/src/VrcFisher.Desktop/Overlay/`：覆盖层由原生 Windows 窗口统一管理，不依赖常驻工具球；
- `VRC-Fisher/app/src/VrcFisher.Desktop/Ui/UiFactory.cs` 和 `App.xaml`：使用统一 Fluent 资源、卡片、标题和表单构造，页面视觉规则集中管理。

这套方式适合 VRCTranslate，因为本项目同样是 Windows-only，核心能力依赖 WASAPI、全局热键、透明字幕窗口和 Windows 原生安装。首个 V2 不再需要屏幕捕获和 OCR 推理，因此可以进一步缩小运行时边界。C# 迁移的价值在于删除 Python 运行时、统一 Windows DPI/窗口行为、降低发布依赖，而不是单纯改变编程语言。

## 3. V2 产品形态

### 3.1 首屏只做一件事：开始翻译

软件启动后直接进入“运行”页，显示一个运行状态卡：

| 状态 | 主按钮 | 页面内容 |
|---|---|---|
| 未配置 | 开始设置 | 当前缺少的模型、翻译服务和音频权限 |
| 已就绪 | 启动语音字幕 | 当前音频源、目标语言和预设 |
| 语音运行中 | 暂停语音 | 最近原文、译文、识别/翻译延迟 |
| 错误 | 查看并修复 | 错误阶段、原因、下一步操作 |

用户不需要进入多个功能页拼装设置，也不需要寻找 OCR 菜单。运行页始终告诉用户下一步是什么。

### 3.2 取消常驻悬浮球

V2 不创建 OCR 球或语音球，也不把常驻置顶窗口当作主要导航。替代设计如下：

- 语音：默认快捷键 `F7`，按下后开始/暂停字幕；
- 翻译自己的消息：默认快捷键 `Ctrl+Alt+I`，打开输入条；
- 托盘菜单提供同样的两个动作；
- 运行中的语音只显示轻量状态条和字幕结果，不显示可拖动球；
- 需要调试时，运行页提供“显示控制条”开关，控制条使用靠边自动隐藏的窄条，退出运行后自动消失。

这样可以彻底解决悬浮球长期占据画面、状态不明确、必须点击球才能操作的问题。V2 不重复实现 QQ、微信等应用已经提供的屏幕翻译能力。

### 3.3 OCR 说明

指南只保留一句固定说明：

> 需要屏幕翻译时，可在 QQ 中按 `Ctrl+Alt+F`；其他软件的快捷键以其自身版本为准。VRCTranslate 暂不提供 OCR，后续是否增加集成能力将另行评估。

这句话不引导用户配置 OCR，也不创建 OCR 页面、模型、权限、状态或运行入口。以后如果外部软件快捷键发生变化，只更新指南文案，不改变 V2 架构。

### 3.4 语音新流程

语音字幕不再是“先展开球，再点播放”。用户按 `F7` 即可开始或暂停：

- 默认捕获前台 VRChat 进程输出；
- 运行页显示音频源、识别语言、目标语言和当前延迟；
- 字幕覆盖层默认停靠在屏幕下方，只有新字幕出现时短暂显示；
- 语音结果按“原文小字、译文大字”显示，历史条数默认 3 条；
- 语音停止后覆盖层自动收起，不留下常驻控件；
- 用户需要测试其他程序时，在运行页显式选择进程，不改变默认 VRChat 体验。

### 3.5 自身消息

保留快捷输入，但改为 Windows 原生轻量输入条：直接输入文字，翻译预览、复制和发送三步在同一条面板完成。目标语言和翻译模型由统一翻译方案决定，不再让用户在快捷输入页与翻译路由之间来回切换。

## 4. V2 界面信息架构

### 4.1 五个页面

| 页面 | 普通用户看到的内容 | 高级内容 |
|---|---|---|
| 运行 | 启停、当前阶段、快捷键、最近结果、延迟 | 音频线程、网络请求和调试状态 |
| 翻译 | 当前翻译方案、模型选择、凭据测试、目标语言 | 服务档案、方向质量矩阵、回退策略 |
| 语音 | SenseVoice 安装、音频源、语音字幕 | 识别模型、VAD、设备诊断 |
| 指南 | 首次配置、快捷键、隐私与支持范围 | 故障诊断链接 |
| 设置 | 语言、显示位置、快捷键、日志 | 窗口、音频和高级网络参数 |

不再保留 OCR 页面，也不再要求用户在多个入口间拼装翻译配置。翻译模型有独立的一等页面，文字输入和语音字幕默认使用同一个翻译方案。

### 4.2 一个翻译路由管理文字和语音

**文字和语音可以共用一个路由，但不能把 ASR 识别模型和翻译模型混为一谈。** V2 的统一路由只负责“已经得到的文字如何翻译”，因此结构如下：

```text
文字输入 / 语音识别结果
                     |
             TranslationRoute
                     |
       翻译模型 + 目标语言 + 术语 + 校验
                     |
       预览 / 字幕 / OSC Chatbox
```

路由包含以下公共字段：

- 当前翻译模型；
- 目标语言；
- 源语言策略（自动检测、固定语言、跟随识别结果）；
- 术语库开关；
- URL/用户名/数字等不变量保护；
- 超时、重试和失败回退策略。

两种输入统一使用这条路由：

| 输入来源 | V2 行为 | 是否单独配置翻译模型 |
|---|---|---|
| 快捷文字 | 输入或粘贴文字后翻译，可发送 OSC | 否，继承默认路由 |
| 他人语音 | SenseVoice 输出最终原文后翻译并显示字幕 | 否，继承默认路由 |

这样用户只配置一次模型，语音字幕和文字输入自然保持术语、目标语言和格式一致。高级设置允许为语音指定固定源语言，或为某个输入临时覆盖模型，但覆盖必须明确显示“已覆盖默认方案”。未来如果增加 OCR 文本接入，它直接作为第三种文字输入复用该路由，不新增 OCR 专用配置。

语音识别模型、进程音频源和 VAD 仍属于语音功能自身；它们不是翻译路由。未来重新加入一次性 OCR 时，OCR 识别模型也只属于 OCR 扩展，不会复制翻译配置。

### 4.3 翻译模型配置页

翻译页必须同时承担“选择模型”和“配置模型”，不能让用户先去服务档案页创建对象，再回到路由页寻找对象。页面首屏显示当前方案：

```text
当前翻译方案
模型：腾讯云翻译 · TextTranslate        [更换]
目标：简体中文                          [选择]
状态：已验证，最近测试 380 ms            [测试]
使用：文字输入、他人语音                [查看覆盖]
```

点击“更换”打开模型选择器，按以下顺序操作：

1. 选择服务类型：机器翻译、大模型、实验性服务；
2. 选择服务商模板，自动填充协议、区域和模型示例；
3. 只填写该服务必需的地址、密钥和模型名，可选字段折叠；
4. 点击“测试连接并翻译示例”，一次验证凭据、语言方向、返回格式和延迟；
5. 测试通过后点击“设为当前方案”；
6. 页面立即显示该模型会被文字和语音共同使用。

已有模型以卡片显示：服务商、模型、支持语言、是否支持自动检测、文本/图片能力、最近成功率、P50/P95、费用提示和验证时间。删除或修改当前模型时，页面必须先要求选择另一个已验证模型，避免运行中突然失去翻译服务。

多模态图片模型不作为 V2 功能入口。若未来新增 OCR 扩展，图片识别完成后仍回到同一 `TranslationRoute`，不额外创建第三套路由。

### 4.4 首次配置向导

首次启动只走一个向导：

1. 选择界面语言和目标语言；
2. 配置并测试一个翻译模型，直接设为默认方案；
3. 选择是否启用他人语音，启用后安装并验证 SenseVoice；
4. 选择 VRChat 音频源，自动测试回环音量；
5. 检查 OSC、快捷键和字幕位置；
6. 进入运行页。

向导完成后不再显示 OCR、未使用的语音模型和多模态选项。重新运行向导只修改默认翻译方案或语音开关，不删除 API 密钥、术语库和历史配置。

## 5. 全新技术架构

### 5.1 正式软件技术栈

| 层 | V2 方案 |
|---|---|
| 语言 | C#、.NET 10、Windows x64 |
| UI | WinUI 3、Windows App SDK、Fluent 资源 |
| 语音推理 | sherpa-onnx C# 原生绑定，SenseVoice 优先 |
| 音频 | WASAPI loopback、Windows 音频设备枚举 |
| 网络 | `HttpClient`、`ClientWebSocket`、云服务 SDK 或手写协议适配器 |
| OSC | C# UDP/OSC 适配器 |
| 配置 | `System.Text.Json`，版本化 JSON schema |
| 日志 | `Microsoft.Extensions.Logging`，结构化文件日志 |
| 安装 | Inno Setup，self-contained，用户不需要 Python 或 .NET |
| 测试 | xUnit 核心测试、WinAppDriver/Windows App SDK UI 场景、现场回放测试 |

不采用 WPF、Avalonia、Electron、WebView、Python sidecar、RapidOCR 或 OCR 专用 ONNX 运行时。首个 V2 不实现屏幕捕获和 OCR；未来重新评估 OCR 时，必须作为独立扩展立项。

### 5.2 分层

```text
Desktop
  -> Infrastructure
  -> Application
  -> Core
```

- `Core`：翻译任务状态机、语言能力、术语和不变量契约、ASR 结果、质量门禁；
- `Application`：启动/停止事务、统一翻译路由、配置迁移、模型目录、运行快照和错误恢复；
- `Infrastructure`：WASAPI、SenseVoice、HTTP/WebSocket、OSC、文件和 Win32；
- `Desktop`：WinUI 页面、覆盖层、托盘、热键、本地化和资源组装。

页面不得直接调用 WASAPI、模型、HTTP、OSC 或 Win32。音频、识别和网络请求不得运行在 UI 线程；跨层只传递普通 DTO、字节数组、时间戳和错误码。

### 5.3 运行管线

```text
快捷文字
  -> TextNormalizer
  -> TranslationRoute
  -> InvariantGuard
  -> 预览 / OSC Chatbox
```

```text
VRChat WASAPI Loopback
  -> Audio Segmenter / VAD
  -> SenseVoice
  -> LanguageNormalizer
  -> TranslationRoute
  -> InvariantGuard
  -> CaptionStore
  -> WinUI SubtitleOverlay
```

两条管线共享同一个 `TranslationRoute`、术语库、不变量保护、质量监控和结果存储。文本输入直接进入路由，语音输入只负责把音频转换为最终文字；两者不重复配置翻译服务，也不共享音频线程和识别会话。

### 5.4 模型与安装包

参考 VRC-Fisher 的模型页设计，语音识别模型是独立资源，不打进主程序。翻译模型是网络服务配置，不下载推理模型：

```text
<安装目录>/
  program/       WinUI 程序与语言资源
  config/        V2 设置、任务预设、服务资源
  models/        ASR 模型、版本和许可证
  downloads/     可恢复下载暂存
  logs/          当前和上一会话日志
```

模型卡显示用途、语言、版本、大小、运行后端、校验状态和删除影响。下载成功后原子替换旧模型；失败或取消不得破坏可用版本。基础安装包只包含 UI、OSC、HTTP 和音频捕获，SenseVoice 首次启用语音时按需安装。

## 6. 翻译质量重做

### 6.1 路由从“服务选择”改为“方向决策”

结论是：**V2 使用一个翻译路由管理文字输入和语音识别文本。** 两者在进入路由前的输入类型不同，但最终都是待翻译字符串；ASR 的识别模型不属于这个路由。未来若增加 OCR，OCR 结果也可以直接接入同一路由。

V2 不再让用户维护三套几乎相同的服务选择。系统维护一张本地质量矩阵：

```text
(source, target, provider, model) -> quality, p50, p95, cost, last_verified
```

只从用户已经配置并验证通过的服务中推荐，不自动新增付费服务。用户看到的是“推荐、可用、实验性、未验证”以及最近测试日期；高级用户可手动覆盖。

路由解析顺序固定为：输入自带的可信语言提示 → 用户设置的固定源语言 → 服务支持的自动检测。若当前服务不支持自动检测，页面在保存前就要求明确源语言；不会等到文字输入或语音运行时才报错。目标语言只有一个默认值，文字和语音字幕都继承它。

### 6.2 不变量保护升级

将 URL、邮箱、`@用户名`、OSC 地址、路径、数字、代码片段、VRChat 世界/Avatar 名称抽取为带类型、值、顺序的 token AST。翻译后必须检查：

- token 数量和类型一致；
- token 原值一致；
- token 顺序没有变化；
- 数字、版本号、坐标和 URL 查询参数没有变化。

检查失败时自动重试一次；仍失败则显示原文和错误标记，不发送损坏译文。错误按“丢失、重复、改写、顺序变化”分类计数，加入发布报告。

### 6.3 质量数据和模型边界

- OCR 不属于 V2 功能，只在指南中保留 QQ `Ctrl+Alt+F` 的外部工具说明；
- SenseVoice 正式支持中、英、日、韩，端到端 P50 目标 0.4–0.6 秒；
- 法、德、俄语音识别在没有约 1 秒延迟模型前不列为正式本地实时功能；西班牙语只能作为实验组件；
- 翻译发布门禁：成功率 ≥99%、不变量保留率 100%、数字召回率 ≥99%、严重误译率 ≤5%；
- 每个版本使用 30 句通用样本、30 句 VRChat 领域样本、30 段真实噪声语音，并人工复核否定、人称、敬语、俚语、专名和世界名。

### 6.4 源语言能力必须显式

服务不支持自动检测时，UI 禁用“自动”并要求选择源语言。旧配置不得静默迁移为日语等固定语言。ASR 输出的 `yue` 等代码先统一到 V2 语言表，无法支持时应明确提示，而不是把错误代码直接发送给翻译服务。

## 7. 外观和交互设计

视觉风格直接采用 VRC-Fisher 的设计方向，但针对翻译工具重新定义密度：

- 使用 WinUI Fluent 主题、Segoe UI、统一资源字典和 6px 小圆角；
- 页面采用单列滚动布局和少量大状态卡，不使用当前 Qt 的多层卡片网格；
- 运行状态卡固定在窗口右上角，主行显示阶段，次行显示下一步和快捷键；
- 覆盖层使用半透明深色字幕底板，默认 3 条，原文小、译文大，背景不长期显示；
- 状态色只表达运行、等待、错误和未配置，不使用青色边框和常驻动画制造视觉噪声；
- 调试信息只在调试模式显示，包含检测框、置信度、帧龄和各阶段延迟；
- 所有窗口支持 100/125/150/175/200% DPI，多屏字幕位置使用物理像素与逻辑像素明确转换；
- 语音字幕覆盖层支持一键隐藏，隐藏后不影响快捷键、托盘和运行页。

## 8. V1 到 V2 的迁移策略

这不是在旧 Qt 代码中逐个替换控件，而是建立新的 `v2/` 解决方案和新的配置 schema。

### 阶段 0：冻结行为契约（1–2 周）

- 从现有 Python 提取 OSC、翻译、术语、不变量、语言能力和配置样例；
- 生成 JSON schema、翻译请求/响应 DTO、ASR 结果 DTO 和错误码表；
- 固定质量集、性能基线和 V1 配置只读导入规则。

### 阶段 1：WinUI 壳与运行页（3–5 周）

- 建立 `Core/Application/Infrastructure/Desktop` 四层 C# solution；
- 实现 WinUI 3 主窗口、托盘、指南、运行页、状态卡和本地化；
- 实现全局热键、任务预设、配置保存和 V1 配置导入；
- 暂不接语音识别，先完成启动、停止、错误呈现和安装器。

### 阶段 2：翻译、OSC 和文本输入（3–5 周）

- 实现 `HttpClient` 翻译适配器、质量矩阵、token AST、不变量校验和术语库；
- 实现 OSC Chatbox、自身消息输入条和服务测试向导；
- 通过核心契约测试对比 V1 结果，确保不变量和消息格式不退化。

### 阶段 3：WASAPI 与语音字幕（4–8 周）

- 实现进程回环音频、VAD、SenseVoice C# 绑定、语言归一化和字幕覆盖层；
- 默认只接入中英日韩；实验性模型必须单独下载且明确显示延迟；
- 完成音频设备、前台进程、噪声和停止事务的现场测试。

### 阶段 4：替换发布（2–4 周）

- 用 Inno Setup 生成 self-contained x64 安装包；
- V1 只负责导出配置和提示用户迁移，V2 成为新的正式入口；
- 保留 V1 可执行文件一个版本周期，方便回滚；
- 完成 Windows 10 19041、Windows 11、多 DPI、多屏、VRChat 窗口化/无边框和遮挡测试。

## 9. V2 是否成功的硬指标

只有全部满足才替换 V1：

- 用户首次安装到首条文字或语音译文 ≤60 秒；快捷文字只需一次快捷键，语音只需一次快捷键；
- 默认画面没有常驻 OCR 球和语音球；隐藏字幕覆盖层不影响快捷键和托盘；
- 基础安装不需要 Python、虚拟环境、Miniconda 或预装 .NET；
- 基础包、冷启动、空闲 RSS、ASR RSS 均不高于优化后的 V1；目标是基础包和空闲 RSS 至少降低 20%；
- SenseVoice 中英日韩端到端 P50 ≤0.6 秒，P95 <1 秒；
- URL、用户名、数字、OSC、版本号和术语 token 回归 100% 通过；
- 迁移后的配置、快捷键、术语库和服务资源可回滚；
- WinUI UI 场景测试覆盖首次向导、翻译模型配置、启动/停止语音、快捷文字、隐藏字幕、模型下载和错误恢复。

任何一项不达标都不能以“界面已经重写”为理由发布。OCR 不属于 V2 的发布门槛；未来重新立项时必须单独提交需求、性能预算和质量验证。

## 10. 明确不再延续的旧设计

- 不再把 OCR、OCR 悬浮球、OCR 选区控制条和 OCR 模型作为 V2 功能；
- 不再把语音球、字幕窗各自设计成长期存在的浮窗；
- 不再让普通用户看到 VAD 阈值、队列容量、TTL 等实现参数；
- 不再按“服务档案/路由/模型包”要求用户跨页面拼装功能；
- 不再以 PySide6 + PyInstaller 作为正式发布技术栈；
- 不再为兼容旧界面而保留旧页面结构；兼容只存在于一次性数据迁移和 V1 回滚。
