## 2. `[当前模型固有]` 两路声音真正重叠 → 只有一路能被识别

### 现象（实测）

把两段真人语音按 50% 增益叠加（模拟两人同时讲话）送进内置 SenseVoice：

| 合成音频 | 识别结果 | 丢失 |
| --- | --- | --- |
| 中文 5.6 s + 日语 5.6 s **完全重叠** | 「うちの中学は別当生で持ってきない場合は50円の学校販売のパ。」 | **中文整段** |
| 英语 4.6 s + 韩语 4.6 s **完全重叠** | 「The tribal chieftain called for the boy and presented.」 | **韩语整段** |
| 中文 5.6 s + 日语后半段插入（**半重叠**） | 「开饭时间早上9点至下午5点。」 | **日语整段** |

**对照**：顺序换语种（中文说完 0.6 s 后日语开始）两段**都**识别出来了；单语种四段**逐字正确**。
⇒ 问题不在「换语种」也不在「长音频」，只在**两路声音时间上重叠**。

### 影响与根因

被压住的那一路**完全不产生字幕**——用户看到的不是「翻译错了」，而是「什么都没出现」。
根因：**SenseVoiceSmall 是单说话人模型**，输入假设是「一段只有一个说话人的音频」；两路叠加后能量/音素更清晰的那路占优，另一路被当噪声。

### 语言参数完全无效（50 格矩阵）

| 音频 | mode=auto / zh / ja / ko / en |
| --- | --- |
| 中文+日语 完全重叠 | 五种模式**都只有日语** |
| 英语+韩语 完全重叠 | 五种模式**都只有英语** |
| 中文+日语 半重叠 | 五种模式**都只有中文** |

这也是「为语言选择器加功能」被否掉的证据（见《实验记录》§识别层）。

### 无效方向（都已排除）

| 方向 | 为什么无效 |
| --- | --- |
| 换翻译引擎 | 翻译层拿到的就已经只有一路文本 |
| 调 VAD 阈值 / 静音时长 | VAD 决定「什么时候切一段」，不决定「一段里有几个人」 |
| 指定 source language | 实测 5 种模式输出逐字相同 |
| 中文跳过 / 延迟优化 | 与识别内容无关 |

### 包内已有模型**做不到**「分离」（重要澄清）

`Models\speaker\` 里的 pyannote 分割 + CAM++ 声纹，**只做「这段话是谁说的」（识别与匹配），不做「把两个人的声音拆开」（分离）**。
要分离必须引入**新的模型**——而这条路的结论见 §6.3。

### 产品原则（已拍板）

> **宁可漏一个人，也不要出乱码。** 两路混音硬识别出来是「四不像」的烂句，用户会以为翻译坏了；现在的「没出现」至少是干净的失败。

### 复现

```powershell
python artifacts\mix_audio.py            # 合成重叠音频
pwsh -NoProfile -File artifacts\bench-asr.ps1 `
  -Files mix_zh_ja_over,mix_en_ko_over,mix_zh_ja_half -Modes auto,zh,ja,ko,en -Samples 10
```

原始记录（50 格）：`docs/evidence/asr-matrix.jsonl`。

## 3. `[批式固有]` 字幕间隔长、文本大块

**连说型的人**（句间几乎没有静音，只有段落结束才停）会遇到：字幕隔很久才出一条，**一条里塞了三四个句子**。

> 用户原话：「硬切影响的很小，只是**字幕出现的间隔长，文本大块大块的**」

### 根因

批式识别**必须先拿到一段完整音频才能出文本**，所以「什么时候切」只能靠外部规则，而规则只有两条：

| 触发点 | 谁会命中 | 后果 |
| --- | --- | --- |
| 静音满 **600 ms** | 句间停顿 ≥600 ms 的人 | 正常出字幕 |
| 硬切 **12 秒** | **连说型**（句间停顿只有 100~200 ms） | **每 12 秒一条大块字幕** |

**12 秒硬切不是缺陷，是连说型唯一的兜底**——没有它，那个人说话时永远切不出来。
把它调小（如 5 秒）能让字幕更勤，**但改不了「必须靠切」这个范式**。

### 更根本的一点：模型输出没有段内结构（实测）

实测（真实双人播客前 8 分钟 / 58 个 VAD 段）：**98.3% 的段以句号结尾，而 0% 的段内部出现标点**——
SenseVoice **只在整段末尾补一个标点，段内不断句**。这直接否掉了两个「靠标点救场」的方案（§6.1、§6.2）。

### 唯一解法（**已否决**）

理论上只有**换流式识别**能解：触发点从「静音/硬切」变成「引擎自己知道这句说完了」。
**但已否决**——理由与成本账见 §7。⇒ 本条**作为长期边界接受**。

## 4. `[批式固有]` 说完话到字幕出现 0.83~1.75 s

| 环节 | 耗时 | 说明 |
| --- | ---: | --- |
| VAD 等静音收尾 | **600 ms** | 判断「说完了」的手段，固定存在 |
| 本地识别 | 130~450 ms | CPU int8，压不动 |
| 翻译 HTTP | 100~700 ms | 腾讯/阿里 195~270 ms，DeepSeek 495 ms，小米 696 ms |
| 推送 OSC/字幕 | 约 1 ms | 可忽略 |

**为什么不能把 600 ms 调小**：说话人之间的停顿区间**互相重叠**——

| 说话人 | 句内停顿 | 句间停顿 | 600 ms 的结果 |
| --- | ---: | ---: | --- |
| A（想词型） | 600~900 ms | 900 ms | 句子被切成两条 ⛔ |
| B（连说型） | 150 ms | 250 ms | 两句并成一条 ⛔ |
| C（正常） | 300~500 ms | 600~700 ms | 刚好 ✅ |

**A 的句内停顿（700 ms）比 B 的句间停顿（250 ms）还长** ⇒ 任何固定阈值都会切错一部分人、并错另一部分人。

### 强切损耗（实测在案，不修）

- 12 秒强切每次吃约 **1280~1344 样本（80~84 ms）**；检测器预热约 1280 样本（80 ms）；
- **真实语音从未触发 12 秒强切**——实测最长自然段 **5.46 s**；
- 回归防线：`SileroVadSegmenterTests.A_continuous_signal_is_force_cut_at_12s_without_eating_speech`。

## 6. 决策记录：评估过但**不做**的功能

### 6.1 ❌ 文本回退早切（D22）

**原设想**：静音 250 ms 就先切段识别，用识别文本的**末尾标点**判断说完没有——句号则上屏，逗号则挂起、等下一段拼起来重识别。

**为什么做不了**（实测，真实播客 58 段）：

| 指标 | 数值 |
| --- | ---: |
| 段尾是句子结束符（。？！?!.） | **57 / 58 = 98.3%** |
| **正文内部出现句子结束符的段** | **0 / 58 = 0%** |

98.3% 都以句号结尾 ⇒ 判定**永远走「立即上屏」**；0% 段内有标点 ⇒ 「末尾是逗号」**几乎不存在** ⇒ **挂起与合并永不触发**。
方案于是退化成「单纯把静音阈值 600 → 250 ms」——正是它要避免的事。

**跨语种复核**：中/日/韩/英四语，识别结果**都只有末尾 1 个标点**，不是英语特例。

**复现**：`artifacts/measure-sentence-punctuation2.ps1`（含 ASCII 标点的修正版）、`artifacts/check-punctuation-langs.ps1`。

### 6.2 ❌ 按标点把长文本拆成多条字幕

**为什么做不了**：与 §6.1 同源——**段内 0% 有标点，没有标点可拆**。
（即使能拆，它也只改显示：识别还是 12 秒一次，触发时机一点没变，反而把 1 次翻译变成 4 次。）

### 6.3 ❌ 当前随包技术栈用音源分离救「重叠丢一路」（D23）

| 检查项 | 结果 |
| --- | --- |
| sherpa-onnx 自带分离模型能拆两个人声吗 | ❌ 不能。只提供 **Spleeter / UVR**，都是**音乐伴奏分离**；两路都是人声时不会拆开 |
| sherpa-onnx 分离接口本机可用吗 | ❌ 用官方 `spleeter-2stems` 模型，`process()` 报 `ComputeStft: Invalid channel 1. Max 1`（1.13.8） |
| 换人声专用模型（SepFormer） | ⚠️ 需 **Python + PyTorch** 栈（与「纯 .NET + onnxruntime」冲突），且无 ONNX 版本可嵌入 |
| 就算能分离，延迟能接受吗 | ❌ 按训练块推理（SepFormer 块长 **4 s**）⇒ 字幕至少晚**数秒**，等于把功能做废 |

**结论：当前版本不做**，维持「保一路」（§2 的产品原则）。这里证明的是 sherpa-onnx 1.13.8 随包能力和本轮候选不适用，不能外推成“人声—人声分离永久不可行”。只有同时满足以下条件才重启评估：

1. 先用真实 VRChat 会话统计真正重叠语音的占比，确认收益值得包体与算力成本；
2. 候选模型可由 .NET / ONNX Runtime 直接部署，不重新引入 Python / PyTorch 运行栈；
3. 处理块不超过约 1 秒，实时因子、内存和发布包体满足桌面实时字幕要求；
4. 分离后双路识别的准确率明显优于当前“保一路”，且不会大量产生拼接乱码。

**复现**：`artifacts/d23-separate.py`、`artifacts/d23-probe-api2.py`、`artifacts/d23-sepformer.py`。

### 6.4 ❌→✅ 关于「删掉声纹换人切分」：建议已撤回

**曾一度建议删除**，理由是「合成素材上切分恒为 0 段」。
**该建议已撤回**——用**真实双人播客**实测后结论反转：换人切分**确实有效**。

| 项 | 实测 |
| --- | --- |
| 换人切分 | ✅ 15.21 s 的段切成 3 片，识别文本各自完整，声纹标签 `spk-0001 / spk-0002 / spk-0002`；另一段 12.94 s → 3 片，标签 `0001 / 0002 / 0001`（一来一回） |
| 曾判断「恒为 0 段」的原因 | 当时只有**自拼接的合成音频**——声纹不自然，不代表真人对话 |
| 头尾预判 | ❌ 有害：36 个长段里 **11 段（38%）的真换人被预判挡掉**，且预判为 False 的段 pyannote 只要 33~233 ms——**没省到钱** |
| 每句真实成本 | 预判 33~50 ms + pyannote **300~900 ms（13 s 段）** + 整句嵌入 50~100 ms |

**据此已实施三项算法修复**（D25/D26/D27，见《未决问题与已修复》）：删预判、边界变更点夹紧、最小切分时长 4.5 → 3 s。
**效果**：同一素材成功切分从约 **13 段 → 29 段**。后续代码审计发现，生产集成仍把这项切分错误地绑定到“显示说话人标签”开关，默认关闭时根本不执行；这是 D29 的待修实现缺陷，不改变这里“切分算法有效”的实验结论。

**素材**：B 站 `BV1rq4CeDE1h`《English Pod》P1（两位主持人交替对话），已转 16 kHz 存于 `artifacts/probe/podcast-p1-*.wav`；
抓取脚本 `artifacts/fetch-bili-full.py`；实测脚本 `artifacts/test-podcast-*.ps1`、`artifacts/measure-speaker-*.ps1`。

## 7. 流式识别：评估结论 **❌ 不做**（D24 已否决）

`[批式固有]` 的两条（§3）**理论上只有流式能解**；评估下来判定**代价超过收益**，决定不做。

### 7.1 它确实能解决什么

| 对比项 | 现在（批式） | 流式 |
| --- | --- | --- |
| 触发点 | 静音 600 ms 或硬切 12 秒 | **引擎自己判断句子结束** |
| 连说型的人 | 每 12 秒一条大块字幕 | 边说边出 |
| 600 ms 等待 | 固定存在 | 不需要等静音 |

### 7.2 先纠正两个常见误解（本次核查）

这两句很自然，但都不成立。**决策不能立在它们上面**——否则将来任何人拿一句话就能把它推翻。

| 误解 | 核查结果 |
| --- | --- |
| 「流式识别**只能走云端**」 | ❌ **本地就够得着**。本机已装的 `org.k2fsa.sherpa.onnx 1.13.8` 中，`sherpa-onnx.dll` 与 `sherpa-onnx-c-api.dll` **同时导出 `OnlineRecognizer` / `OnlineStream` / `KeywordSpotter` / `OnlinePunctuation`**（二进制核对，2026-09）；官方另有 .NET 麦克风流式识别示例。模型侧也有现成件：日语 **ReazonSpeech v2.1** 流式模型、中英双语 streaming zipformer。 |
| 「本地流式**要换技术栈**」 | ❌ **不用换**。用 sherpa-onnx 自家流式，**C# + onnxruntime + 打包方式一行都不用改**。只有「更强的本地流式模型」（Python/PyTorch 生态）才要换技术栈。 |

> **核查边界（如实记录）**：本次 `huggingface.co` / `raw.githubusercontent.com` / `k2-fsa.github.io` 均被 DNS 阻断，**「有没有中英日韩四语合一的流式模型」未能最终核实**；下文一律按「**未发现**」表述，**不等于「已证明不存在」**。

### 7.3 真正的理由（这些才站得住）

| # | 限制 | 说明 |
| ---: | --- | --- |
| **1** | **多语种矩阵（决定性）** | 场景是「他人语音、**语种不确定**」，中文/日语/英语随时切。批式的 SenseVoice **一个模型管四语**；流式模型**一模型一语种或双语**（未发现四语合一的），而**流式不会在音频里告诉你「这里换语言了」**。业界把这问题分成两条路线：**cascade**（先判语种再路由到各自模型）与 **unified multilingual**（一个模型内部判语种）——**只有 unified 能消除路由与切换开销**，那正是本地流式给不了的。（补充：**「判语种」这步不是障碍**——本机 sherpa-onnx 1.13.8 已带 `SpokenLanguageIdentification`；障碍是**切换本身**：流式一模型一语种，切点与准确率都不可控。） |
| **2** | **准确率先退一步** | 流式模型为低延迟把规模与上下文压小，**普遍不如 228 MB 的批式 SenseVoice**（CER 4.9~10%）⇒ 换来「字幕快」先丢「字幕准」，而主诉恰恰在「准」这一侧 |
| 3 | 切碎句子**反而伤翻译质量** | 现在整段（最长 12 s、上下文完整）交给翻译服务；流式切成短句后**上下文变少**，翻译质量下降——**这恰恰是「想要更好翻译质量」的人最不该走的路** |
| 4 | 说话人标签要重做 | CAM++ 现按「整段」算嵌入，流式要改成按时间轴，§6.4 刚修好的换人切分要重做一遍 |
| 5 | 无二次修订 | 批式可对整段重识别/调参；流式出字即最终结果 |

### 7.4 成本账：识别上云 ≈ 翻译的 13~143 倍

云流式**按音频时长计费**（公开价目卡，2026-08）：

| 服务 | 单价 | 折算 | 每天 2 小时（60 h/月） |
| --- | --- | ---: | ---: |
| Telnyx / Soniox（自有 GPU） | $0.0015/min | ≈0.64 元/h | ≈38 元/月 |
| Deepgram Nova-2 | $0.0043/min | ≈1.8 元/h | ≈110 元/月 |
| Deepgram Flux（对话流式） | $0.0074/min | ≈3.2 元/h | ≈190 元/月 |
| AssemblyAI | $0.012/min | ≈5.2 元/h | ≈310 元/月 |
| Azure 实时 | $1.00/音频小时 | ≈7.2 元/h | ≈430 元/月 |
| **现在：翻译（用户自带 key）** | — | **0.05 元/h** | **≈3 元/月** |

**结论**：识别上云的典型成本是 **≈110 元/月**，是现在翻译费（≈3 元/月）的 **13~143 倍**。
⇒ 成本**不会消失，只会转移**：开发者侧是**模型矩阵与长期维护**（本地流式），用户侧是**按小时计费的钱**（云端）——两边都不小。

### 7.5 若将来重启：三条前置条件（缺一条都不能做）

| # | 前置条件 | 为什么 |
| ---: | --- | --- |
| 1 | **隐私与明示同意** | 翻译的是 **VRChat 里别人的语音**；上云 = 把第三方声音上传。必须有明示说明 + **默认关闭**的开关。**这是本地路径没有的新增成本，比钱更硬。** |
| 2 | **计费硬上限与可见计量** | 按音频时长计费，麦克风常开就是钱包常漏；必须有硬上限与实时用量显示 |
| 3 | **核实国内可选性** | 能解「多语混说」的是 Deepgram/Flux 一类境外统一多语模型；国内网络与支付下现实可选的是腾讯云/阿里云/讯飞，而它们**按引擎分语种**（中英混说一个引擎，日/韩各自引擎）⇒ **§7.3 第 1 条会在云端国内选项里再出现一次**。（按既有印象，**未经本次核实**，重启前必须先查） |

### 7.6 决策

> **不做流式改造。** 理由：**代价超过收益**——要押上多语种能力、准确率、翻译上下文、说话人标签，外加一整套新缺陷面（隐私、计费、网络），去换一个延迟指标。**是「不划算」，不是「做不到」。**
>
> 批式的两条边界——**字幕粒度以「段」为单位**（§3）与**说完要等静音 600 ms**（§4）——**暂不对外声明、不写进产品说明**；本地识别侧还有未验证的提升路径（§9），验证完之前不把它当结论。

（D24 状态：**已否决**，非「暂缓」。）

## 9. 本地识别仍有提升空间：能力清点与**未验证**路径

> 本节是对 §7 / §8 的**修正**。先前把「字幕以段为单位」「等静音 600 ms」当成已到边界、把「换流式」当成唯一出路——**下得太满**。本节列的是模型实验，不代替必须先完成的 D28/D29 代码修复。
> 事实是：本机这套依赖里**还有没用上的能力**，而且有 **4 条路径从未验证**。

### 9.1 能力清点（本机 sherpa-onnx 1.13.8 原生库导出接口，二进制核对）

| 能力 | 原生接口 | 项目现状 |
| --- | --- | --- |
| 流式识别 | `SherpaOnnxCreateOnlineRecognizer` | ❌ 未用（§7 已否决） |
| 流式 VAD | `SherpaOnnxCreateVoiceActivityDetector` | ✅ **已在用**（Silero）——`SileroVadSegmenter` 直接用它，**本身就是逐 32 ms 帧的实时 VAD**；且 **VAD 模型可换**：1.13.8 同时支持 **TEN-VAD**（`--ten-vad-*` 与 `--silero-vad-*` 字段一一对应：threshold / min-speech / min-silence / max-speech） |
| 流式降噪 | `SherpaOnnxCreateOnlineSpeechDenoiser`（GTCRN / DPDFNet） | ❌ **未用** |
| 离线降噪 | `SherpaOnnxCreateOfflineSpeechDenoiser` | ❌ 未用 |
| 语种识别 | `SherpaOnnxCreateSpokenLanguageIdentification` | ❌ 未用 |
| 声源分离 | `SherpaOnnxCreateOfflineSourceSeparation` | ❌ 未用；**1.13.8 只支持 Spleeter / UVR**（字段名只有 `vocals` / `accompaniment` / `2stems`）⇒ 是**伴奏分离，拆不开两个人声** |
| 说话人分离 | `SherpaOnnxCreateOfflineSpeakerDiarization` | ✅ 在用（pyannote 分割 + CAM++ 嵌入） |
| 说话人嵌入 | `SherpaOnnxCreateSpeakerEmbeddingExtractor` | ✅ 在用（CAM++） |
| 识别模型家族 | SenseVoice / **Dolphin** / **FireRedASR** / **Canary** / Moonshine / NeMo / Whisper / Paraformer / Zipformer / TDNN | 只用了 **SenseVoiceSmall INT8** |

### 9.2 四条未验证路径（**都还没测，不要当结论**）

| # | 路径 | 为什么可能有提升 | 先要什么数据 | 风险 |
| ---: | --- | --- | --- | --- |
| 1 | **换 / 加识别模型**（Dolphin 多语、FireRedASR 中英） | 现在只用一个 228 MB 的 small 模型；同框架内还支持多个更强的家族，其中 **Dolphin 是多语种模型** | 同一批真实语音上的 **CER / 耗时 / 体积** | 大模型 CPU 太慢会顶掉实时性；CTC 模型不给标点 |
| 2 | **实时降噪前端**（GTCRN / DPDFNet） | VRChat 远端语音音量小、有压缩与噪声，识别在小音量上明显变差 | 小音量 / 噪声素材上开、关降噪的 **CER 差** | 降噪伪影可能反而伤识别 |
| 3 | **收尾判定**（两条子路：**换 VAD 模型** Silero → TEN-VAD；**按说话人自适应阈值**） | 600 ms 是**全局固定**值，而实测三人停顿分布完全不同（A 句内 600~900、B 句内 150、C 300~500）⇒ 用一个人的尺子量所有人。若新 VAD 在 VRChat 压缩音频上判得更准，**整条取舍曲线可能左移**（600 ms 就能往下调） | 同一素材上 Silero vs TEN-VAD 的误切/漏切对比；按说话人分组的停顿统计 + 回溯模拟 | 判错人 ⇒ 切碎或并句（正是 §4 的 ⛔）；换 VAD 需重新标定四个旋钮 |
| 4 | **人声—人声分离** | 只在**重叠**时才有用；1.13.8 做不到，但那是**版本边界** | ① 新版 sherpa-onnx 有没有人声分离模型；② **真实素材里重叠占几 %** | 双路识别（耗时 ×2）+ 分离模型体积与延迟；重叠占比低就不划算 |

### 9.3 结论

**先验证、再定边界。** 在 §9.2 给出数据之前：**不再声称「识别侧已到边界」，也不把边界写进产品说明**（用户决定）。
