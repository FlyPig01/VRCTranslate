# 他人语音采集自动切换方案（修订版）

修订日期：2026-09-15

## 本轮结论

原方案的产品目标成立：运行 VRChat 时优先只采集 VRChat 的音频，未运行时保留系统回环，便于测试和兼容旧系统。

原方案不能直接实施，原因有四项：

1. Windows 进程回环的官方最低系统版本是 **Windows 10 Build 20348**，不是 2004（Build 19041）。项目当前仍以 19041 为最低版本，必须运行时检测并保留系统回环降级。
2. 进程切换放在 `SubtitleSpeechSession` 并重建整个识别会话，会把两个来源拼进同一个语音段，也可能让停止时的旧识别结果晚于新来源输出。
3. 当前 `IAudioCapture` 只有样本事件，没有来源、故障和停止状态；激活失败或设备断开无法被上层正确处理。
4. PowerShell 播放器不能稳定证明“只捕获目标进程”，原集成测试不足以作为验收依据。

本轮只修改本方案文档，暂不修改生产代码。待本方案审核通过后，再按分阶段计划实施。

方案依据：Microsoft Windows Classic Samples 的 [Application loopback audio capture](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)。实现前应再次核对目标 SDK、系统 Build 和当前 NAudio 版本的 API 定义。

## 目标行为

| 场景 | 采集源 | 用户看到的状态 | 预期结果 |
| --- | --- | --- | --- |
| 检测到可用的 VRChat 进程回环 | VRChat 进程树 | `VRChat 音频` | 只把 VRChat 及子进程的渲染音频送入识别 |
| 未检测到 VRChat | 系统回环 | `系统声音` | 可用播放器或任意系统声音测试 |
| 系统不支持进程回环，或激活失败 | 系统回环 | `系统声音（兼容模式）` | 识别保持可用；只在失败时给一次短提示 |
| VRChat 启动、退出或重启 | 自适应切换 | 状态徽标更新 | 不把两个来源拼成一句字幕，不产生旧来源的迟到结果 |
| VRChat 进程存在但没有渲染流 | 进程回环 | `VRChat 音频` | 保持静音；不能因为静音而退回系统回环 |

用户不配置进程名、PID、音频源或白名单。目标固定为 VRChat，所有切换在后台完成。

进程回环只按“哪个进程输出了声音”做隔离，不会把 VRChat 的 BGM、世界音效或界面音效自动区分成人声。现有 VAD、切句和识别链仍然必须保留；本方案解决的是浏览器、音乐等非 VRChat 进程的混入。

## 分层设计

### Application：稳定的音频边界

在 `VrcTranslate.Application.Abstractions` 增加与平台无关的契约：

- `AudioCaptureSourceKind`：`SystemLoopback`、`ProcessLoopback`、`SystemLoopbackFallback`。
- `ProcessIdentity`：PID 与进程启动时间组成的身份，避免 PID 被系统复用后误切换。
- `AudioSourceState`：来源类型、当前进程身份、是否兼容模式、最近一次故障码。
- `AudioSourceChangedEventArgs`、`AudioCaptureFaultedEventArgs`。
- `IAudioCapture` 增加 `SourceKind`、`SourceChanged`、`Faulted`、`Stopped` 事件；事件只传递应用层数据，不暴露 NAudio、COM 或 Win32 类型。
- `IAudioCaptureFactory` 改为接收 `AudioCaptureRequest`（来源类型、可选 `ProcessIdentity`、麦克风设备 ID），不把 PID 塞进现有的 `deviceId` 字符串。
- `IProcessTargetResolver`：只负责返回当前 VRChat 的稳定进程身份，不依赖 `WorkspaceSettings`。VRChat 是产品固定目标，界面不提供进程配置。

新增 `AdaptiveLoopbackAudioCapture`（应用层协调器，实现 `IAudioCapture`）。它对上层表现为一个连续的采集流，内部管理系统回环、进程回环、切换顺序和来源状态。`LocalSpeechCaptureSession`、SenseVoice、翻译和 OSC 链路继续使用同一个接口，不需要知道采集来自哪个平台实现。

### Infrastructure：Windows 实现

#### VRChat 进程监视器

新增 `VrchatProcessResolver` / `VrchatProcessWatcher`：

- 内部使用规范化名称 `VRChat`（`GetProcessesByName` 不带 `.exe`），不读取或写入用户设置。
- 启动监视后立即扫描，随后每 3 秒扫描一次；候选变化先做短暂复核，避免启动器或快速重启造成抖动。
- 选择策略：先限制在当前交互用户的 SessionId，并优先选择前台 VRChat 窗口对应的实例；没有可用前台信息时，当前身份仍存活则保持当前身份，当前身份退出后从可读取启动时间的候选中选择最早启动者；无法读取启动时间时用 PID 作为稳定的次级排序。该策略必须在单测中固定，不能依赖机器上的偶然进程顺序。
- 每次使用 `Process` 后立即释放；捕获无权限、进程退出和 `StartTime` 读取竞态。
- 身份比较同时使用 PID 与启动时间，PID 重用必须视为新目标。
- 支持取消和异步释放，应用关闭后不留轮询任务。

#### 进程回环采集器

使用 Windows 官方 Application Loopback 接口：

`ActivateAudioInterfaceAsync` → `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK` → `AUDIOCLIENT_ACTIVATION_PARAMS` → `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` → `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` → 目标 PID。

实现边界如下：

- 官方进程回环要求 Windows 10 Build 20348 或更高版本。项目仍编译为 `net10.0-windows10.0.19041.0`，运行时必须通过能力检测决定是否启用；19041 至 20347 只使用系统回环。
- NAudio 新版本包含部分低层激活声明，但没有可直接替换 `IWaveIn` 的完整进程回环采集器。优先复用 NAudio 已有的 COM/WASAPI 类型和微软样例的激活流程，只补项目所需的最小互操作层，避免重复声明整套 `IAudioClient`。
- `ProcessLoopbackAudioCapture` 直接实现项目的 `IAudioCapture`，不向 Application 泄露 `IWaveIn`。事件驱动地排空 `IAudioCaptureClient`，处理 48 kHz 浮点/WAVEFORMATEXTENSIBLE、静音标志、数据不连续、设备失效和异步停止。
- 样本继续复用 `AudioSampleConverter` 转为单声道 16 kHz；不写临时 WAV 文件。
- 激活同时检查 `ActivateAudioInterfaceAsync` 的立即返回值和异步 `GetActivateResult`；完成回调对象必须保持存活并满足跨线程调用要求，不能在 UI STA 上同步等待。`PROPVARIANT`、x64 结构体对齐和 COM 释放集中封装。
- 采集循环在同一线程成对执行 `GetBuffer`、复制和 `ReleaseBuffer`，处理 `BUFFER_EMPTY`、`SILENT`、`DATA_DISCONTINUITY`、`DEVICE_INVALIDATED`、`RESOURCES_INVALIDATED` 和 `SERVICE_NOT_RUNNING`；`RecordingStopped` 只发布一次。
- 激活、COM apartment、回调线程和释放顺序都必须可取消且可重复。任何 HRESULT 进入 `Faulted`，不得在 NAudio 回调线程直接更新 UI。

现有 `WindowsAudioCapture` 保留为麦克风和系统回环实现，并在相同的应用层接口下补齐故障/停止事件。

## 自适应切换状态机

`AdaptiveLoopbackAudioCapture` 的状态只有以下几类：

`Stopped` → `SystemLoopback` → `ProcessLoopback` → `SystemLoopback`；进程激活失败时进入 `SystemLoopbackFallback`，不是错误终止。

切换流程：

1. 监视器产生新的 `ProcessIdentity` 或 `null`，协调器为该决策分配递增的 generation，并取消上一代的候选启动任务。
2. 在后台创建并启动候选采集器；候选未成功启动前，当前正常采集器继续工作。
3. 候选成功后，先暂停向识别管线派发样本，发布来源边界事件，再停止并释放旧采集器，原子替换当前采集器，最后恢复派发。
4. 来源边界事件通知 `LocalSpeechCaptureSession`：取消旧 generation 的未完成识别任务，丢弃 segmenter 中尚未闭合的样本并重置 VAD/能量门限。切换前的半句话不发送，避免系统声音和 VRChat 声音拼句。
5. 所有识别、翻译和 OSC 输出在提交结果前检查 generation；旧任务即使晚返回，也不能更新字幕、预览或 OSC。切换和 Stop 共用同一个取消令牌，并在释放前等待旧任务结束。
6. 候选启动失败时保留当前采集器；若当前来源已不可用，则切换到系统回环并标记兼容模式。
7. 同一进程身份的失败采用退避（例如 5 秒、15 秒、30 秒后封顶），PID 变化、设备变化或应用重新启动时清除退避。旧决策的异步结果不得覆盖新 PID 决策。
8. 目标进程没有音频渲染流时，进程回环正常返回静音；静音不是激活失败，不触发系统回环降级。

停止和释放必须与切换串行化：应用退出、页面切换、设备断开和进程变化不能同时操作同一个 capture 实例。

## 会话与界面接线

- `SubtitleSpeechSession` 请求 `AdaptiveLoopbackAudioCapture`，不再固定请求 `SystemLoopback`。
- `VoiceSessionHost` 继续负责应用生命周期；页面只订阅运行状态、音量和短来源标签，不持有 watcher、PID 或切换线程。
- `LocalSpeechCaptureSession` 增加“来源边界重置”入口，识别模型、语言和翻译路由不改。
- 语音页只显示一个紧凑状态徽标：`VRChat 音频`、`系统声音` 或 `系统声音（兼容模式）`。切换不弹 InfoBar、不堆叠说明文字；仅首次激活失败时显示一次短提示，恢复后自动消失。
- 不增加进程选择、音频源下拉、目标语言或模型配置。现有用户界面保持面向普通用户的简洁结构。

## 系统兼容与失败策略

| 情况 | 处理 | 是否重试 |
| --- | --- | --- |
| Windows Build < 20348 | 直接使用系统回环 | 不尝试进程激活 |
| 进程回环 HRESULT 激活失败 | 保留当前采集；无可用来源时使用系统回环并标记兼容模式 | 按当前进程身份退避 |
| VRChat 退出 | 切回系统回环 | 下一次检测到 VRChat 时重试 |
| 音频设备失效 | 先重建同一来源，失败后使用系统回环 | 受退避限制 |
| 进程无渲染流 | 保持进程回环静音 | 不因静音降级 |
| 应用停止/Dispose | 取消 watcher、停止采集、释放 COM 和回调 | 不重试 |

“不中断识别”改为可验证的表述：识别会话对象保持运行，但来源切换允许有短暂空窗；切换边界上的未完成语音段会被丢弃，以保证字幕内容正确。

## 自动测试与验收

### Application 单元测试

- 进程名规范化、首次立即扫描、轮询去重、取消和释放。
- 多实例选择、`StartTime` 无权限、进程退出竞态、PID 重用（PID 相同但启动时间不同）。
- 无目标、目标出现、目标退出、目标重启和快速抖动的决策表。
- 不支持系统、激活失败、设备失效、退避与重试上限。
- 候选采集启动失败时旧采集仍保持；新 generation 不能被旧异步结果覆盖。
- 来源切换会重置 segmenter；旧语音段、识别、翻译和 OSC 结果均不会泄漏到新来源。
- Stop、Dispose、切换并发时只释放一次，不残留任务、事件订阅或线程。

### Windows 集成测试

不使用临时 PowerShell 播放器。新增受控的 Windows 音频测试 helper：两个独立进程分别通过 WASAPI/WaveOut 输出不同频率的持续音（例如 440 Hz 与 880 Hz），测试捕获结果的能量/频率相关性：

1. 目标进程回环能检测到目标频率。
2. 非目标进程频率不进入目标回环结果。
3. 目标进程无渲染流时结果为静音且不自动切到系统回环。
4. 目标结束后系统回环仍能捕获已知测试音。

测试仅在 Windows Build ≥20348 且存在活动播放端点时运行，否则明确标记为 Skip；不把 CI 静音当成失败。另保留不依赖硬件的协调器和状态机单测。

### 人工验收

- 未启动 VRChat 时播放音频，状态为 `系统声音`，能正常得到字幕。
- 音频测试素材（用户指定）：<https://www.bilibili.com/video/BV1dEY76fEn2/>，用于「未启动 VRChat」与「启动 VRChat + 浏览器音乐」两类场景。
- 启动 VRChat，同时播放浏览器音乐，状态切为 `VRChat 音频`，浏览器声音不产生字幕。
- VRChat 退出、重启、多个实例并存时，来源和字幕内容正确。
- 在不支持进程回环的系统上，软件仍能使用系统声音，不崩溃。
- 关闭主程序后 watcher、采集器、COM 回调和悬浮窗全部退出。

验收指标统一为：目标进程状态变化的发现延迟不超过 3 秒；候选采集成功后切换完成不超过 1 秒；切换不得产生跨来源字幕或旧结果。

## 实施决策记录

Phase 1 已实施（提交 `37b28ed`：应用层采集契约、VRChat 实例决策纯函数、自适应协调器状态机与全套 fake 单测，218 项测试全绿，对用户零行为变化）。实施中出现三处方案未覆盖、或需要修正的地方，作为 Phase 2 及以后的约束固定下来。

### 决策 1：`AudioCaptureSourceKind` 增加 `Microphone`（已实施）

方案只列出三个回环成员（`SystemLoopback` / `ProcessLoopback` / `SystemLoopbackFallback`），但 `IAudioCapture.SourceKind` 对自身语音的麦克风采集也必须返回有意义的值，否则只能说成 `SystemLoopback`，上层再也分不清「系统混音」和「我的麦克风」。因此增加 `Microphone` 成员：三个回环成员语义不变，只增不减。

Phase 2 接线时必须让自身语音会话报告 `Microphone`，不得复用回环来源值。

### 决策 2：来源切换分「换流」与「换标签」，只有换流才丢半句（已实施）

方案要求「切换时丢弃未闭合语音段」。但 `系统声音` → `系统声音（兼容模式）` 只是标签变化，底层仍是同一条系统混音流；若也丢半句，用户说到一半的话会无故消失。因此给 `AudioSourceChangedEventArgs` 增加 `IsBoundary`：

| 事件 | IsBoundary | 会话行为 |
| --- | --- | --- |
| 真正换了采集实例（系统 ↔ 进程 ↔ 兼容模式重建） | true | 取消旧 generation 识别、丢弃未闭合语音段、重置 segmenter |
| 仅来源类型或标签变化，底层同一条流 | false | 保留当前半句，只更新状态徽标 |

「不产生跨来源字幕」仍然成立：跨来源一定伴随换流。Phase 2 接监视器与协调器时必须显式区分这两种变化，不得一律按切换处理。

### 决策 3：Phase 3 必须改写「进程回环一律不支持」的测试（待办，本轮不动）

> **执行时机：Phase 3 实施时一并修改。Phase 1/2 都不得改动这条测试，也不得为了让脚本或构建通过而删掉它。**

Phase 1 的 Windows 工厂对 `ProcessLoopback` 请求抛 `ProcessLoopbackNotSupportedException`（绝不静默降级为系统回环），该行为被 `tests/VrcTranslate.Infrastructure.Tests/AudioSampleConverterTests.cs` 中一条测试固定。Phase 3 实现官方进程回环后必须同步处理，否则这条测试会挡住正确实现：

- Build ≥ 20348 且能力检测通过 → 走进程回环，测试改为断言「能创建进程回环采集器」；
- Build < 20348 → 保持抛不支持，保留现有断言；
- 建议按 Build 条件分支，而不是删除测试。

Phase 3 还需补齐：能力检测入口、激活失败路径、48 kHz 浮点/WAVEFORMATEXTENSIBLE 格式处理、静默/断流/设备失效处理，以及方案「Windows 集成测试」一节要求的双进程测试音集成测试。本机为 Windows 11 Build 26200，满足 ≥20348，可真机实测，不必标记 Skip；低于 20348 的回退路径只能靠单测覆盖。

## 实施发现（Phase 3 实测）

Phase 3 在本机（Windows 11 Build 26200）真跑双进程测试音集成测试后，有三处只有真机才会暴露的行为。它们不是可选项，而是后续维护进程回环代码时必须知道的事实。

### 发现 1：虚拟客户端不提供格式与周期信息（E_NOTIMPL）

- **现象**：激活本身成功，随后立刻失败。`IAudioClient::GetMixFormat`、`GetDevicePeriod`、`GetStreamLatency` 返回 `E_NOTIMPL(0x80004001)`，经 NAudio 包装表现为 `NotImplementedException`，堆栈看起来像调用方漏了空的程序缺陷。
- **原因**：进程回环流由虚拟客户端（`VAD\Process_Loopback`）提供，它不绑定任何物理设备，因此不实现只对设备有意义的成员。这是该设备的**正常行为**，不是激活失败。
- **处理**：不向虚拟客户端要格式。改用当前默认播放端点的混音格式（实测为 48 kHz / 32-bit float / 2ch，`WAVEFORMATEXTENSIBLE`）传给 `Initialize`；实测该客户端接受多种候选格式，因此 Phase 4 进一步把它做成候选列表的第一项（见下文措施 3）。原始格式原样交给 `Initialize`，只有样本转换器看到归一化后的类型（真实类型在 `WAVEFORMATEXTENSIBLE` 的子格式里）。
- **影响**：报错信息有误导性（看起来像程序缺陷，实为该设备正常行为），官方文档未记载，只有真跑才会暴露。任何"向 `IAudioClient` 询问设备信息"的后续代码都要先假设这一步会返回 `E_NOTIMPL`。

### 发现 2：AUDCLNT_S_BUFFER_EMPTY 是成功码，空包不得 ReleaseBuffer

- **现象**：若把 `0x08890001` 当错误处理，或对空包调用一次 `ReleaseBuffer`，采集会在若干秒后**静默卡死**：不报错、没有声音、也不会自行恢复。查询包大小的调用与 `GetBuffer` 之间存在竞态，因此空包一定会出现。
- **原因**：`AUDCLNT_S_BUFFER_EMPTY(0x08890001)` 属于**成功码**（`S_` 前缀），语义是"此刻没有可读数据"；这种包不携带缓冲区，帧数为 0。对它调用 `ReleaseBuffer` 会让引擎的缓冲计数错乱，最终耗尽缓冲区。
- **处理**：采集循环用"已公告帧数 > 0"和"本包帧数 > 0"双重判断；帧数为 0 的包直接跳过，**不**释放。现有单测 `Empty_packets_are_skipped_without_a_release` 固定该规则。
- **影响**：这类故障没有任何用户可见症状，只能靠结构性规则避免。任何重写采集循环的改动都必须保留"空包不释放"。

### 发现 3：担心的 E_ILLEGAL_METHOD_CALL(0x8001010E) 没有出现

- **现象**：方案预判完成回调会因跨公寓调用失败（`0x8001010E`），实测在全路径上从未出现。
- **原因**：完成回调对象创建在采集自己的专用 MTA 线程，Windows 从同一 apartment 的工作线程回调，因此不需要 free-threaded marshaler，也不需要代理/桩。
- **处理**：主路径按 MTA 实现（`ComApartment` + 专用采集线程），不引入 marshaler；同时按"跨机器不一定总是这样"的假设保留兜底：公寓不被允许时换一个公寓重试一次（见下文措施 2）。
- **影响**：这条预判从"主路径阻塞项"降级为"兜底路径"，但它不是可以删除的假设——别人的机器上 COM 单元状态可能不同。

## COM 健壮性措施（跨机器）

本机 Build 26200 上一次通过，**不代表其他机器不会失败**：别人的显卡驱动、音频驱动、系统版本、外设和 COM 单元状态都不同。分发版本的验收标准因此不是"本机能跑"，而是：

> **任何 COM 异常都不影响可用性，并且能诊断**——进程回环失败时系统回环继续出字幕、界面能看出当前来源、进程不崩、失败原因留下可反馈的技术细节。

下面逐条固定实现与验证方式。这些措施只在进程回环路径上生效，自身语音（麦克风）与系统回环不受影响。

| # | 措施 | 触发条件 | 结果 | 单测 |
| --- | --- | --- | --- | --- |
| 1 | 激活超时 | 异步激活 5 秒内没有回调 | `Faulted`，FaultCode = `ActivationTimeout`，协调器降级到系统回环并按退避重试 | `An_activation_that_never_completes_times_out_instead_of_waiting_forever`、`A_timed_out_activation_is_a_fault_with_the_timeout_code` |
| 2 | 公寓模型重试一次 | 环境类 HRESULT（见下） | 换一个公寓重试**一次**；再失败即视为本机不支持 | `An_apartment_failure_is_retried_exactly_once_in_the_other_apartment`、`A_second_apartment_failure_is_permanent_and_never_retried_again` |
| 3 | 格式候选回退 | `Initialize` 拒绝当前候选 | 按候选列表继续；全部失败才 Faulted，并记录每个候选的 HRESULT | `The_format_ladder_moves_on_until_the_client_accepts_one`、`A_client_that_refuses_every_format_reports_the_whole_ladder` |
| 4 | 一次性熔断 | 不可重试类 HRESULT，或公寓重试用尽 | 本会话内进程回环永久不支持，不再尝试；系统回环保持可用 | `A_permanent_hresult_is_unsupported_without_any_apartment_retry`、`A_permanent_failure_trips_the_factory_fuse_so_the_next_start_touches_no_com` |
| 5 | 诊断日志 | 每次激活尝试 | 写入 `data\capture-diagnostics.log`（≤200 行、覆盖式、无音频/个人信息） | `ProcessLoopbackDiagnosticsTests` 全类 |

### 措施 1：激活超时（默认 5 秒，可注入）

激活改为"有界等待"：`ProcessLoopbackActivationOptions.ActivationTimeout`（默认 5 秒）与 `ActivationPollInterval`（默认 50 ms）由注入的选项提供，等待循环每一片都检查取消与超时。超时抛 `ProcessLoopbackActivationTimeoutException`，`Faulted` 事件的 `FaultCode` 固定为 `ActivationTimeout`。

超时**不**等于"本机不支持"：机器可能只是忙，因此它按可重试故障处理，由协调器退避重试，并且永远不会无限等待。注入超时值是单测能在一秒内跑完这条路径的原因。

### 措施 2：公寓模型重试一次

优先 MTA（Windows 官方样例的模型）。若激活过程返回下面这类"环境不允许"错误：

- `E_ILLEGAL_METHOD_CALL` / `RPC_E_WRONG_THREAD(0x8001010E)`
- 整个 `RPC_E_*` 区间（`0x80010100`–`0x800101FF`）
- `CO_E_NOTINITIALIZED(0x800401F0)`
- `E_ACCESSDENIED(0x80070005)`

则在**新建线程**上换另一个公寓（MTA ↔ STA）重试**一次**：公寓是线程的属性，无法在原线程上切换。STA 路径用 `CoWaitForMultipleHandles`（分发 COM 调用与窗口消息）等待回调，因为 STA 的回调经消息队列投递，直接阻塞会永远等不到。

重试再失败即视为本机不支持：不再有第三次尝试。`E_ACCESSDENIED` 同时属于"环境"与"不可重试"两类，规则是**先给它一次公寓重试，若再次出现则熔断**。

这条路径在本机无法真机触发（MTA 一次通过），因此由注入的公寓宿主（`IProcessLoopbackApartmentHost`）与脚本化会话工厂单测固定；真机未验证的部分见文末说明。

### 措施 3：格式候选回退

`Initialize` 被拒时按候选列表依次尝试，默认顺序为：

1. 当前默认播放端点的混音格式（读不到时跳过并记录原因）；
2. IEEE float 48 kHz / 32-bit / 2ch；
3. PCM 16-bit 48 kHz / 2ch；
4. PCM 16-bit 44.1 kHz / 2ch；
5. PCM 16-bit 16 kHz / 1ch。

每个候选的 HRESULT 都记进诊断日志；被接受的那个格式既用于 `Initialize`，也用于样本转换（不再假设等于端点混音格式）。全部失败才 Faulted；此时上报的 HRESULT 由"最可诊断"的候选决定——只要有一个候选返回不可重试类 HRESULT，就上报它，让熔断生效，而不是每 30 秒重走一遍注定失败的阶梯。不可转换的候选直接跳过并注明原因。

### 措施 4：一次性熔断（可注入、可单测）

`IProcessLoopbackCircuitBreaker`（默认实现 `ProcessLoopbackCircuitBreaker`）记录"本会话已确认本机进程回环不可用"这一状态，由 `WindowsAudioCaptureFactory` 持有，工厂与采集共享同一个实例：

- 采集侧在遇到不可重试类 HRESULT（`E_NOTIMPL`、`CLASS_NOT_REGISTERED`、`E_ACCESSDENIED`、`E_NOINTERFACE`、`ERROR_NOT_SUPPORTED`、`ERROR_OLD_WIN_VERSION`）或公寓重试用尽时，把失败转成 `ProcessLoopbackNotSupportedException` 并打开熔断；
- 协调器收到该异常后立即把来源标为 `系统声音（兼容模式）` 并**不再尝试**（Phase 2 已有行为，未改动）；
- 工厂在熔断打开后直接拒绝进程回环请求，**连 COM 都不碰**，因此下一次开始识别不会再有 5 秒超时或每 3 秒一次的打扰；
- 系统回环与麦克风路径完全不受影响。

熔断状态通过构造注入，所以"打开后不再尝试"可以在单测里直接断言。

### 措施 5：诊断日志

每次激活尝试（成功或失败）向便携目录写一条记录到 `data\capture-diagnostics.log`：时间戳、公寓、**Build 号**、**默认端点格式**（读不到时写原因）、**激活立即返回值**、**`GetActivateResult` 返回值**、每个候选格式及其 HRESULT、最终采用的格式、**最终 FaultCode** 与一句失败说明。

- **限长覆盖式**：文件最多 `FileProcessLoopbackDiagnostics.MaxLines`（200）行，超出时从顶部丢弃最旧的块，长期运行不会无限增长；
- **不含音频/个人信息**：只有版本号、格式描述与 HRESULT，没有样本、文本、进程名或 PID；
- **失败静默**：目录只读、文件被占用或路径不可用时只丢失日志，绝不影响采集（有单测固定）；
- 目的是界面只显示结论（来源徽标 + 一次提示），技术细节靠这个文件反馈问题。

### 措施 6：绝不崩进程

- 采集线程的顶层 `Pump` 有兜底 `try/catch`：任何逃逸异常都会变成 `Faulted` 事件与启动失败，而不是后台线程上的未处理异常（那会直接结束进程）；
- 每次尝试自带 `try/catch/finally`，会话、事件句柄与 COM 单元在任何路径上都会被释放；
- 事件回调（`SamplesReady`/`SourceChanged`/`Faulted`）全部包在 `try/catch` 里，订阅者抛异常不会拆掉采集；
- 不变量沿用现有约定：采集回调线程不触碰 UI，界面侧一律 `DispatcherQueue.TryEnqueue` 后再更新（Phase 4 的来源徽标就是这样接的）。

### 措施 7：不静默降级

降级到系统回环必须**在界面可见**：语音页状态卡内的来源徽标显示 `VRChat 音频` / `系统声音` / `系统声音（兼容模式）`（Phase 4 接线），并且只在一次降级的首次失败时给一次短提示（`无法只采集 VRChat 声音，已改用系统声音`），恢复后提示自动消失、后续重试失败不再重复提示。提示只由会话层的"一次性门闩"（`LocalSpeechCaptureSession.ConsumeFallbackNotice`）决定，页面重新进入也不会重复弹出。

### 本机无法真机覆盖的部分

- **MTA 被拒后的 STA 重试**：本机 MTA 一次通过，STA 分支的重试决策由单测固定，但"STA 里 `CoWaitForMultipleHandles` 能否真的收到回调"未在真机验证；若其他机器走到这条路径且仍失败，日志会记录第二次尝试的公寓与 HRESULT。
- **低于 Build 20348 的系统**：沿用现有门控（不尝试、不报错、不弹提示），仍只能靠单测与代码审查覆盖，见「兼容性要求」。
- **非默认端点格式的环境**：候选阶梯的接受情况取决于具体驱动，日志中的 `candidate[i]` 行就是为这种情况准备的。
