# 后续优化方向：接话与延迟

> **状态：调研 + 实测已做，方案未实施（等决策）**。
> 本文整理自 2026-09-16 的几轮讨论：**两人接话能不能修、600 ms 延迟能不能降**。
> 所有数字都是本机实测（脚本见 §6），不是估算。

## 0. 一页结论

| 问题 | 能不能修 | 结论 |
| --- | --- | --- |
| **① 一人说完、另一人紧接着说**（不重叠） | **能，但代码现在是坏的** | 已有声纹切分机制，实测**预判说「怀疑换人」、切分却返回 0 段**——功能实际未生效，不是参数紧 |
| **② 一人还没说完、另一人插话**（重叠） | **不能**（能力上限） | 叠加音轨在识别层就只剩一路（与 D14 同源）；现有**保一路**是正确取舍 |
| **③ 说完话到字幕出现 0.83~1.75 s** | **能，最多省 200~450 ms** | 三笔可省：识别/翻译重叠（130~450 ms）、文本回退早切（约 210 ms）、自适应静音窗 |
| 单纯把静音阈值 600 → 400 ms | **不做** | 说话人之间的停顿区间**互相重叠**（想词型的人句内停顿比连说型的人句间停顿还长），改任何固定值都会害到另一部分人 |

## 1. 延迟的构成（先看清钱花在哪）

```
对方说完话
   │
   ├─ VAD 等静音收尾 ─────── 600 ms   ← 最大的一块，也是唯一能大幅压的
   ├─ 本地识别 ─────────── 130~450 ms（CPU int8，压不动）
   ├─ 翻译 HTTP ────────── 100~700 ms（取决于引擎）
   └─ 推送 OSC/字幕 ─────── 约 1 ms
```

⇒ **端到端 0.83~1.75 s**，其中识别 + 翻译是**串行**的（见 §4.1，这是白捡的一笔）。

## 2. 场景①：快速接话（不重叠）

### 2.1 代码里本来有这个机制

`LocalSpeechCaptureSession.PlanSpeakerSpans()` 会在识别前把一段音频**按说话人变更切成多片、分别识别、各自贴标签**。
但它有三道门（`SpeakerIdentifierOptions`）：

| 门 | 条件 | 快速接话时 |
| --- | --- | --- |
| 门 1 | 用户开启了「说话人标签」 | 默认**关闭** → 整个机制不运行 |
| 门 2 | 段长 ≥ **4.5 s**（`MinimumSplitSeconds`） | 两人各说一句短的，整段 3~4 s → **不切** |
| 门 3 | 头尾各能取到 **2 s** 有声窗且不重叠（`ChangeWindowSeconds`） | 短段取不到 → **不切** |

> 门 3 的 2 秒**不是调参偏好**：随包 CAM++ 实测 1 秒窗同人相似度只有 0.45（与跨人区间重叠，无法区分），2 秒才拉开（同人 0.69 / 异人 0.09）。

### 2.2 实测：切分现在是坏的

拿「中文说完接日语」的素材（**确实是两个人**：`mix_zh_ja_seq`）截成不同长度：

| 段长 | 预判是否怀疑换人 | 切分耗时 | **返回段数** |
| ---: | --- | ---: | ---: |
| 13.4 s | **True**（怀疑） | 933 ms | **0** ⛔ |
| 10.0 s | **True** | 39 ms | **0** ⛔ |
| 8.0 s | **True** | 37 ms | **0** ⛔ |
| 6.0 s | False | 36 ms | 0 |
| 4.6 s | False | 36 ms | 0 |
| ≤4.4 s | False | 未执行 | 0 |

**两个反常识的点**：

1. **预判说「怀疑换人」，切分却返回 0 段** —— 说明 pyannote 分段模型在我们的素材上**从没成功切过**；
2. **10 s 只花 39 ms、13.4 s 却花 933 ms** —— 说明分段器内部有个长度门槛（超过才真跑），需要查清。

⚠️ **重要限制**：以上素材是**拼接的合成音**（同一说话人的录音 + 静音 + 另一段录音），声纹特征不自然，**可能正是切分失败的原因**。
**要下结论必须有真实两人对话录音**——这一点决定了后面的路怎么走。

### 2.3 场景①的后续（按顺序）

| 编号 | 事项 | 成本 | 决定什么 |
| --- | --- | ---: | --- |
| **D20** | 用**真实两人对话录音**复测切分；同时查清「预判 True / 切分 0 段」与 10 s↔13 s 的耗时跳变 | 1~2 小时 | 切分还能不能用 |
| **D21** | 切分可用 → 改门槛：短段直接调 pyannote（跳过 2 秒窗预判）、`MinimumSplitSeconds` 4.5 → 3.0、`MinimumPartSeconds` 1.0 → 0.8、`MaxParts` 3 → 4 | 半天 | 快速接话能出**两条**带标签字幕 |
| **D22** | 切分不可用 → 走**文本回退**：250 ms 早切 + 标点判定 + 挂起重识别（详见 §4.3） | 1 天 | 绕开声纹分割，用「句子完整没完整」决定 |

## 3. 场景②：重叠插话（修不了，但取舍要拍板）

- **现状**：两路声音叠加后，单说话人模型**只跟住能量/音素更清晰的一路**，另一路**不产生任何 token**——被压住的人连乱码字幕都没有，是**完全空白**；
- **为什么不能修**：叠加区域的音素是混在一起的，**切分/声纹都无从下手**（D14 已确认，五个方向实测无效）；
- **一个要拍板的产品原则**：

  > **宁可漏一个人，也不要出乱码。**
  > 两路混音硬识别出来是「四不像」的烂句，用户会以为翻译坏了；现在的「没出现」至少是干净的失败。

- **唯一可能的方向**：音源分离（Demucs / MossFormer 这类）把混合音轨拆两路再分别识别。但：
  1. 已经打包的 pyannote + CAM++ **只做「这是谁」，不做「把声音拆开」**——必须引入新模型；
  2. 就算分得开，还要测**实时性**（分离慢的话字幕延迟翻倍）；
  3. 结论必须来自实验（D23），**现在不投入**。

## 4. 延迟优化（能省的都在这）

### 4.1 白捡的一笔：识别与翻译重叠（推荐先做）

**现状**：`RecognizeSegmentAsync` 识别完、抛出结果之后，`VoiceSessionHost` **才开始**发翻译请求——**两段串行**。

**改法**：识别一拿到文本就立刻发起翻译请求，识别下一段的同时等翻译结果。

| 收益 | 说明 |
| --- | --- |
| **省 130~450 ms** | 只对「上一句还在翻译、下一句已经来了」的场景生效；**单句场景省不了** |
| 风险 | 低。只是把两次 await 从串行改成并行，**不改任何判定逻辑** |

**编号 D19，成本约 2 小时。**

### 4.2 600 ms 静音窗：为什么不能简单调小

| 说话人 | 句内停顿 | 句间停顿 | 600 ms 的结果 |
| --- | ---: | ---: | --- |
| A（想词型） | 600~900 ms | 900 ms | **句子被切成两条** ⛔ |
| B（连着说型） | 150 ms | 250 ms | **两句并成一条** ⛔ |
| C（正常） | 300~500 ms | 600~700 ms | 刚好 ✅ |

**A 的句内停顿（700 ms）比 B 的句间停顿（250 ms）还长** ⇒ 两个区间重叠 ⇒ **任何固定阈值都会切错一部分人、并错另一部分人**。
所以「测一测句内停顿分布，然后调到 400 ms」这条**不成立**，已作废。

### 4.3 正确的方向：用「句子完整没完整」代替「静音多长」

**核心思路**：不等 600 ms，250 ms 就先动手，用**识别结果**（SenseVoice 是带标点的）反悔。

```
静音 250 ms
   ↓ 立刻切段送识别（约 140 ms），字幕先不显示
   ↓
末尾是「。」「？」「！」  → 判定说完了，立即显示   ⇒ 延迟 ≈ 390 ms（省 210 ms）
末尾是「，」或无标点    → 判定还要说，挂起继续收音
   ↓
他接着说 → 合并后重识别一次   ⇒ 出的是完整句，不会中间断
他没接着说（静音 > 600 ms）→ 确认挂起段并显示
```

| 情况 | 延迟 | 准确度 |
| --- | ---: | --- |
| B 型（连着说、句末完整） | **390 ms** | ✅ 正常 |
| A 型（想词、末尾是逗号） | 约 800 ms | ✅ **比现在更准**（现在会切成两条） |
| A 型但标点识别错 | 390 ms | ⚠️ 偶发切错 |

**关键优点**：**A 型（长停顿说话的人）的字幕质量会变好**——用延迟换来正确断句。
**代价**：挂起段要重识别（CPU 多约 250 ms）；要处理「挂起中又来了新句」的时序；**字幕一旦显示就不能撤**。

### 4.4 辅助手段（可与 4.3 叠加）

sherpa-onnx 的 VAD 内部本来有**逐窗语音概率曲线**，现在被包装层丢掉了（只吐 0/1）。把它暴露出来可以做一条便宜判据：

- **句末**：概率从高**快速掉到 0**；
- **想词**：概率在**中低位抖动**（仍有微弱能量）。

不需要新模型，只是把已有数据拿出来用。

### 4.5 明确不做的

| 不做 | 原因 |
| --- | --- |
| 单纯调静音阈值 | §4.2：区间重叠，调任何值都会害到人 |
| 流式识别（边说边出字） | 要换掉整个批式识别管线；且 D14 已确认模型上限 |
| 音源分离完整实现 | 先做 D23 实验；没结论前不投入 |
| 不给 pyannote 加长度门控 | §5：预判（33~50 ms）已经挡住了长段上的 0.9 秒开销 |

## 5. 「预判到底有没有必要省」——实测回答

| 素材 | 时长 | 头尾预判 | **pyannote 切分** | 整句嵌入 |
| --- | ---: | ---: | ---: | ---: |
| `mix_zh_ja_seq` | 13.4 s | 33 ms | **977 ms** | 118 ms |
| `mix_multi3` | 18.4 s | 47 ms | **1033 ms** | 128 ms |
| `mix_zh_ja_over` | 5.6 s | 47 ms | 42 ms | 53 ms |
| `zh`（单语） | 5.6 s | 50 ms | 35 ms | 47 ms |

**结论**：

1. **预判很便宜**（33~50 ms），只占长段上 pyannote 开销的约 **5%**；
2. **但 pyannote 在 13~18 秒的段上要 0.9~1.0 秒**——去掉预判等于给每个长句白烧 0.9 秒 CPU，**字幕延迟也会跟着涨**；
3. 所以 **预判该留**：它的价值不在短段（短段本来就跑了 pyannote 也不贵），而在**长段上避免整段跑分段**；
4. **场景①的病根不是性能**，而是「门 2/门 3 把短段全都排除了」，加上切分本身返回 0 段。

### 5.1 「说话人标签」开关的延迟成本（实测）

开着标签 = 每句多付 **「预判 + 整句嵌入」**；**疑似换人**时再付 **「pyannote 切分」**。关着 = 这三项**一次都不做**（代码里就是一个 bool 短路）。

| 场景 | 预判中位 | 切分中位 | 整句嵌入中位 | **每句合计** |
| --- | ---: | ---: | ---: | ---: |
| 单语 5 s（中文一句） | 48.1 ms | 38.6 ms | 45.7 ms | **132 ms** |
| 换人 5.6 s（短段，预判 False → 不切） | 44.0 ms | 36.0 ms | 48.6 ms | **129 ms** |
| 换人 13.4 s（长段，预判 True → 真跑 pyannote） | 45.4 ms | **481.6 ms** | 102.4 ms | **629 ms** |

**切分耗时随音频长度增长**（同一段素材截断后取 5 次中位，同一素材 7 次重跑方差很小）：

| 段长 | 预判 | 切分 | 段数 |
| ---: | ---: | ---: | ---: |
| ≤3 s | **0 ms**（直接返回 False） | 0 ms | 0 |
| 5 s | 39 ms | 38 ms | 0 |
| 8 s | 49 ms | 34 ms | 0 |
| 10 s | 51 ms | 37 ms | 0 |
| 11 s | 51 ms | 207 ms | 0 |
| 12 s | 51 ms | 306 ms | 0 |
| 13 s | 49 ms | 384 ms | 0 |
| 13.4 s | 51 ms | 461 ms（13.4 s 素材 7 次重跑中位 490 ms） | 0 |
| 18.4 s | — | 975 ms（7 次重跑中位） | 0 |

**三条结论**：

1. **典型对话句（3~5 秒）开着标签的代价约 +130 ms**，与官方文档原先估计的「每句约多 50 ms」不符——**那个数只算了整句嵌入，没算预判**；
2. **长段是真正的代价**：≥11 秒的段会真的跑 pyannote 分段，从 200 ms 一路涨到 1 秒（18.4 s 时 975 ms）；
3. **而且它现在并不产出结果**：所有长度上**段数都是 0**——开着标签只是在付钱，没拿到换人切分。这也解释了为什么默认关闭是合理的。
