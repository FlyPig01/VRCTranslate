# 他人语音采集自动切换方案（修订版）

修订日期：2026-09-15

## 本轮结论

原方案的产品目标成立：运行 VRChat 时优先只采集 VRChat 的音频，未运行时保留系统回环，便于测试和兼容旧系统。

原方案不能直接实施，原因有四项：

1. Windows 进程回环的官方最低系统版本是 **Windows 10 Build 20348**，不是 2004（Build 19041）。项目当前仍以 19041 为最低版本，必须运行时检测并保留系统回环降级。
2. 进程切换放在 `SubtitleSpeechSession` 并重建整个识别会话，会把两个来源拼进同一个语音段，也可能让停止时的旧识别结果晚于新来源输出。
3. 当前 `IAudioCapture` 只有样本事件，没有来源、故障和停止状态；激活失败或设备断开无法被上层正确处理。
4. PowerShell 播放器不能稳定证明“只捕获目标进程”，原集成测试不足以作为验收依据。

本轮只修改本方案文档，暂不修改生产代码。待本方案审核通过后，再按分阶段计划实施。

方案依据：Microsoft Windows Classic Samples 的 [Application loopback audio capture](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)。实现前应再次核对目标 SDK、系统 Build 和当前 NAudio 版本的 API 定义。

## 目标行为

| 场景 | 采集源 | 用户看到的状态 | 预期结果 |
| --- | --- | --- | --- |
| 检测到可用的 VRChat 进程回环 | VRChat 进程树 | `VRChat 音频` | 只把 VRChat 及子进程的渲染音频送入识别 |
| 未检测到 VRChat | 系统回环 | `系统声音` | 可用播放器或任意系统声音测试 |
| 系统不支持进程回环，或激活失败 | 系统回环 | `系统声音（兼容模式）` | 识别保持可用；只在失败时给一次短提示 |
| VRChat 启动、退出或重启 | 自适应切换 | 状态徽标更新 | 不把两个来源拼成一句字幕，不产生旧来源的迟到结果 |
| VRChat 进程存在但没有渲染流 | 进程回环 | `VRChat 音频` | 保持静音；不能因为静音而退回系统回环 |

用户不配置进程名、PID、音频源或白名单。目标固定为 VRChat，所有切换在后台完成。

进程回环只按“哪个进程输出了声音”做隔离，不会把 VRChat 的 BGM、世界音效或界面音效自动区分成人声。现有 VAD、切句和识别链仍然必须保留；本方案解决的是浏览器、音乐等非 VRChat 进程的混入。

## 分层设计

### Application：稳定的音频边界

在 `VrcTranslate.Application.Abstractions` 增加与平台无关的契约：

- `AudioCaptureSourceKind`：`SystemLoopback`、`ProcessLoopback`、`SystemLoopbackFallback`。
- `ProcessIdentity`：PID 与进程启动时间组成的身份，避免 PID 被系统复用后误切换。
- `AudioSourceState`：来源类型、当前进程身份、是否兼容模式、最近一次故障码。
- `AudioSourceChangedEventArgs`、`AudioCaptureFaultedEventArgs`。
- `IAudioCapture` 增加 `SourceKind`、`SourceChanged`、`Faulted`、`Stopped` 事件；事件只传递应用层数据，不暴露 NAudio、COM 或 Win32 类型。
- `IAudioCaptureFactory` 改为接收 `AudioCaptureRequest`（来源类型、可选 `ProcessIdentity`、麦克风设备 ID），不把 PID 塞进现有的 `deviceId` 字符串。
- `IProcessTargetResolver`：只负责返回当前 VRChat 的稳定进程身份，不依赖 `WorkspaceSettings`。VRChat 是产品固定目标，界面不提供进程配置。

新增 `AdaptiveLoopbackAudioCapture`（应用层协调器，实现 `IAudioCapture`）。它对上层表现为一个连续的采集流，内部管理系统回环、进程回环、切换顺序和来源状态。`LocalSpeechCaptureSession`、SenseVoice、翻译和 OSC 链路继续使用同一个接口，不需要知道采集来自哪个平台实现。

### Infrastructure：Windows 实现

#### VRChat 进程监视器

新增 `VrchatProcessResolver` / `VrchatProcessWatcher`：

- 内部使用规范化名称 `VRChat`（`GetProcessesByName` 不带 `.exe`），不读取或写入用户设置。
- 启动监视后立即扫描，随后每 3 秒扫描一次；候选变化先做短暂复核，避免启动器或快速重启造成抖动。
- 选择策略：先限制在当前交互用户的 SessionId，并优先选择前台 VRChat 窗口对应的实例；没有可用前台信息时，当前身份仍存活则保持当前身份，当前身份退出后从可读取启动时间的候选中选择最早启动者；无法读取启动时间时用 PID 作为稳定的次级排序。该策略必须在单测中固定，不能依赖机器上的偶然进程顺序。
- 每次使用 `Process` 后立即释放；捕获无权限、进程退出和 `StartTime` 读取竞态。
- 身份比较同时使用 PID 与启动时间，PID 重用必须视为新目标。
- 支持取消和异步释放，应用关闭后不留轮询任务。

#### 进程回环采集器

使用 Windows 官方 Application Loopback 接口：

`ActivateAudioInterfaceAsync` → `VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK` → `AUDIOCLIENT_ACTIVATION_PARAMS` → `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` → `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` → 目标 PID。

实现边界如下：

- 官方进程回环要求 Windows 10 Build 20348 或更高版本。项目仍编译为 `net10.0-windows10.0.19041.0`，运行时必须通过能力检测决定是否启用；19041 至 20347 只使用系统回环。
- NAudio 新版本包含部分低层激活声明，但没有可直接替换 `IWaveIn` 的完整进程回环采集器。优先复用 NAudio 已有的 COM/WASAPI 类型和微软样例的激活流程，只补项目所需的最小互操作层，避免重复声明整套 `IAudioClient`。
- `ProcessLoopbackAudioCapture` 直接实现项目的 `IAudioCapture`，不向 Application 泄露 `IWaveIn`。事件驱动地排空 `IAudioCaptureClient`，处理 48 kHz 浮点/WAVEFORMATEXTENSIBLE、静音标志、数据不连续、设备失效和异步停止。
- 样本继续复用 `AudioSampleConverter` 转为单声道 16 kHz；不写临时 WAV 文件。
- 激活同时检查 `ActivateAudioInterfaceAsync` 的立即返回值和异步 `GetActivateResult`；完成回调对象必须保持存活并满足跨线程调用要求，不能在 UI STA 上同步等待。`PROPVARIANT`、x64 结构体对齐和 COM 释放集中封装。
- 采集循环在同一线程成对执行 `GetBuffer`、复制和 `ReleaseBuffer`，处理 `BUFFER_EMPTY`、`SILENT`、`DATA_DISCONTINUITY`、`DEVICE_INVALIDATED`、`RESOURCES_INVALIDATED` 和 `SERVICE_NOT_RUNNING`；`RecordingStopped` 只发布一次。
- 激活、COM apartment、回调线程和释放顺序都必须可取消且可重复。任何 HRESULT 进入 `Faulted`，不得在 NAudio 回调线程直接更新 UI。

现有 `WindowsAudioCapture` 保留为麦克风和系统回环实现，并在相同的应用层接口下补齐故障/停止事件。

## 自适应切换状态机

`AdaptiveLoopbackAudioCapture` 的状态只有以下几类：

`Stopped` → `SystemLoopback` → `ProcessLoopback` → `SystemLoopback`；进程激活失败时进入 `SystemLoopbackFallback`，不是错误终止。

切换流程：

1. 监视器产生新的 `ProcessIdentity` 或 `null`，协调器为该决策分配递增的 generation，并取消上一代的候选启动任务。
2. 在后台创建并启动候选采集器；候选未成功启动前，当前正常采集器继续工作。
3. 候选成功后，先暂停向识别管线派发样本，发布来源边界事件，再停止并释放旧采集器，原子替换当前采集器，最后恢复派发。
4. 来源边界事件通知 `LocalSpeechCaptureSession`：取消旧 generation 的未完成识别任务，丢弃 segmenter 中尚未闭合的样本并重置 VAD/能量门限。切换前的半句话不发送，避免系统声音和 VRChat 声音拼句。
5. 所有识别、翻译和 OSC 输出在提交结果前检查 generation；旧任务即使晚返回，也不能更新字幕、预览或 OSC。切换和 Stop 共用同一个取消令牌，并在释放前等待旧任务结束。
6. 候选启动失败时保留当前采集器；若当前来源已不可用，则切换到系统回环并标记兼容模式。
7. 同一进程身份的失败采用退避（例如 5 秒、15 秒、30 秒后封顶），PID 变化、设备变化或应用重新启动时清除退避。旧决策的异步结果不得覆盖新 PID 决策。
8. 目标进程没有音频渲染流时，进程回环正常返回静音；静音不是激活失败，不触发系统回环降级。

停止和释放必须与切换串行化：应用退出、页面切换、设备断开和进程变化不能同时操作同一个 capture 实例。

## 会话与界面接线

- `SubtitleSpeechSession` 请求 `AdaptiveLoopbackAudioCapture`，不再固定请求 `SystemLoopback`。
- `VoiceSessionHost` 继续负责应用生命周期；页面只订阅运行状态、音量和短来源标签，不持有 watcher、PID 或切换线程。
- `LocalSpeechCaptureSession` 增加“来源边界重置”入口，识别模型、语言和翻译路由不改。
- 语音页只显示一个紧凑状态徽标：`VRChat 音频`、`系统声音` 或 `系统声音（兼容模式）`。切换不弹 InfoBar、不堆叠说明文字；仅首次激活失败时显示一次短提示，恢复后自动消失。
- 不增加进程选择、音频源下拉、目标语言或模型配置。现有用户界面保持面向普通用户的简洁结构。

## 系统兼容与失败策略

| 情况 | 处理 | 是否重试 |
| --- | --- | --- |
| Windows Build < 20348 | 直接使用系统回环 | 不尝试进程激活 |
| 进程回环 HRESULT 激活失败 | 保留当前采集；无可用来源时使用系统回环并标记兼容模式 | 按当前进程身份退避 |
| VRChat 退出 | 切回系统回环 | 下一次检测到 VRChat 时重试 |
| 音频设备失效 | 先重建同一来源，失败后使用系统回环 | 受退避限制 |
| 进程无渲染流 | 保持进程回环静音 | 不因静音降级 |
| 应用停止/Dispose | 取消 watcher、停止采集、释放 COM 和回调 | 不重试 |

“不中断识别”改为可验证的表述：识别会话对象保持运行，但来源切换允许有短暂空窗；切换边界上的未完成语音段会被丢弃，以保证字幕内容正确。

## 自动测试与验收

### Application 单元测试

- 进程名规范化、首次立即扫描、轮询去重、取消和释放。
- 多实例选择、`StartTime` 无权限、进程退出竞态、PID 重用（PID 相同但启动时间不同）。
- 无目标、目标出现、目标退出、目标重启和快速抖动的决策表。
- 不支持系统、激活失败、设备失效、退避与重试上限。
- 候选采集启动失败时旧采集仍保持；新 generation 不能被旧异步结果覆盖。
- 来源切换会重置 segmenter；旧语音段、识别、翻译和 OSC 结果均不会泄漏到新来源。
- Stop、Dispose、切换并发时只释放一次，不残留任务、事件订阅或线程。

### Windows 集成测试

不使用临时 PowerShell 播放器。新增受控的 Windows 音频测试 helper：两个独立进程分别通过 WASAPI/WaveOut 输出不同频率的持续音（例如 440 Hz 与 880 Hz），测试捕获结果的能量/频率相关性：

1. 目标进程回环能检测到目标频率。
2. 非目标进程频率不进入目标回环结果。
3. 目标进程无渲染流时结果为静音且不自动切到系统回环。
4. 目标结束后系统回环仍能捕获已知测试音。

测试仅在 Windows Build ≥20348 且存在活动播放端点时运行，否则明确标记为 Skip；不把 CI 静音当成失败。另保留不依赖硬件的协调器和状态机单测。

### 人工验收

- 未启动 VRChat 时播放音频，状态为 `系统声音`，能正常得到字幕。
- 启动 VRChat，同时播放浏览器音乐，状态切为 `VRChat 音频`，浏览器声音不产生字幕。
- VRChat 退出、重启、多个实例并存时，来源和字幕内容正确。
- 在不支持进程回环的系统上，软件仍能使用系统声音，不崩溃。
- 关闭主程序后 watcher、采集器、COM 回调和悬浮窗全部退出。

验收指标统一为：目标进程状态变化的发现延迟不超过 3 秒；候选采集成功后切换完成不超过 1 秒；切换不得产生跨来源字幕或旧结果。

## 不做的事

- 不增加进程名、PID、多应用白名单或音频源选择 UI。
- 不使用 WMI/ETW 事件订阅；轮询足够轻且更容易测试和释放。
- 不按“没有声音”自动降级，避免浏览器音乐重新混入。
- 不修改 SenseVoice、翻译模型、语言策略、OSC 格式或字幕浮窗布局。

## 实施阶段与工作量

原文的 1～1.5 天估计不可信，进程回环的 COM/异步资源管理和真实音频验收需要分阶段完成：

| 阶段 | 内容 | 估计 |
| --- | --- | --- |
| 1 | Application 契约、进程决策器、状态机和全套 fake 单测 | 0.5～1 天 |
| 2 | 系统回环/进程回环协调器、退避、generation 和切句边界 | 1～1.5 天 |
| 3 | Windows 官方进程回环互操作、格式处理、资源释放 | 1.5～2.5 天 |
| 4 | 页面状态接线、Windows helper 集成测试和人工验收 | 1～1.5 天 |

总计约 4～6 天，实际时间取决于系统版本、音频设备和原生 API 调试结果。每阶段先通过自动测试，再进入下一阶段；本文件审核通过后才开始代码实施。
