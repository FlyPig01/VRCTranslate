## 2. 已完结项摘要

- **D1**：他人语音长对话改为消息条滚动列表——每条一句、可上下回看、新消息自动滚到底；不持久化、无清空入口。
- **D2**：术语库卡片删掉保存按钮与重复「启用」文字，标题行与其它卡片对齐；补齐删除后的自动保存触发点。
- **D3**：F7 成为「他人语音 → 字幕」总开关，语音页「打开字幕」按钮删除；任何启停路径结束后窗口可见性 = 识别运行状态。
- **D4**：字幕浮窗去掉易误会的「麦克风」标识，字幕水平居中。
- **D5**：根因是 `SubtitleSpeechSession` 把他人语音译文写进共享预览状态；已改为独立通道。
- **D6**：字幕浮窗样式改造 + 渐进式字幕（分段渐进上屏）落地。
- **D7**：大字幕窗口消息列表改为顶部对齐，高度跟随内容时窗口顶边固定、向下生长。
- **D8**：DeepL / Google 两个提供商删除；老配置回落到仍可用的档案。
- **D9**：三个快捷键改为「点击即录制」的按键捕获框（X 图标随之消失）；清空后的快捷键不再在其它页面回落默认值。
- **D10**：输入浮窗默认宽度按 DPI 换算，不再出现高 DPI 下过窄。
- **D11**：OSC 载荷带原文（与 VRChat Chatbox 的显示契约对齐）。
- **D12**：小米 MiMo 接入（`mimo-v2.5` 默认、关思考）；ASR 明确不接（云 ASR 非流式、只支持中英、丢说话人区分，纯亏）。
- **D13**：腾讯/阿里翻译链路修复三个必填/签名问题（缺 `ProjectId`、签名覆盖的 content-type 与实际发送的不一致、缺 `FormatType`），此后真实密钥端到端可用。
- **D16**：**关闭为「直喂实验的假象」**——原实验绕过 VAD 把 18.4 s 整段喂给识别器，暴露的是识别器单段上限；软件真实路径先经 VAD 切段（生产同款参数与 512 块长），逐段识别**三语全部恢复**（中文 + 英语完整句 + 韩语整句），且每段比直喂更完整。VAD 强切损耗实测在案（每次 80~84 ms、预热 80 ms），真实语音从未触发强切（最长自然段 5.46 s），**不修**。回归防线 `SileroVadSegmenterTests.A_continuous_signal_is_force_cut_at_12s_without_eating_speech`。
- **D17**：偶发失败的根因是**测试断言与生产异步之间的间隙**（`InstallAsync` 先 `SetState`，旧采集的 Stop/Dispose 在之后的 await 里才完成），非进程枚举竞争。修复只动测试：等待条件加强到「换流完全落地」（`InstallSettled`）、`changes` 读侧加锁、假采集计数改 `Interlocked`/`volatile`、超时可选（本测试 10 s）。验收要求**全量并行**连跑（单跑不会饥饿，证明不了）——**连跑 5 次全绿**，生产代码零改动。
- **D18**：输入框底部截断——默认高度 `150 → 200` DIP（漏算标题栏与状态行）；已保存过矩形的用户拖高即可，不用清数据。
- **D20**：**结论反转**——用**真实双人播客**实测，换人切分**确实有效**（15.21 s 段切成 3 片、声纹标签分开）；此前「恒为 0 段」的判断只在自拼接的合成音频上成立，**已作废**。同时发现**头尾预判有害**：36 个长段里 **11 段（38%）的真换人被预判挡掉**，而预判为 False 的段 pyannote 只要 33~233 ms——**没省到钱**。素材与脚本见 [能力边界与决策记录.md](能力边界与决策记录.md) §6.4。
- **D25/D26/D27**：删掉头尾预判（`ISpeakerChangeSuspected` 及其专用辅助一并删除）、边界变更点改「夹紧到 `[minPart, total-minPart]`」并加「两片放不下取中点」兜底、`MinimumSplitSeconds` 4.5 → 3.0 s（依据：2.5 s 片只有 6/24、3.0 s 片有 8/20 能给出换人点）。新增 8 条 `SpeakerSegmentSplitter` 单测。**效果**：同一素材（播客前 8 分钟、58 个 VAD 段）成功切分从约 **13 段 → 29 段**，切分耗时中位 34 ms、最大 1.26 s（不再有预判开销）。验证：全量 **389 条**测试连跑 3 次全绿。

## 4. 未决项（保留全文）


### D23 · 音源分离能不能救「重叠丢一路」→ ❌ 不可行（实验已完成）

| 检查项 | 结果 |
| --- | --- |
| sherpa-onnx 自带分离模型能拆两个人声吗 | ❌ 不能。只提供 **Spleeter / UVR**，都是**音乐伴奏分离**；两路都是人声时不会拆开 |
| sherpa-onnx 分离接口本机可用吗 | ❌ 用官方 `spleeter-2stems` 模型报 `ComputeStft: Invalid channel 1. Max 1`（1.13.8） |
| 换人声专用模型（SepFormer） | ⚠️ 需 Python + PyTorch 栈（与「纯 .NET + onnxruntime」冲突），无 ONNX 版本可嵌入 |
| 就算能分离，延迟可接受吗 | ❌ 按训练块推理（块长 4 s）⇒ 字幕至少晚**数秒** |

**结论：不做**，维持「保一路」。完整记录见 [能力边界与决策记录.md](能力边界与决策记录.md) §6.3。

### D24 · 是否引入流式识别 → ⏸ 暂缓（架构级决定）

它是 `[批式固有]` 两条（字幕疏、文本大块）**唯一**的解法，但代价包括：语言从「一个模型四语」变成「一语一模型」、**日语流式模型质量尚未核实**、识别层与说话人标签要重做、资源与包体上升。

**用户已明确暂缓**：这属于引入新功能，不是修缺陷。零风险起步（查资料半天 → 小样对比半天）见 [能力边界与决策记录.md](能力边界与决策记录.md) §7。
