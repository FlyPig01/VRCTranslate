# 分析：说话人区分（声纹）功能——实测结论与建议

> **状态：分析稿 v2，待决策**。v1 曾建议「删掉换人切分」，**该建议已作废**——
> 原因是 v1 只有合成素材（自拼接录音），**不代表真人对话**。
> v2 用**真实双人播客**（B 站《English Pod》，Marco 与 Erica 两人对话）实测，结论反转。

## 0. 结论（v2）

| 项 | v1 的说法 | **v2 实测** |
| --- | --- | --- |
| 换人切分能不能用 | ⛔ 建议删除（合成素材段数恒为 0） | ✅ **真人对话上确实能切**，且切出来的片带不同声纹标签 |
| 头尾预判 | 以为在省钱 | ❌ **有害**：漏掉 38% 真换人，还白跑 pyannote |
| 每句成本 | 130 ms | 13 秒段约 **500~900 ms**（pyannote 本身），预判另加 33~50 ms |
| 建议 | 只删①换人切分 | **保留①，改三处**：删预判、降 `MinimumSplitSeconds`、边界变更点改夹紧 |

## 2. 核心实测：切分在真人对话上确实工作

以 P1-01 的一分钟为例，VAD 切出 6 段，其中 15.21 s 的那段切成 3 片：

| 片 | 时长 | 声纹 | 识别文本 |
| --- | ---: | --- | --- |
| 1 | 4.64 s | `spk-0001` | That's right, we're going to give you some real English to t… |
| 2 | 5.37 s | `spk-0002` | Exactly English that you would use in everyday life that you… |
| 3 | 5.21 s | `spk-0002` | English people actually use Exact, so why don't you tell us… |

另一段 12.94 s → 3 片（7.76 / 2.21 / 2.97 s），声纹依次 `spk-0001 / spk-0002 / spk-0001`——
**正是两位主持人一来一回**。

⇒ **① 换人切分有效**；对应的 ② 贴标签也有效（同段内能分出两个声纹）。

## 3. 核心实测：头尾预判**有害**，不是省钱

扫描 P1 前 8 分钟的全部 **36 个长段（≥3 s）**：

| 项 | 段数 |
| --- | ---: |
| 预判 = True | 18 |
| **预判 = False（这些段现在根本不会跑 pyannote）** | **11** |
| pyannote 认为「没换人」（变更点为 0） | 7 |
| 有变更点、但被边距规则丢弃（白跑一次） | 2 |

**两个致命问题**：

1. **漏检**：**11/29 ≈ 38% 的真换人段落被预判挡掉**（这些段本来能切出来）；
2. **预判根本没省钱**：看实测耗时——

| 段长 | 预判 | 切分耗时 |
| ---: | ---: | ---: |
| 9.0 s | False | **38 ms** |
| 10.7 s | False | 233 ms |
| 12.7 s | True | 476 ms |
| 15.2 s | True | 886 ms |
| 12.7 s | True | 1,317 ms |

**预判为 False 的段，pyannote 也会很快返回（几十毫秒）**——也就是说：
**「先预判再决定跑不跑」省下的那点时间，远远抵不上它挡掉的换人。**

### 顺带更正官方文档的一个错数

文档原写「开启后每句约多 50 ms」——那只算了②贴标签的整句嵌入。
**实测（真人 13 秒段）：预判 33~50 ms + pyannote 300~900 ms + 嵌入 50~100 ms ⇒ 约 0.4~1.1 秒/段。**

## 4. 另两个可改进点

### 4.1 变更点贴边就被丢弃（白跑）

`SpeakerSegmentSplitter.Split`（`SpeakerSegmentSplitter.cs:25`）：

```csharp
if (point < minPartSamples || point > totalSamples - minPartSamples) continue;
```

变更点离两端不足 1 秒时**整点丢弃**。实测 36 段里有 **2 段**因此白跑 pyannote（有变更点却切不出片）。
**改法**：把贴边的变更点**夹紧到 1 秒边界**（`max(minPart, min(point, total-minPart))`），或直接切成「1 秒 + 其余」，而不是丢弃。

### 4.2 `MinimumSplitSeconds = 4.5 s` 偏高

短于 4.5 s 的段完全跳过切分；但真人快速接话常常整段只有 3~4 秒。
配合「删掉预判」，可以把它降到 **3.0~3.5 s**，并用边距规则（`MinimumPartSeconds = 1.0 s`）兜住碎片。

## 5. 修正后的建议

| 建议 | 内容 | 预期收益 | 成本 |
| --- | --- | --- | ---: |
| **① 删掉头尾预判** ⭐ | `PlanSpeakerSpans` 里不再调 `IsSpeakerChangeSuspected`，长段直接跑 pyannote | **多挽回 38% 的换人**，且**更快**（省 33~50 ms/段的预判） | 小 |
| **② 边界变更点改夹紧** | 贴边不丢弃，夹到 1 秒边界 | 再挽回约 2/36 段 | 小 |
| **③ `MinimumSplitSeconds` 4.5 → 3.0 s** | 让 3~4 秒的快速接话也能切 | 覆盖快速接话场景 | 小 |
| ④ 保留 ②贴标签 与 ③声纹库 | 不变 | — | — |

**不需要做的**：不必删功能、不必换模型、不必上流式（那是另一条线，见《模型能力边界.md》§4）。

## 6. 仍未解决的部分（说清楚）

| 项 | 现状 |
| --- | --- |
| pyannote 对**短促快速接话**（<3 s 整段） | 仍无法切（模型本身需要一定长度）；这类只能靠 D22 文本回退那条线 |
| **重叠同时说话**（两人同时出声） | **仍然无解**（单说话人模型，见《模型能力边界.md》§1） |
| 长段切分耗时（13 s 段 0.5~1.3 s） | 删预判后这一项会**全部落在识别链路上**，需要评估是否可接受（13 s 段的识别本身约 200 ms，切分占比很高） |
