## D13 · 腾讯云 / 阿里云翻译从未真正成功过（三个必填/签名问题，已修复）

- **发现经过**：用户提供 V1 的 `config.json` 后，用**真实密钥**做端到端验证，才发现这两条链路根本走不通；
  在此之前它们从未被真实调用验证过（应用内只有"回显"档案被实际使用过）。
- **三个根因（都靠真实请求逐条定位）**：

  | # | 服务 | 现象 | 根因 |
  | --- | --- | --- | --- |
  | 1 | 阿里云 | `400 MissingFormatType` | `TranslateGeneral` 的 `FormatType` 是**必填**，我们没发 |
  | 2 | 阿里云 | `10004 参数出错` | **专业版不是"同一个 Action 换 Scene"**：通用版是 `TranslateGeneral + Scene=general`，专业版是 **`Action=Translate` + 领域 Scene**（`title`/`description`/`communication`/`medical`/`social`/`finance`），传 `professional` 会被拒 |
  | 3 | 腾讯云 | `AuthFailure.SignatureFailure` | 两个叠加原因：① 请求体缺 `ProjectId`（TMT 要求该字段，缺了不报"缺参数"而是报签名错）；② **签名覆盖的 content-type 与实发的不一致**——`StringContent` 实际发出 `application/json; charset=utf-8`，而规范请求串里写的是 `application/json` |

- **定位方法（可复用）**：抓应用真正发出的原始请求（自定义 `DelegatingHandler`）→ 与手写签名逐项对照 →
  做**单变量矩阵**（content-type 带不带 charset、action 大小写、末尾换行、body 带不带 ProjectId），
  一次请求就能判定哪一项是决定性的。注意：**签名错误会掩盖参数错误**（body 一变签名就对不上，
  服务端只会回 `SignatureFailure`），所以"签名不对"时先怀疑参数，而不是先怀疑密钥。
- **修复**：
  - 腾讯：请求体恒定带 `ProjectId`（默认 0，可用 `project_id` 选项覆盖）；新增常量
    `SignedContentType = "application/json; charset=utf-8"`，**签名与实发共用同一个常量**。
  - 阿里云：补 `FormatType=text`；按版本分派 Action（`Translate` / `TranslateGeneral`），
    专业版的 `Scene` 取领域值（默认 `social`，可用 `domain` 选项覆盖）；`ResolveScene`/`IsProfessional` 可单测。
- **验证（真实密钥，直读 config.json，四个组合全绿）**：

  | 组合 | 结果 |
  | --- | --- |
  | 腾讯云 | ✅ 575 ms → 你好，准备好了吗？ |
  | 阿里云通用版 | ✅ 326 ms |
  | 阿里云专业版（下拉选择） | ✅ 395 ms |
  | 阿里云专业版（仅 `Model` 兜底） | ✅ 373 ms |

  单测：新增/更新 4 条（版本×Action×Scene、腾讯 content-type 与 ProjectId、错误码提示），
  其中**改写了一条原本断言错误行为的旧测试**（`Aliyun_provider_signs_form_request_and_maps_professional_scene`
  原先断言 `Scene=professional`，那正是会被服务端拒绝的写法）。
- **顺带修正的错误结论**：我曾用**手敲的密钥**做验证，得到"密钥已失效"的结论——**那是错的**：
  手写转写引入差异，服务端返回 `SecretIdNotFound` 把我带偏。教训：**测试凭据必须从来源文件直读，不要手工转写**。

## D1 · 他人语音长对话消息堆叠，无法查阅

- **状态：已实施**（消息条滚动列表：每条一句、可上下回看、新消息自动滚到底；不持久化、无清空入口；暂停保持现状）
- **现象**：语速很快的长对话里，字幕把连续多句一次性堆在一起输出，成了一整块文字，无法逐条查阅。
- **期望**：改成消息条滚动列表（类似 QQ / 微信）——每条一句、可上下滚动回看历史、新消息自动滚到底。
- **影响面**：只涉及字幕的呈现与消息模型（`SubtitleOverlayWindow` / `OverlayWindowHost` / `SubtitleSpeechSession` 的输出路径），**不涉及识别与翻译链路**。

### 已确认的产品决定

| 问题 | 决定 |
| --- | --- |
| 是否持久化历史 | **不持久化**：消息只存在于当前运行期间，不写磁盘 |
| 是否提供「清空」 | **不提供**清空按钮 |
| 暂停时的行为 | **保持现状**：暂停即停止追加，不清空、不改变已有消息 |
| 与现有「原文 + 译文」结构 | **合并为同一条消息**，不新增一层结构 |
| 呈现内容 | **可选**：仅译文 / 译文 + 原文 |
| 说话人标签 | 开启说话人区分时随消息呈现（沿用现有标签） |

### 实施决定（原「待定」项的落地结果）

- 消息条数上限 **200 条**（`SubtitleCaptionBuffer.DefaultCapacity`），超出丢弃最旧的，内存有界；
- 暂停后重新开始**接着已有消息继续追加**：`Pause` / `Resume` 只控制是否追加，不清空、不改写已有消息；
- 自动滚底只在用户停留在底部时生效；用户上翻后改为显示「有新消息」提示，回到底部再恢复自动滚动；
- 呈现内容「仅译文 / 译文 + 原文」在语音页「字幕窗口」卡片内切换，落在 `v2-voice-settings.json` 的 `SubtitleContent`，默认「译文 + 原文」。

- **测试素材**：B 站视频 <https://www.bilibili.com/video/BV1dEY76fEn2/> —— 用户指定的音频测试素材，本现象即由此发现。

## D3 · 「字幕」快捷键的名称与实际职责不符；并取消暂停识别

- **状态：已实施**（与 D4 一并执行；F7 成为「他人语音 → 字幕」总开关，语音页「打开字幕」按钮已删除）
- **现状**：F7 目前**只**切换字幕浮窗的显示/隐藏，不影响他人语音识别（识别由语音页的开始/停止按钮控制）。
- **要求（用户已澄清）**：
  1. **让 F7 同时开关语音识别**：按下时“开”＝开始他人语音识别 + 显示字幕浮窗；再按下“关”＝停止识别 + 隐藏浮窗。
     即这条快捷键成为整个“他人语音 → 字幕”功能的总开关。
  2. **改名**：它的职责从“只管子幕”变成“识别 + 字幕”，所以不能再叫「字幕」。
  3. **不新增快捷键**：不要为“暂停识别”单独加一条，一切合并在这一条上。
- **名称已定：`他人语音`**（与侧边栏页面名「语音」呼应；设置页三行成为「打开输入框 / 他人语音 / 自身语音」）。
  所有出现该快捷键的地方统一为「他人语音」，提示语改为“开始 / 停止他人语音识别”。
- **影响面**：设置页快捷键行文案与提示语（现为“打开 / 关闭字幕”）、指南页快捷键表、语音页与浮窗的快捷键提示、
  F7 的行为接线（`HotkeyActionRouter` / `MainWindow` / `VoiceSessionHost` 的启停路径）；**不涉及识别模型与翻译逻辑**。
- **行为后果与决定（用户已裁定）**：
  - F7 成为“全开 / 全关”：开启＝开始识别 + 显示浮窗，关闭＝停止识别 + 隐藏浮窗；
  - **删除语音页上的「打开字幕」按钮**（用户不认同保留“只藏窗口”的入口）：浮窗只随识别状态出现与消失，
    不再提供独立开关。实施时须同步更新验证脚本中与之相关的断言与冒烟（例如“打开字幕 只允许出现一次”的计数断言、
    以及用该按钮打开浮窗的冒烟路径），按新交互保留其真实意图，不得为了通过而放宽要求；
  - 识别启动需要模型就绪：模型未就绪时按 F7 应给一次明确提示（而不是静默无反应）；
  - 浮窗隐藏与识别停止必须走同一条串行化路径，避免“窗口藏了但识别还在跑”或反之的中间态。

### 实施结果

- **总开关**：Application 层的 OtherPlayerCaptionToggle 是唯一入口——快捷键、语音页的开始 / 停止按钮、
  以及字幕浮窗的系统关闭都走它；切换在信号量上串行化，开＝先启动识别再显示浮窗，
  关＝先停止识别再隐藏浮窗（停止报错也会把浮窗收掉），模型未就绪时两个效果都不施加。
- **窗口与识别不会脱节**：OverlayWindowHost 同时把 SubtitleVoice.RunningChanged 映射到浮窗的显示 / 隐藏，
  因此任何启停路径（含退出时的 ShutdownSpeechAsync）结束时窗口状态都等于识别状态；
  关闭字幕窗口不再是“只藏窗口”，而是把整条功能关掉（停止识别 + 隐藏窗口）。
- **启动行为**：字幕浮窗不再随程序启动出现，只在识别运行时出现——识别没跑时它不留在桌面上。
- **模型未就绪**：按 F7 会切到语音页并弹出一条明确提示（“本地语音模型尚未就绪，请先安装模型”），
  不再静默无反应；判定与提示都落在可测接缝上（OtherPlayerCaptionToggleOutcome.ModelNotReady）。
- **改名**：设置页快捷键行、指南页快捷键表、语音页快捷键提示统一为「他人语音」，
  提示语为“开始 / 停止他人语音识别”（设置页三行为「打开输入框 / 他人语音 / 自身语音」）。
- **验证脚本**：删除「打开字幕 只允许出现一次」的计数断言与该按钮的交互冒烟，改为断言按钮必须不存在、
  语音页唯一入口走总开关；语音页冒烟改用 F7 打开 / 关闭浮窗，并用状态文本核对“窗口可见 ⇔ 识别运行”。


## D4 · 字幕浮窗的「麦克风」标识易误会；字幕应水平居中

- **状态：已实施**（与 D3 一并执行）
- **现象与要求**：
  1. 字幕浮窗左侧有一个圆形标识，看起来像**麦克风**，容易让人误会“软件在用麦克风收音”——实际采集的是系统声音 / VRChat 音频。**去掉该标识**；
  2. 字幕文本改为**水平居中**。
- **影响面**：`SubtitleOverlayWindow.xaml` / `.xaml.cs`。
- **连带影响（实施时必须处理）**：该标识就是“活动标记”（subtitle-activity-mark），`Invoke-V2Validation.ps1` 里有一条
  「Subtitle activity mark render and animation」冒烟专门统计它区域的像素变化。标识移除后必须同步更新该冒烟与相关断言，
  按新的真实意图处理（浮窗不再有活动指示），不得为了让脚本通过而放水；活动反馈仍由语音页的电平表承担。

### 实施结果

- 左侧圆形活动标识（含呼吸光环与 90ms 视觉定时器）已整体删除，浮窗只剩消息条与「有新消息」提示；
  源码断言改为“不得再出现活动标识 / 图标 / 装饰”，渲染冒烟改为核对表面已绘制、没有残留强调色像素，
  并核对消息条在浮窗内左右留白对称（旧标识列会让左侧多出 46px）。
- 消息条、译文、原文与说话人标签行全部按整条消息宽度居中（TextAlignment.Center + 拉伸），
  D1 的消息条列表、自动滚底与上翻提示行为不变。

## D5 · 他人语音的译文漏进「输入框」（已修复）

- **现象**：识别他人语音时，翻译结果同时出现在**快速输入浮窗**里（那是给自己说话用的）。
- **根因**：`VoiceSessionHost.SubtitleSpeechSession` 把他人语音的译文写进了**共享的翻译预览状态** `AppState.SetTranslationPreview`，
  而 `QuickInputWindow` 与自身语音页都订阅 `TranslationPreviewChanged`。等于把“别人说的话”塞进了“我说的话”的展示位。
- **修复**：他人语音路径不再写共享预览；字幕只走字幕浮窗（OSC 行保持原样）。自身语音路径不变。

## D6 · 字幕浮窗样式问题与渐进式字幕（已实施）

- **状态：已实施**（样式改造与渐进式字幕均已落地，见文末「实施结果」）
- **用户反馈（原话要点）**：字太大；句子和译文的格式不统一；第一句译文的位置不对；有时候一次弹出两个翻译记录；整体看着不舒服。
- **现状实测（代码事实）**：
  - 译文 22px / SemiBold，原文 15px / Normal，说话人标签 12px / SemiBold；三者全部**居中**；
  - 每条消息是一个**圆角气泡**（Background + CornerRadius 8 + Padding 10,6 + 下间距 6）；
  - 浮窗最小宽度仅 360px —— 在这么窄的窗口里放 22px 译文，一句话会被拆成很多行，这是“字太大”的量化原因；
  - 消息列表 `VerticalAlignment=Bottom`（底部对齐）：只有一条消息时它贴在窗口最底部，上方全空 —— 这很可能就是“第一句位置不对”的观感来源。
- **“一次弹出两条”的两种可能（需确认）**：① VAD 把一句话切成两段，各自成条（Silero VAD 上线后更敏感）；
  ② 同一条消息被渲染两次。需要用户提供一张截图（或说明两条内容是否重复）来定位。

### 改造方案（待确认）

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 译文字号 | 22px | **18px**（并可随窗口宽度自适应，窄窗再降一档） |
| 原文字号 | 15px | **13px**，颜色再暗一档，明确是“辅助信息” |
| 统一格式 | 译文 SemiBold 居中 + 原文 Normal 居中，主次差异过大 | 两者**同一对齐方式、同一左右内边距、同一行距**；只用字号/字重/颜色区分主次 |
| 行序 | 按消息内容顺序（译文在前、原文在后） | 固定为**译文在上、原文在下**（同一条消息内），不要随来源变化 |
| 气泡 | 每条一个圆角气泡 | 保留消息条概念，但**去掉圆角气泡感**：整块深色表面 + 细分隔（更像播放器字幕，减少视觉噪音） |
| 首条位置 | 底部对齐，单条时贴底、上方大片留白 | 保持底部对齐（字幕惯例），但**窗口高度随内容收缩到合适值**，避免单条时窗口空一大块 |
| 间距 | 消息间 6px，气泡内 10,6 | 行距 1.35 左右，消息间 8~10px，视觉上更透气 |

- **“参考他人做法”的结论**：主流字幕（YouTube 双语、会议字幕）是**居中、无气泡、半透明深色底、主译文大 + 副原文小、字号随窗口自适应**；
  QQ/微信式气泡适合聊天记录，用在实时字幕上会显得碎、吵。建议按上表向“播放器字幕”靠，同时保留可回看滚动。


### D6 决定（已确认）

- **样式方向：认可**，按上表实施（译文 18px、原文 13px、统一格式、固定“译文在上原文在下”、弱化气泡向播放器字幕靠、窗口高度随内容收缩、行距 1.35 / 消息间距 8~10px）。
- **“一次弹出两条”的成因已查明（用户确认）**：**内容不重复**，是 VAD 把快语速切成了两段，加上翻译（约 900 ms）远慢于识别（约 140 ms），
  第二段识别完成时第一段还在翻译，于是两条译文几乎同时落地。既有“分段”因素也有“翻译慢”因素，不是渲染重复。
- **采用的对策：渐进式字幕**——识别完成即先显示原文（含说话人标签），译文到达后再**填进同一条消息**，不改条数、不重排。
  这样每条消息在它真正识别出来时就出现，翻译只是后续填充，不再出现“一次冒出两条”。
  （VAD 阈值在无实测证据前不动；如仍嫌切得碎，另行评估。）

### 实施结果

- **样式**（`SubtitleOverlayWindow.xaml.cs`）：译文 18px、窄窗（面板宽度 < 420）降一档到 16px；原文 13px 且颜色调暗一档（#93A7BC）；
  说话人 12px。三行共用同一居中方式（`TextAlignment.Center` + 整条宽度拉伸）、同一左右内边距（12）与同一行距（1.35 × 字号）。
  行序固定「译文在上、原文在下」，由 `SubtitleCaptionBuffer.Present` 一处决定，不随来源变化。
- **气泡**：删除每条消息的圆角气泡与底色，改成整块深色表面 + 消息之间的 1px 细分隔（#26364B），消息间距 9px；
  最上面那条不画分隔线（`RefreshSeparators`）。浮窗仍然没有选择器、没有清空入口、只有一个 `subtitle-text`，XAML 里只剩「有新消息」一个 Button。
- **窗口高度随内容收缩**：`FitSurfaceHeight` 按消息列表的实际高度 + 非客户区高度算出目标高度（下限是面板最小高度 `MinHeight=72`），
  底部边缘固定（由 `OverlayWindowController.ResizeKeepingBottom` 向上生长），不超过用户上次的窗口高度，
  单条消息不再贴在一个大空块的最下面。
  - 还没有任何消息时不做收缩：空面板保持用户留下的矩形，不为「零条消息」先塌成一条。
  - 用户手动改过窗口高度后，本次运行不再随内容改高度（`_readerOwnsHeight`），不会把刚拖出来的高度又缩回去。
    用户的高度同时是上限与持久化目标：`ToStoredLayout` 只存「用户高度 + 保持底边」，
    自动跟随出来的高度是运行时细节，既不会覆盖用户的选择，也不会让下一次启动被压缩后的高度卡住。
- **渐进式字幕**：`VoiceSessionHost` 新增 `PublishRecognized` 钩子，在结果排队等翻译之前就把它交给浮窗；
  浮窗用调用方给的关联 id 建一条「只有原文 + 说话人标签」的消息（`SubtitleCaption.Pending`），
  翻译完成后用同一个 id 调 `SubtitleCaptionBuffer.TrySetTranslation`，只重绘这一条（不新增、不重排、不改变滚动位置）。
- **失败与空译文**：翻译抛异常或返回空串时，该条解析成 `SubtitleTranslationState.Unavailable`，
  仍是只有原文的一条消息，行尾标注「（未翻译）」，不会留下永远空着的占位，也不会永远停在「等待翻译」。
- **既有行为不变**：200 条上限与丢弃最旧、暂停保持（暂停只挡新消息，已经显示出来的那条仍会被填完）、
  上翻不被拉回、「有新消息」提示、仅译文 / 译文 + 原文模式、OSC 行仍只发译文且照旧走 `TranslationOutputFormatter.TrimForOsc`。
  「仅译文」模式下译文未到达时显示原文，到达后原地换成译文（同一条消息）。
- **测试**：`SubtitleCaptionBufferTests` 新增 10 个渐进式用例（先出原文、译文填进同一条且条数不变、空/失败解析、仅译文过渡显示、
  未知 id 不动已有消息、按 id 读回、暂停中仍然完成、超出上限的待填消息不再可填）；`Invoke-V2Validation.ps1` 增加 D6 源断言
  （样式常量、无 `CornerRadius`、细分隔、随内容高度、渐进式链路、浮窗仍然只有一个 Button、失败必须解析而不是留占位）。


## D7 · 大字幕窗口的内容位置（贴底导致上方大片空白）

- **状态：已实施**（消息列表改为顶部对齐；高度跟随内容时窗口顶边固定、向下生长）
- **现象（用户截图）**：把字幕浮窗拉大后，消息仍然**贴在窗口底部**，上方留下大片空白，观感很怪。用户期望内容出现在**上半部分**。
- **原因**：消息列表是底部对齐（字幕惯例），且 D6 的“高度随内容收缩”在用户手动改过高度后会停止自动跟随，于是大窗口里内容一直贴底。
- **决定**：改为**顶部对齐**——消息从窗口上方开始排列、向下生长；内容超出窗口高度时照旧滚动并自动滚到底；
  「有新消息」提示、上翻不被拉回、暂停保持、200 条上限、高度随内容收缩（未手动改尺寸时）全部保持不变。

### 实施结果

- 消息列表改为**顶部对齐**（`SubtitleOverlayWindow.xaml`：`VerticalContentAlignment="Top"` 与 `CaptionMessages` 的
  `VerticalAlignment="Top"`）：第一条消息紧贴标题栏下方，后续消息向下生长；浮窗被拉大后内容留在上半部分，
  上方不再出现一大片空白。
- 窗口高度跟随内容时**顶边固定、向下生长**（`OverlayWindowController.ResizeKeepingTop`，取代 D6 的 `ResizeKeepingBottom`）：
  生长方向与消息一致，已经显示的句子不会被下一条消息推着往上跳；向下生长受显示器工作区下沿约束，不会顶出屏幕。
  持久化只存「用户自己的高度」，锚点由底边改成顶边（`ToStoredLayout` 不再反推 Y）。
- **不变的行为**：内容超出窗口高度时照旧滚动并自动滚到底（新消息仍可见）、上翻不被拉回、「有新消息」提示、
  暂停保持、200 条上限、仅译文 / 译文 + 原文、渐进式字幕（同一条消息先原文、译文后填）、
  「未手动改过尺寸时窗口高度随内容收缩」；D6 的 `_readerOwnsHeight`（用户手动改过高度后本次运行不再自动改高度）保持不变。
- **验证**：`Invoke-V2Validation.ps1` 新增 D7 源码断言（顶部对齐、不得再出现 `VerticalContentAlignment="Bottom"`、
  不得再出现 `ResizeKeepingBottom`、顶边固定的调用形状、`_readerOwnsHeight` 仍在），并在字幕渲染冒烟里
  灌入一条确定性字幕、把窗口拉高到 520px，用像素扫描断言首行文字落在客户区上半部分
  （旧的底部对齐会把这条消息压到客户区最下边）。冒烟字幕由 `VRC_TRANSLATE_SMOKE_CAPTION` 注入，
  仅验证脚本设置，正常启动不生效——真实字幕只在识别之后出现，而该冒烟不等语音；
  这条探针按「仅译文」呈现：原文行的浅蓝与浮窗禁止出现的强调色在像素上无法区分，白色译文可以，
  因此 D4 的「没有强调色像素」断言不需要放宽。

## D9 · 快捷键改不了；输入框里的「X」像文本、样式不对

- **状态：已实施**（三个快捷键改为「点击即录制」的按键捕获框：字段不再是 TextBox，那个「X」随之消失；
  合法组合按下即校验、即落盘，非法/冲突组合显示红框 + 一行说明；见文末「实施结果」）
- **现象（用户反馈）**：设置页里快捷键**改不动**；输入框右侧有一个「X」，看起来像文本的一部分，样式也不对。
- **初步诊断的实测结论**：
  1. **证实**：那个「X」就是 WinUI `TextBox` 模板里的清除按钮（元素名 `DeleteButton`）。它**只在输入框拿到焦点时出现**，
     是一枚没有按钮底色的裸字形，所以看起来像多出来的一个字符；点它会把已经输入的手势清空，而且**焦点并不离开输入框**，
     于是既不弹确认框也不给提示，只表现为“改不了”。WinAppSDK 1.8 的 `TextBox` **没有**关闭它的公开 API（反射证据见「实施结果」）。
  2. **修正**：手势解析本身没问题——`Ctrl+Alt+I` / `F7` / `Ctrl+F8` 都能被 `HotkeyBinding.Normalize` 接受（实测可落盘）。
     但“改不动”还有第二个真实原因：旧实现只在 `LostFocus`/回车时提交，而页面空白处**不可聚焦**，
     所以点了空白处或直接翻页时 `LostFocus` 根本不触发 → 无确认框、无提示、不写文件，翻回设置页还是旧值。
  3. 已排除项保持不变：全局快捷键是**轮询**读取设置的（`MainWindow.PollGlobalHotkeys` 每拍 `ReadHotkeys()`），
     所以不存在“需要重启才生效”的问题——本轮没有往“重新注册热键”方向改。
- **要求**：
  1. 去掉或替换那个「X」（清除按钮）——先**用反射确认 WinUI 版本里是否存在可关闭它的公开 API**（例如 `IsDeleteButtonEnabled` 之类），
     有就用；没有就换控件或改模板，**不要靠猜 API**；
  2. 让快捷键输入框的样式与其它输入框一致、看起来就是个输入框；
  3. 把“改快捷键”整条路径实测走通：输入合法手势 → 确认弹窗 → 落盘 → 轮询立即生效（含 `Ctrl+Alt+I`、`F7`、`Ctrl+F8` 等既有默认值）；
  4. 非法输入要有明确提示，不能表现为“默默改不动”。
- **影响面**：`Pages/SettingsPage.xaml(.cs)` 的快捷键三段（打开输入框 / 他人语音 / 自身语音）；不涉及识别、翻译、采集逻辑。

### 实施结果

- **交互（用户确认的方案 A「按键捕获」）**：三个字段由可编辑 TextBox 改为**只读按键显示区 + 点击录制**。
  点击（或聚焦后按 Enter/空格）进入录制态（高亮边框 + 「请按下快捷键…」），按下组合键即捕获、即校验、即落盘；
  Esc 取消并保持原值；Backspace/Delete 清空（清空后该功能确实没有快捷键，显示占位「未设置」）；
  只按修饰键不结束录制（显示 `[Ctrl] …`，松开修饰键会重绘）；非法或被占用的组合同样是**红框 + 一行说明**，
  **不会**默默恢复旧值。显示用键帽（每个键一个小圆角方块、间距 7px、沿用设置页既有色板），
  控件类型为 `Button`（自带清除按钮因此彻底不存在），并带 `AutomationProperties.Name`
  （打开输入框快捷键 / 他人语音快捷键 / 自身语音快捷键），Tab 可聚焦、Enter 可进入录制。
- **控件选择理由**：`Button` 天然可聚焦、Enter/空格可用、UIA 暴露 Invoke 模式（便于自动化验证与无障碍），
  而且不必为“看起来像输入框”写整套 ControlTemplate：外层 Border 用
  `{ThemeResource TextControlBackground}` / `{ThemeResource TextControlBorderBrush}`，与其它输入框同源；
  实测尺寸 765×57，与旧 TextBox（765×53）基本一致。桌面布局的编辑列由 220 加宽到 260，容得下最长组合的键帽。
- **反射确认的 WinUI API（WinAppSDK 1.8.260710003）**：
  - `Microsoft.UI.Xaml.Controls.TextBox` **不存在** `IsDeleteButtonEnabled` 一类属性：`Microsoft.WinUI.dll` 上枚举全部
    公开属性（含继承与接口）没有该名字，原生 `Microsoft.ui.xaml.dll` 字符串扫描也没有；模板部件名 `DeleteButton` 确实存在
    （与 `PlaceholderTextContentPresenter` / `HeaderContentPresenter` 等模板名相邻）——即“关掉它”没有公开开关 → 换控件。
  - 修饰键状态：`Microsoft.UI.Input.InputKeyboardSource.GetKeyStateForCurrentThread(Windows.System.VirtualKey)`
    → `Windows.UI.Core.CoreVirtualKeyStates`（程序集 `Microsoft.InteractiveExperiences.Projection.dll`）。
  - 录制键：`UIElement.PreviewKeyDown` / `PreviewKeyUp`（隧道事件，先于 Button 自身的空格/回车处理）。
- **顺带修掉的两个真实缺陷**：
  1. 录制期间全局轮询必须让位，否则按 `Ctrl+Alt+I` 会顺手把输入框浮窗打开；`MainWindow.PollGlobalHotkeys` 在
     `SettingsPage.IsHotkeyCaptureActive` 期间直接返回，捕获结束后再由 60ms 计时器确认按键已抬起才交还键盘——
     否则刚落盘的新组合会因为“键还按着”被轮询立刻触发一次。
  2. 清空 = 真的没有快捷键：`MainWindow.ReadHotkeys` 对空值不再回落默认值（非法值仍回落默认值），
     所以「未设置」不会偷偷保留一个还能用的热键。

  - `dotnet build VrcTranslate.sln -c Debug -p:Platform=x64` → 0 警告 0 错误；
  - `dotnet test VrcTranslate.sln -c Debug -p:Platform=x64` → 328 全绿（Core 63 / Application 116 / Infrastructure 149，只增不减）；
  - `tests/Invoke-V2Validation.ps1` → `V2 validation passed.`（含按新结构改写、保留原意的快捷键断言与紧凑布局 UIA 段）；

## D11 · 发到聊天框的那份文本要不要带原文（已实施）

- **诉求（用户提出）**：「原文要可以选择是否显示」——指的是**自身消息发往 VRChat 聊天框（OSC `/chatbox/input`）的那份载荷**，

  | 发送点 | 载荷 |

  | 自身语音 `SelfVoiceSpeechSession` | `译文 / 第二译文? / 原文`（总是带原文） |

- **落地**：
  - `TranslationOutputFormatter.FormatForChatbox(原文, 主译文, 副译文, includeOriginal)`：唯一的拼装入口，
    关掉时只去掉原文，仍然走 `TrimForOsc`（144 UTF-16 上限、不切断代理对）。
    一个刻意的例外：**一个译文都没有时（翻译失败/为空）原文照发**——否则关掉开关会让聊天框收到空串、
    把用户刚打的字擦掉，而不是显示它。
  - `OscChatboxSettings.ReadIncludeOriginal()`：读 `v2-user-settings.json` 的 `IncludeOriginalInOsc`，

  - 设置页「OSC 连接」卡片新增一行开关「OSC 消息带原文」（`osc-include-original-toggle`，
    On＝「译文 / 原文」、Off＝「仅译文」），与主机/端口一样**立即保存**；`TrySave` / `TrySaveHotkeys` 都带上这个字段，
    不会因为改快捷键或端口把它丢掉。
  - 输入浮窗的发送与预览共用同一个 `BuildChatboxText`，所以「实发文本」那行**所见即所发**；
    自身语音的发送走同一个 `FormatForChatbox`。自身语音页「最近一条」的原文/译文两行不动（那是给用户看的记录）。
- **验证（实跑，最终代码）**：
  - `dotnet build VrcTranslate.sln -c Debug -p:Platform=x64` → 0 警告 0 错误；
  - Core 单测新增 6 条（带原文＝原有断言不变、不带原文只留译文、无译文时回落原文、截断在上限内、
    批次入口同规则），全量测试只增不减；
  - 校验脚本新增源码断言：OSC 卡片必须有该开关、开关必须立即保存、保存值必须来自开关且默认走出厂常量、
    两个发送点都必须经过 `FormatForChatbox` + `ReadIncludeOriginal`（且不得再用旧的 `FormatForOsc(result)`）；
  - **真实报文验证**（新增 `Invoke-OscChatboxSmoke`，新增在隔离数据目录里跑：输入框 → 翻译 → OSC，
    脚本自己起一个 UDP 监听当 VRChat 端，解析收到的 `/chatbox/input` 报文字符串参数）：
    开关开＝输入那段文字出现 3 次（两个语言的译文 + 末尾原文）、关＝出现 2 次且**不以原文结尾**。

- **实施发现（写给后来者）**：
  1. OSC 客户端（`AppState._osc`）在应用启动时按 settings 里的 host/port 建一次，所以冒烟必须**先写端口再启动**；
     改端口后不重启是无效的（这是既有行为）。
  2. 那条 UDP 报文里字符串参数是「0 结尾 + 补齐到 4 字节」，**没有长度前缀**；冒烟解析必须以

## D15 · 中文/粤语也送去翻译：白等 100~600 ms，大模型还会改写原意（**已决定：不做**）

- **现象**：他人语音识别出的文本若是纯中文（含粤语书面语），当前代码照常调用翻译服务：
  - 机翻（腾讯 / 阿里通用 / 阿里专业）：**原样返回**，白等 99~108 ms；
  - 大模型（DeepSeek 413 ms / 小米 591 ms）：会**改写原文**，例如「开饭时间早上9点至下午5点。」
    → 小米「用餐时间为上午9点至下午5点。」（chrF2 64.6，用户看到的是被改过的句子）。
- **曾考虑的方案**：`含汉字 且 不含 假名(ぁ-ヿ) / 谚文(가-힣) / 拉丁字母(A-Za-z)` → 跳过翻译，直接复用原文。
  该判定在 27 条评测集 + 4 段音频上**全部判定正确**（见《实验报告-识别与翻译.md》§6.3）；
  若写成「含汉字就跳过」则会把日语/韩语/混说句误判，实测质量从 chrF2 78.6/86.7 **掉到 35.4**。
- **用户决定（2026-02）：不实现，保持「一律送翻译」**。理由：
  1. 实测延迟与语种关系不大——纯中文 99~108 ms（机翻）本来就在同一量级，省下的时间不值得为它加一条语言相关分支；
  2. 软件以后可能要扩展给其他语种的人使用，语言相关的特判越多越难改。
- **接受的代价（明确记录，避免以后当成新 bug 再查一遍）**：
  - 机翻档：中文条目**原样返回**，用户看到的字幕与对方原话一致，只是白等 99~108 ms；
  - 大模型档（DeepSeek 93.7 / 小米 64.6 chrF2）：中文条目会被**轻微改写**——例如「这个图好像有人掉线了」
    → DeepSeek「这张图里好像有人掉线了。」。**意思不变、措辞会变**。这个代价已写进引导页推荐文案，
    在意「字幕与原话逐字一致」的用户可按文案选机翻档。
- **状态**：**不做**（decision closed）。若将来真要加，§6.3 的判定规则可直接复用。
