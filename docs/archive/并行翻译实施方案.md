# 并行翻译实施方案

日期：2026-09-15 · 状态：**已实施**（提交 `947e14c`）· 决策已确认（见第 6 节）

配套阅读：`docs/翻译服务软件内实测对比.md`（实测数据与口径更正）、`docs/小米MiMo模型清单与选型.md`。

> **实施结果（实跑，同一套软件内 UDP 计时法，7 句）**

> | 提供商 | 改前中位 | 改后中位 | 变化 |
> | --- | --- | --- | --- |

>

## 1. 问题

自身消息（手动输入 / 自身语音）每句要翻**两个目标语言**（默认英语 + 日语），
`TranslationService.TranslateManyAsync` 现在是 **foreach 串行**：

```
英语 ────► 日语 ────► 格式化 ────► OSC      ← 现在：≈ 单次调用 × 2
```

实测印证：DeepSeek 单次约 660 ms → 软件内端到端中位 **1590 ms**；小米单次约 920 ms → 软件内中位 **2553 ms**。
**两家的延迟差只有约 1.4 倍，而"两次串行"是 2 倍** —— 所以先修架构，比换模型收益大。

## 2. 目标与非目标

**目标**

1. 一句多目标改成**并行请求**，用户感知延迟从"两次之和"降到约"最慢的那一次"；
2. 结果**顺序不变**（主译文仍是第 1 个目标、第二译文仍是第 2 个），下游格式化 / OSC / 预览一行都不用改；
3. 失败与重试语义**与现在一致**（同一个目标失败仍按路由的重试策略重试）。

**非目标**

- 不做"识别一句还没翻完就开始下一句"的**跨句并行**（见第 4 节）；
- 不改提供商、模型、提示词、OSC 格式、术语库行为。

## 3. 语音的翻译能不能并行？——能，而且和第 2 条是同一处改动

先看清现在有几条链路：

| 链路 | 调用 | 目标语言 | 并行有收益吗 |
| --- | --- | --- | --- |
| 手动输入框 | `AppState.TranslateSelfAsync` → `TranslateManyAsync` | 英语 + 日语 | ✅ 收益最大（用户盯着输入框等） |
| **自身语音** | **同一个** `TranslateSelfAsync` → `TranslateManyAsync` | 英语 + 日语 | ✅ **同样收益（用户提的问题，答案是肯定的）** |
| 他人语音字幕 | `Translator.TranslateAsync`（单目标） | 仅中文 | ❌ 只有一次调用，并行无收益 |

关键点：**自身语音走的就是同一个服务方法**，所以在 `TranslateManyAsync` 里改一次，
两条自身消息链路同时受益——**不需要为语音单独做一套**。

## 4. 语音链路里"并行"能到哪一步（把边界说清）

1. **句内并行（本方案做的）**：一句识别结果 → 英语 + 日语并发 → 等齐 → 发送。语音和手动输入都受益。
2. **跨句并行（本方案不做）**：`VoiceSessionHost` 有 `_processingGate` + `_processingResult` 闸门，
   **一个识别结果处理完才处理下一个**，这是刻意的（保证字幕顺序、避免短时间刷屏、避免把提供商的 RPM/TPM 打满）。
   改成流水线会让"字幕顺序"和"一次弹出两条"的老问题回来，**不在本轮**。
3. 因此语音路径的**请求总量不变**，只是把"一句两次串行"压缩成"一句一次并发"。

## 4.1 为什么不做"跨句并行"（补充说明，含真实数据）

用户追问：**"翻译器慢就慢在语音方面，文字慢一点无所谓"**——这个判断需要用数据核对。
先把语音链路的延迟拆开（代码里读出来的真实参数，不是猜）：

| 阶段 | 现状耗时 | 依据 |
| --- | --- | --- |
| 说完话 → VAD 判定句子结束 | **约 600 ms** | `SileroVadSegmenter` 默认 `MinSilenceDuration = 0.6 s`（能量门则是 `SilenceMilliseconds = 650`） |
| 识别（本地 SenseVoice） | 约 140 ms | 既有实测 |
| 翻译主目标 | 660 ~ 920 ms | 见《翻译服务软件内实测对比》5.1 |
| **翻译第二目标（串行）** | **再 660 ~ 920 ms** | `TranslateManyAsync` 的 foreach |
| 字幕/OSC 输出 | 数十 ms | — |
| **说完话 → 字幕出现** | **约 2.1 ~ 2.6 s** | 上列相加 |

**核对你的判断**：语音确实比文字慢——因为多了"VAD 等静音 600 ms"这一段；
但**两者的大头都是翻译，不是识别**（识别只占 140 ms / 约 6%）。
把翻译从"两次串行"改成"两次并行"，**语音和文字同时受益**：
说完话到字幕从约 2.1~2.6 s 降到约 **1.4~1.7 s**。

**那为什么不再往前一步做"跨句并行"（上一句还在翻就开始翻下一句）？**

不是不想，而是**收益小、代价明确**：

1. **回环链路本来就已经"跨句流水"了**：`OnResultReady` 在结果就绪时**立刻** `PublishRecognized`
   （字幕先显示识别原文，见 `VoiceSessionHost` 注释："识别比翻译快约 6 倍"），
   只有**翻译与输出**被 `_processingGate` 串行化。也就是说识别不会被翻译拖住。
2. **字幕列表是"只追加"的**：`SubtitleOverlayWindow` 的消息按到达顺序追加。
   如果两句同时翻，**后说的话先翻完就会先上屏，顺序颠倒**；要在中间插回一条，就得改列表结构 +
   决定"多晚算太晚"，这正好会把用户早前投诉过的"一次弹出两条""顺序乱"重新引回来。
3. **真正的瓶颈是"翻译相互排队"**：连续说话时，第 2 句的翻译要等第 1 句翻译（两次调用）做完。
   但这个排队长度**在句内并行之后就已经减半**；再跨句并行只能再省"第 2 句的等待"，
   而它在实际对话里通常被"下一句还在说"的时间盖住。
4. **成本与限流**：跨句并行意味着同一时刻最多 4 个请求在飞（2 句 × 2 目标），
   命中提供商限流的概率上升，字幕抖动更难看。

**结论**：本轮先做"句内并行"（收益确定、风险低、两条链路都受益）。
跨句并行留作后续可选项——如果做完句内并行你还觉得连续说话时跟不上，我们再单独评估
（前置条件是字幕列表支持"按句序插入"）。

## 5. 设计

**改动点只有一个方法**：`src/VrcTranslate.Application/Translation/TranslationService.TranslateManyAsync`

```
现在：foreach (target in targets.Languages) results.Add(await TranslateAsync(targetRequest));
改后：每个 target 先建好 targetRequest
      → 并行执行（Task.WhenAll）
      → 按目标顺序放回结果数组（索引固定，顺序天然不变）
      → 仍用 TextTranslationBatchResult(request, targets, results) 返回
```

- **顺序保证**：`Task.WhenAll` 返回的数组按输入顺序，`Results[i]` 永远对应 `targets.Languages[i]`，
  所以 `Primary` / `Secondary` / `FormattedText`（"译文1 / 译文2 / 原文"）**一个字都不用动**。
- **并发规模**：并发度 = 目标语言数（当前最多 2，`TranslationTargetSet` 只允许主 + 副），
  不需要引入信号量；提供商的 RPM/TPM 配额（小米 100 RPM / 10M TPM、DeepSeek 2500 并发）远高于此。
- **取消与超时**：沿用外层 `CancellationToken` 与每个请求的 `RetryPolicy.RequestTimeout`，不新增超时语义。
- **重试**：每个目标的失败重试仍走各自 `TranslateAsync` 内部已有的重试循环，互不影响。

## 6. 需要你拍板的决策（重点）

### 决策 1：一个目标失败、另一个成功时，怎么办？

现在：**任何一个失败 → 整个 `TranslateManyAsync` 抛异常**（`Task.WhenAll` 默认也会这样），
表现是输入框显示"发送失败：… · 按 Enter 重试"、OSC 不发。

可选：

- **A. 保持"全有或全无"**（不改语义，最小风险）：一个目标失败就不发送，让用户重试。
- **B. 部分成功就发部分**：例如英语成功、日语失败 → 只发"英语译文 / 原文"。
  但注意 `TextTranslationBatchResult` **强制要求结果数 == 目标数**，且 `TextTranslationResult` **不接受空译文**，
  所以 B **必须改 Core 的契约**（允许空结果）→ 会影响 `FormattedText`、预览、OSC、录音页显示，改动面大。
- **C. 折中（我推荐）**：**失败的那个目标按"没有第二语言"处理**——
  第二次目标的失败不再让整句失败，而是把结果集收缩成只剩成功的目标（复用现有 `TranslationTargetSet("en-US")` 单目标路径），
  用户看到"英语译文 / 原文"；**主目标（第一个）失败仍然整句失败**，因为它是主译文，没有它就没什么可发。

### 决策 2：等齐再发，还是先发主译文？

- **等齐再发**（我推荐）：一条消息一次发完，聊天框不会出现"先英语、再补日语"的两次刷新；
  代价是等到最慢的那个（≈ max 而非 sum，已经比现在快一倍）。
- **先发主译文、到了第二语言再补发**：更快出字，但聊天框会刷两次，且 OSC 有频率限制，**不推荐**。

### 决策 3：并发上限要不要做成设置项？

- **不做**（我推荐）：并发度 = 目标数（≤2），没有可调的必要，少一个设置项。
- 如果你希望将来支持 3 个以上目标语言，再加一个"最多同时 N 个"的常量即可。

## 6.1 顺带发现：语音还有一个独立的 600 ms 延迟（可选优化）

VAD 判定"这句话说完了"要等 **600 ms 静音**（`SileroVadSegmenter.MinSilenceDuration = 0.6`）。
这是**独立于翻译**的一段时间，而且它在整条链路的**最前面**——用户说完话后先白等 600 ms 才开始识别。

- **调小的收益**：直接砍掉一部分"说完话到出字幕"的延迟（例如 600 → 350 ms 可省 250 ms）；
- **调小的代价**：说话中间停顿稍长就会被切句（"我去了……那个地方"会变成两条），
  这是用户在 D6 时期抱怨过"一次弹出两条"的同一类问题；
- **建议**：**本轮不动**。如果句内并行做完后你还觉得"反应慢半拍"，我们再单独做一次实验：
  用同一段录音在 350 / 450 / 600 ms 三档下对比"切句正确率 vs 延迟"，用数据决定，而不是拍脑袋。

## 7. 验证方案（改完怎么证明它真的并行、真的更快）

1. **单测（Application）新增**：
   - **并行证据**：用一个"两次调用各 sleep 300 ms"的假提供商，断言整批耗时 **< 450 ms**（串行会是 ≥600 ms）；
   - **顺序不变**：断言 `Results[0]` 仍是主目标、`FormattedText` 仍是"英语 / 日语 / 原文"（现有两条用例继续通过）；
   - **失败语义**：按决策 1 选定的规则加用例（全失败 / 主失败 / 副失败三种组合）；
   - **单目标零影响**：只有一个目标时不得引入额外等待。
2. **校验脚本**：加一条静态断言，要求 `TranslateManyAsync` 必须并行（禁止退回 foreach + await）；
   并保留"结果顺序必须与目标顺序一致"的既有断言。
3. **真实软件实测（沿用 D11 那套 UDP 抓包方法）**：
   同一批 7 句、同一提供商，对比**改前 / 改后**的端到端中位延迟，预期 DeepSeek 从 ~1590 ms 降到 ~900 ms 量级；
   结果写进 `docs/翻译服务软件内实测对比.md` 的新增小节（带对比表）。
4. **回归**：全量测试（当前 345 条只增不减）+ `Invoke-V2Validation` 全绿；自身语音与输入框两条链路各手动跑一次。
