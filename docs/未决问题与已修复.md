## 2. 已完结项摘要

- **D1**：他人语音长对话改为消息条滚动列表——每条一句、可上下回看、新消息自动滚到底；不持久化、无清空入口。
- **D2**：术语库卡片删掉保存按钮与重复「启用」文字，标题行与其它卡片对齐；补齐删除后的自动保存触发点。
- **D3**：F7 成为「他人语音 → 字幕」总开关，语音页「打开字幕」按钮删除；任何启停路径结束后窗口可见性 = 识别运行状态。
- **D4**：字幕浮窗去掉易误会的「麦克风」标识，字幕水平居中。
- **D5**：根因是 `SubtitleSpeechSession` 把他人语音译文写进共享预览状态；已改为独立通道。
- **D6**：字幕浮窗样式改造 + 渐进式字幕（分段渐进上屏）落地。
- **D7**：大字幕窗口消息列表改为顶部对齐，高度跟随内容时窗口顶边固定、向下生长。
- **D8**：DeepL / Google 两个提供商删除；老配置回落到仍可用的档案。
- **D9**：三个快捷键改为「点击即录制」的按键捕获框（X 图标随之消失）；清空后的快捷键不再在其它页面回落默认值。
- **D10**：输入浮窗默认宽度按 DPI 换算，不再出现高 DPI 下过窄。
- **D11**：手动输入和自身语音的 OSC 载荷可选择是否带原文；他人语音不受该开关影响。
- **D12**：小米 MiMo 接入；2026-10-19 将默认从 `mimo-v2.5` 迁到 `mimo-v2.6-flash`（V2.5 于 2026-10-21 10:00 下线），旧档案/路由自动迁移；ASR 明确不接（云 ASR 非流式、只支持中英、丢说话人区分，纯亏）。V2.6 Flash 复核见《实验记录》§5.5。
- **D13**：腾讯/阿里翻译链路修复三个必填/签名问题（缺 `ProjectId`、签名覆盖的 content-type 与实际发送的不一致、缺 `FormatType`），此后真实密钥端到端可用。
- **D16**：**关闭为「直喂实验的假象」**——原实验绕过 VAD 把 18.4 s 整段喂给识别器，暴露的是识别器单段上限；软件真实路径先经 VAD 切段（生产同款参数与 512 块长），逐段识别**三语全部恢复**（中文 + 英语完整句 + 韩语整句），且每段比直喂更完整。VAD 强切损耗实测在案（每次 80~84 ms、预热 80 ms），真实语音从未触发强切（最长自然段 5.46 s），**不修**。回归防线 `SileroVadSegmenterTests.A_continuous_signal_is_force_cut_at_12s_without_eating_speech`。
- **D17**：偶发失败的根因是**测试断言与生产异步之间的间隙**（`InstallAsync` 先 `SetState`，旧采集的 Stop/Dispose 在之后的 await 里才完成），非进程枚举竞争。修复只动测试：等待条件加强到「换流完全落地」（`InstallSettled`）、`changes` 读侧加锁、假采集计数改 `Interlocked`/`volatile`、超时可选（本测试 10 s）。验收要求**全量并行**连跑（单跑不会饥饿，证明不了）——**连跑 5 次全绿**，生产代码零改动。
- **D18**：输入框底部截断——默认高度 `150 → 200` DIP（漏算标题栏与状态行）；已保存过矩形的用户拖高即可，不用清数据。
- **D19**：原问题把性能瓶颈误写成“识别等待翻译”，此前将其作废是对的；但当时据此写出的“识别结果都会进入 `_processingGate` 排队”是错的——事件入口另有 `_processingResult` 短路，会直接丢掉后续结果。这个新发现按 D29 修复。
- **D20**：**结论反转**——用**真实双人播客**实测，换人切分**确实有效**（15.21 s 段切成 3 片、声纹标签分开）；此前「恒为 0 段」的判断只在自拼接的合成音频上成立，**已作废**。同时发现**头尾预判有害**：36 个长段里 **11 段（38%）的真换人被预判挡掉**，而预判为 False 的段 pyannote 只要 33~233 ms——**没省到钱**。素材与脚本见 [能力边界与决策记录.md](能力边界与决策记录.md) §6.4。
- **D25/D26/D27**：删掉头尾预判（`ISpeakerChangeSuspected` 及其专用辅助一并删除）、边界变更点改「夹紧到 `[minPart, total-minPart]`」并加「两片放不下取中点」兜底、`MinimumSplitSeconds` 4.5 → 3.0 s（依据：2.5 s 片只有 6/24、3.0 s 片有 8/20 能给出换人点）。新增 8 条 `SpeakerSegmentSplitter` 单测。**效果**：同一素材（播客前 8 分钟、58 个 VAD 段）成功切分从约 **13 段 → 29 段**，切分耗时中位 34 ms、最大 1.26 s（不再有预判开销）。验证：全量 **389 条**测试连跑 3 次全绿。
- **D31**：两件事合并成一项。① 主界面没有锁定浅色主题，Windows 用深色应用模式时未显式设前景色的文字全变白，而表面仍是硬编码浅色（白字白底）；App.xaml 固定 `RequestedTheme="Light"`，两个深色浮窗保留 Dark。② 他人语音“有声音、窗口在、永远没字幕”：审计出 VAD 异常被采集回调吞掉、识别错误只弹在页面最底部且标题误导、fire-and-forget 异常无人观察、字幕流 Paused 静默丢弃、模型只查最小体积（239 MB 截断到 120 MB 仍报 Ready）、字幕窗首次显示可能撞上未激活的空白 XAML 岛。本版加“启动自检 + 运行期兜底 + 精确模型校验 + 有界诊断日志 + 浮窗空白自救”，下一次安装要么直接恢复，要么在第一次运行内报出卡在哪一段。详见 §4。
- **D32**：连续人声/播客超过 12s 时，Silero VAD 的 `MaxSpeechDuration=12s` 与备用保护 `SilentVadFallbackWindow=12s` 撞车：保护在 VAD 强制切段前把 VAD 换成能量门限，VAD 正在收尾的段被丢掉，前 12s 无字幕并弹“VAD 不可用”。1.1.2 修复保护窗口 16s/硬上限 24s + `IsSpeechDetected` 活跃保护；1.1.3 用测试视频复核后把应用 VAD 上限降到 6s（原生实测段长仍会到 9.8s，但 53.5s 目标段从 9.9s 缩到 7.3s），保留 16s 保护。文案改为“长时间未产出语音段”；新增 pending 场景单测；换人切分（D29）仍靠段后声纹切分，实测 50.07–60.00s 段在 52.05s 切成两段。
- **D33**：说话人设置卡片此前把 SpeakerIdentity record 直接 ToString() 显示成 JSON 字段；改为 DisplayText（A · 未命名 / A · 小明）。新说话人由识别线程创建，页面没有事件所以必须刷新；新增 SpeakersChanged 事件和 UI dispatcher 订阅。容量改为命名库 100、未命名会话 16；命名后进入命名库、不再占会话名额；10 分钟无语音的未命名会话声纹自动释放，16 个全活跃时新声音标“未知”不硬踢。说话人标签改为常驻开启，去掉开关；同一 SpeakerLabel 连续消息使用同一颜色左侧竖条、去掉分隔线、组首只显示一次标签，不做文本合并。字幕自动滚动方面，程序自己的 ChangeView 会被 ViewChanged 误判为用户上滚，导致下一条不再跟随；加程序滚动保护窗并在布局后二次校正，按钮文案改为“最新消息”。
- **D34**：字幕偶尔停止跟随，长消息/多组长对话最容易复现。根因不是单一 250ms 保护窗：长消息撑高内容、窗口高度适配、翻译回填、内容模式切换和连续快速消息都会让 ScrollableHeight 在 ChangeView 之后继续变化，ViewChanged 被误判成用户上滚；一次校正也不够。现在显式区分程序滚动、内容/布局变化和用户手势：程序滚动用 generation 取消过期重试，最多 5 次布局校正；内容高度变化不翻转跟随状态，只安排校正；只有用户滚轮/拖动/触摸/PageUp/PageDown/Home/End 才关闭跟随。窗口尺寸变化、窄版重排、翻译回填都会触发校正。
- **D35**：声纹匹配不再只看“最高分过阈值”。`SpeakerMatch` 增加 second/margin/reason；最高分过阈值但 margin < 0.06 时不切人，优先保持上一句，否则标不确定；阈值附近灰区不新建幽灵说话人。`LocalSpeakerIdentifier` 对少于 1.5 s 或 RMS < 0.004 的片段不提取、不更新；`LocalSpeechCaptureSession` 记住上一说话人和段内局部 cluster，短段/歧义时沿用。`SpeakerDiarizationSplitter` 返回段内 local speaker id，但只作为先验，强全局匹配仍优先；local id 在每个 VAD 段开始时重置，避免跨段 id 碰撞。字幕右键“不是此人”回滚该说话人最后一次观测并改标未知；命名时样本少于 2 次提示补充。阶段 3 换模型不做。

- **D37**：用户指出短句明显换人却无标签，实际是短句被并进上一人，不是正常延续。修复两层：① 同一段内同一 local cluster 的多个短 span 拼接后只算一次声纹，1s 级短句也能从整个 cluster 识别，避免逐句时长不足被跳过；② 字幕不再隐藏同一人的标签，每条都显示 A/B/名字；确实无法识别时显示灰色“未知”，不再用空白冒充延续。`AttachSpeaker` 无 cluster 时才使用逐 span 匹配；cluster 结果为空/不确定时直接标未知，不继承旧说话人。

## 4. 已修复的方案全文（D28~D31，实施记录含内）

### D28 · 他人语音结果错误进入 OSC → 已二次修复

**实施记录**：`16ebd2a` 只阻止了 echo、失败和同文结果进入 OSC，但仍把“有效译文”发到游戏。用户再次确认产品契约后，管线进一步收紧：`OtherPlayerCaptionPipeline` 删除 `IChatboxOutput`、具体输出字段和构造参数，Desktop 同时删除 `AppStateChatboxOutput`。他人语音管线现在从类型上只能翻译并更新 `IOtherPlayerSubtitleSurface`，无法调用 OSC。

#### 已确认根因

最初的 `SubtitleSpeechSession` 会发送 `translated.TranslatedText`；第一轮修复仍保留了“有效译文可以发送”的职责。无论载荷是原文还是译文，这都违背“识别他人语音只用于本地字幕”的产品边界。

历史上原文出现还会被三种情况放大：默认 `local-test / echo` 原样返回、配置恢复前误用临时 echo 路由，以及真实服务返回同文结果。

D11 的“OSC 消息带原文”只适用于**手动输入和自身语音**。他人语音的识别原文和翻译结果都只进入本地字幕浮窗，不发送到 VRChat Chatbox，也不新增用户开关。

#### 修复方案

1. 他人语音结果由 Application 层 `OtherPlayerCaptionPipeline` 处理；管线只依赖翻译端口和 `IOtherPlayerSubtitleSurface`，不得声明 Chatbox/OSC 输出端口。
2. Desktop 组合根在提交工作项前等待 `AppState.Ready`，一次性取得本句的路由快照并交给管线；Application 层不反向依赖 Desktop。运行中切换默认档案只影响下一句。
3. 真实翻译成功时将完整译文填入本地字幕，不使用 OSC 的 144 UTF-16 长度裁剪；echo、失败、取消、空译文或同文结果保留原文并结束等待态。
4. 手动输入和自身语音继续保留第一译文/第二译文/原文格式及“OSC 消息带原文”开关，不受本次修改影响。
5. 静态架构测试禁止 `OtherPlayerCaptionPipeline` 出现 `IChatboxOutput`、`SendChatboxAsync` 或 `TrimForOsc`，并禁止 Desktop 恢复 `AppStateChatboxOutput`。

#### 验收矩阵

| 输入结果 | 本地字幕 | OSC |
| --- | --- | --- |
| 真实译文且不同于原文 | 原文先出现，随后补完整译文 | 0 次 |
| `local-test / echo` 或未配置真实服务 | 显示原文 | 0 次 |
| 翻译失败、超时、取消或空译文 | 保留原文并结束等待态 | 0 次 |
| 服务返回与原文相同 | 显示一份文本，不重复 | 0 次 |

### D29 · 多人轮流/快速接话时字幕被静默丢弃 → 已修复（`16ebd2a`）

**实施记录**：`_processingResult` 丢弃规则已删除；每句分配单调 `captionId` 并同步发布 Pending 字幕；`Channel` 工作队列 + 会话 worker，翻译并发 2、按 `captionId` 顺序回填；单句失败只终态该句；队列满载给终态 + 诊断事件；每次 Start 新 generation+CTS+队列，Stop/Restart/音源边界（VRChat 进程切换）结束写端、取消并等待 worker，旧 generation 不回填。最终验证又发现相邻结果同时完成时，账本虽在锁内排序，写入提交队列却在锁外，后一个线程仍可能先写入；现已把排序与入队合并到同一临界区，并增加 10 轮、每轮 32 句的并发完成压力测试。`SpeechCaptureProcessingOptions` 把 `SplitAtSpeakerChanges` 与 `AttachSpeakerLabels` 解绑：他人语音固定切分、标签开关只控制命名、自身语音两者全关，切分模型不可用/抛错降级整段。

#### 已确认根因

这不是一个问题，而是两个会叠加的实现错误：

1. `VoiceSessionHost.OnResultReady` 在 `_processingResult == true` 时直接 `return`。上一句翻译的 195~700 ms 内，下一句不会进入 `_processingGate`，而是被静默丢弃。pyannote 将一个 VAD 段切成 A/B/C 三片时，第一片开始翻译后，后两片尤其容易命中这个分支。
2. 提交账本在锁内按 `captionId` 取出结果，却在释放锁后写入 `Channel`。A/B 几乎同时完成时，B 线程可能先写入，字幕实际按 B/A 回填。
3. `LocalSpeechCaptureSession.PlanSpeakerSpans` 用 `SpeakerLabelsEnabled` 同时控制“按换人点切音频”和“显示说话人名字”。用户关闭标签时，已经由真实双人录音证明有效的换人切分也被关闭；默认行为因此最不适合多人对话。

#### 修复方案

1. 删除结果入口的 `_processingResult` 丢弃规则。每个识别结果先分配单调递增的 `captionId` 并立即发布 Pending 字幕，再写入该次会话专属的有序工作队列。
2. 用 `Channel` 和会话 worker 取代“事件里启动未跟踪任务 + 布尔锁”。翻译最多并发 2 条，提交阶段按 `captionId` 排序；慢请求不会阻塞识别，快请求也不会越过前一句回填字幕。
3. 单条失败只将对应字幕结束为“无译文”，随后条目继续处理。队列若达到内部上限，必须把对应字幕明确结束为不可用并记录诊断，禁止静默丢句；不增加用户配置。
4. 每次 Start 创建新的 generation、`CancellationTokenSource` 和队列；Stop、Restart、音源 generation 变化时完成写端、取消并等待 worker。旧 generation 的翻译返回后不得回填字幕。
5. 增加会话级 `SpeechCaptureProcessingOptions`，至少拆成 `SplitAtSpeakerChanges` 和 `AttachSpeakerLabels`：他人语音固定开启前者，后者仍跟随用户的标签开关；自身语音两者均关闭。
6. 换人切分模型不可用或执行失败时降级为整段识别。它只改善先后说话，不承诺恢复真正同时重叠的第二路声音。

#### 自动测试要求

1. 人为阻塞 A 的翻译后连续送入 A/B/C：三条 Pending 字幕必须立即出现，最终一条不少；翻译按 C/B/A 完成时，字幕仍按 A/B/C 回填。
2. B 翻译失败不能阻塞 A/C；队列满载时每个已发布字幕都有明确终态。
3. Stop、Restart 和音源切换后，旧任务不得回填新会话或发通知。
4. 标签关闭时仍调用换人切分，但不调用声纹命名；标签开启时，两个测试说话人必须得到不同身份，文本、身份和 `captionId` 一一对应。
5. 自身语音不调用多人切分；切分模型不可用或抛错时仍产生整段字幕。
6. D28 由管线无 OSC 依赖的架构门禁固定；自身输入、自身语音各保留端到端 OSC 回归测试。
7. `Invoke-V2Validation.ps1` 禁止他人字幕管线重新出现 Chatbox/OSC 类型与调用。
8. 并发压力测试同时放行 32 句翻译并连续运行 10 轮，回填顺序必须始终与 `captionId` 一致。

### D30 · 快捷键开启字幕后窗口未回到顶层 → 已修复

**根因**：窗口创建时虽然设置了 `OverlappedPresenter.IsAlwaysOnTop`，但隐藏、最小化或被其它窗口覆盖后，重新调用 `AppWindow.Show(false)` 不能可靠地把现有 HWND 放回 Windows 的最上层窗口带。

**修复**：字幕通过快捷键显示或从最小化恢复后，调用原生 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_SHOWWINDOW)`。窗口恢复到最上层，但不夺走 VRChat 的键盘焦点，也不改变用户保存的位置和大小；兼容显示路径使用同一逻辑。

**回归测试**：原生窗口冒烟先用 `HWND_NOTOPMOST` 主动撤销字幕窗置顶，再通过真实快捷键重开并检查 `WS_EX_TOPMOST` 已恢复；前台窗口断言同时保证字幕出现后当前前台窗口不变。


### D31 · 系统深色模式白字白底 + 他人语音字幕窗永久空白 → 已修复

#### 现象

- 别人的机器（Windows 应用模式 = 深色）上，主界面大量文字变白、背景仍是浅色，标签直接消失；字幕浮窗本身是深色底、显式白字，不受主题影响。
- 同一台机器上他人语音正在识别、有声音输入，但字幕窗从头到尾一条消息都没有。

#### 主题根因与修复

WinUI 默认跟随系统应用模式；`App.xaml` 没有 `RequestedTheme`，而所有页面表面都是硬编码浅色。深色模式下未显式设置 `Foreground` 的 `TextBlock` 取白色 `TextFillColorPrimaryBrush`，于是白字白底。输入/字幕浮窗各自强制 Dark，所以只有主界面中招。

修复：`App.xaml` 固定 `RequestedTheme="Light"`；两个浮窗保留各自的 Dark；状态横幅与关键标签补显式前景色；验证脚本断言主题。

#### 空字幕：代码审计发现的静默点

1. `LocalSpeechCaptureSession.OnSamplesReady` 的 `_segmenter.Append` 异常被采集回调的 `catch { }` 吞掉：电平照动、无字幕、无报错。
2. `RecognizeSegmentAsync` 的异常只进语音页最底部的 InfoBar，标题还叫「语音采集已停止」。
3. `DispatchRecognizedAsync` 是 fire-and-forget，异常无人观察。
4. `SubtitleOverlayWindow.AddCaption` 在流仍 Paused 时静默丢弃。
5. `LocalSpeechModelManager.GetStatus` 只查最小体积：239 MB 的模型截断到 120 MB 仍报「已就绪」；且随包副本永远优先，用户点「安装模型」下载的好副本被遮蔽。
6. 字幕窗在启动时创建后立刻隐藏，首次显示可能撞上未激活窗口的空白 XAML 岛。

#### 修复

- **启动自检**：随包 5.6 s、16 kHz 单声道语音样本，后台跑 模型加载 → VAD → ASR；结果写 `caption-diagnostics.log`、语音页顶部红色 InfoBar、字幕窗标题（自检失败）。自检同时完成模型预热。
- **运行期兜底**：VAD 异常或连续 12 s 有声音却无段 → 自动切能量门限并回放当前音频块；字幕流与窗口可见性解耦（Show 恢复、Hide 暂停）；说话人 span 夹紧；所有 fire-and-forget / 入窗失败写日志。
- **模型完整性**：随包文件按发布精确大小校验；损坏的随包副本不再遮蔽下载副本；两者都坏时明确提示重新解压或重新下载。
- **诊断**：`data\caption-diagnostics.log`（400 行上限、只记技术字段）：OS Build / DPI / ANSI 代码页、主题、模型状态、自检三段、音频 RMS、VAD 段数、识别条数、字幕 submit/fill/丢弃原因、浮窗矩形/客户区、异常全文。
- **浮窗空白自救**：显示后 400 ms 检查内容区；为 0 则 `UpdateLayout` + 激活一次并记录。

#### 验收

- 全量 **410 条**测试通过（新增自检 5 条、精确体积 3 条、分段器回退 1 条）。
- `Invoke-V2Validation.ps1` 全绿：静态主题/自检断言、翻译交互冒烟、六页冒烟、原生浮窗 4 段、字幕渲染与顶部对齐、OSC、语音总开关。

- 移除模型后截图：顶部红色自检失败 InfoBar + 诊断日志路径，主界面全部文字可读。
- 外部用户空字幕的**确切触发点**仍待其回传 `caption-diagnostics.log`；本版保证要么直接恢复，要么在第一次安装内报出卡在哪一段。


### D23 · 当前随包技术栈能否用音源分离救「重叠丢一路」→ ❌ 不可行（实验已完成）

| 检查项 | 结果 |
| --- | --- |
| sherpa-onnx 自带分离模型能拆两个人声吗 | ❌ 不能。只提供 **Spleeter / UVR**，都是**音乐伴奏分离**；两路都是人声时不会拆开 |
| sherpa-onnx 分离接口本机可用吗 | ❌ 用官方 `spleeter-2stems` 模型报 `ComputeStft: Invalid channel 1. Max 1`（1.13.8） |
| 换人声专用模型（SepFormer） | ⚠️ 需 Python + PyTorch 栈（与「纯 .NET + onnxruntime」冲突），无 ONNX 版本可嵌入 |
| 就算能分离，延迟可接受吗 | ❌ 按训练块推理（块长 4 s）⇒ 字幕至少晚**数秒** |

**结论：当前版本不做**，维持「保一路」；这不是“所有未来技术路线永久不可行”。重启条件见 [能力边界与决策记录.md](能力边界与决策记录.md) §6.3、§9。

### D24 · 是否引入流式识别 → ❌ 已否决（代价超过收益）

它是 `[批式固有]` 两条（字幕疏、文本大块）**唯一**的解法，但**代价超过收益**，决定不做。

| 常见误解 | 核查结果 |
| --- | --- |
| 「流式只能走云端」 | ❌ 本机 sherpa-onnx 1.13.8 已导出 `OnlineRecognizer` / `OnlineStream`；模型侧有日语 ReazonSpeech 流式、中英双语 streaming zipformer |
| 「本地流式要换技术栈」 | ❌ 用 sherpa-onnx 自家流式，C# + onnxruntime 一行都不用改 |

**真理由**：① 流式模型**一模型一语种或双语**（未发现中英日韩四语合一），而场景是「语种不确定、随时换」；② 准确率先退一步；③ 切成短句**反而丢掉翻译上下文**；④ CAM++ 说话人标签要按时间轴重做；⑤ 出字即最终，无法二次修订。
**成本账**：识别上云按音频时长计费，典型 **≈110 元/月**（每天 2 小时），是翻译费（≈3 元/月）的 **13~143 倍**。

完整记录（含实价表与三条重启前置条件：隐私 / 计费上限 / 国内可选性）见 [能力边界与决策记录.md](能力边界与决策记录.md) §7。

## 5. 已实施项：D45 腾讯云实时语音识别（流式）

> 状态：**已实施**。语音页提供本地 / 腾讯云实时 / 腾讯云按句三种选择；实时与按句都只影响其他玩家，默认本地。
> 本节记录实际实现和已知取舍，不再写成“下一版”。

### 5.1 边界

- 只对**其他玩家（系统回环）**生效；自己的麦克风始终本地 SenseVoice。
- 默认关闭；用户主动填 AppID/SecretId/SecretKey 并选择语言后才启用。
- 沿用现有 DPAPI 存储与“云端失败自动回退本地”。
- 实时是**可选引擎**，不替换本地默认路径；D24 对本地流式改造的否决不变。

### 5.2 为什么不能把按句 REST 改成实时

| 项目 | 一句话识别（当前） | 实时语音识别 |
| --- | --- | --- |
| 协议 | HTTPS JSON，一次一段 WAV | WebSocket，持续推流 |
| 结果 | 请求返回后一次性给整句 | `slice_type=0/1/2`，先非稳态、后稳态 |
| 延迟 | VAD 等静音 + 上传 + 识别 | 边说边识别，端点后稳态结果更快 |
| 计费 | 按成功调用次数 | 按识别音频秒数 |
| 语言 | 每次请求选引擎 | 建连时选引擎，不能中途换 |

结论：实时**必须改音频链路**，不是换一个 URL 或参数。

### 5.3 采用“回环推流 + 云端稳态句 + 本地声纹”的混合架构

```text
Windows 回环采集（16 kHz / float32）
  └─ PCM16 环形缓冲（最近 60 秒）
        └─ 每 200 ms → 腾讯云实时 WebSocket
              ├─ slice_type=1：忽略（不做半句预览）
              └─ slice_type=2：稳态句 + start_time/end_time
                    └─ 按时间戳回查环形缓冲
                          └─ 本地 CAM++ 贴说话人标签
                                └─ 现有字幕/翻译管线
```

关键取舍：

- **不追求“逐字上屏”**：只把稳态结果送翻译，避免半句被翻译、字幕抖动。
- **说话人标签仍由本地做**：实时接口不给英/日/韩的说话人分离；用 `start_time/end_time` 从环形缓冲取同一段音频算 CAM++。
- **换人拆句**：支持词时间戳的引擎会把整句按本地换人点拆成多条字幕，各贴各的标签；韩语/多语种没有词时间戳，仍按整句一个标签，这是已知边界。
- **本地只在回退时启用**：实时正常时不跑本地 VAD；连接失败后改用能量分段 + SenseVoice，保证字幕不断。

### 5.4 会话生命周期

1. 启动他人语音 → 建一条 WebSocket；`voice_id` 每次新建，断线必换。
2. 音频按 1:1 实时率发送；发送队列有界，队列满视为网络跟不上，回退本地。
3. `slice_type=2` → 取时间戳 → 贴标签 → 入现有管线；`slice_type=1` 直接忽略。
4. 音源切换（VRChat 退出/回系统混音）→ 关旧连接、清缓冲、换新 `voice_id`，旧结果不得回填。
5. 连接失败/鉴权失败/额度不足 → 一次提示 → 本会话余下时间走本地能量分段 + SenseVoice，避免每句重试。
6. 用户停止 → 发送结束帧、等最后一帧稳态结果（最多 2 秒）→ 关闭。

### 5.7 验收

- 固定日语/英语/韩语各 10 分钟真实回环：稳态结果、断线回退、音源切换、停止收尾都通过。
- 与按句版同一素材对比：端到端“说完 → 字幕”延迟应下降；识别字准不下降。
- 断网/错密钥/额度耗尽：只提示一次，之后本会话走本地，不反复重连。
- 计费：只对实际发送的音频秒数计费；UI 估算与腾讯云账单口径一致（以账单为准）。
- 隐私：默认关闭；未启用时零外发；启用时只上传其他玩家音频。
