## 一、D17：`VrchatProcessSwitchingTests` 偶发失败（观察中）

### 1.1 根因（已定位到行）

旧记录猜测"并行套件并发占用进程枚举/计时窗口"。**读完代码可以排除**：该测试是全脚本的
（`ScriptedVrchatProcessSource` 假进程源 + `FakeLoopbackCaptureFactory` 假采集 + `ScriptedDelay` 手工放行），
从头到尾不碰真实进程枚举。真正的竞态在**测试断言与生产代码的异步间隙**：

`AdaptiveLoopbackAudioCapture.InstallAsync`（`src/VrcTranslate.Application/Speech/AdaptiveLoopbackAudioCapture.cs:393`）的执行顺序：

1. `SetState(新状态)` —— 测试的 `UntilAsync(() => coordinator.SourceKind == …)` 在**这里**就能返回；
2. `RaiseSourceChanged(boundary)`；
3. `await StopQuietlyAsync(previous)` —— 旧采集的 `StopCount` / `DisposeCount` 在**这里之后**才变成 1。

而测试在 `UntilAsync` 返回后**立刻**断言 `factory.Created[0].DisposeCount == 1`
（`VrchatProcessSwitchingTests.cs:50-51`），第二半段同样断言
`Assert.All(factory.Created.SkipLast(1), c => c.DisposeCount == 1)`（`:72`）。

单独跑时第 3 步几乎总在断言前完成（各 await 都走同步完成路径）；全量并行时线程池紧张，
测试线程在第 1 步和第 3 步之间抢到执行权，断言读到 0 → 偶发失败。这与"单独跑必过、
全量跑偶发、与改动无关"的三个观察全部吻合。次要因素：`ProcessTestWait.UntilAsync`
的 5 秒截止在饥饿下偏紧。

### 1.2 修复（只动测试，不动生产代码）

1. **等待条件加强到「换流完全落地」**：两处 `UntilAsync` 的条件从"SourceKind 翻转"加强为
   "SourceKind 翻转 **且** 新采集 `IsStarted` **且** 旧采集全部 `DisposeCount == 1`"，
   然后再做其余断言。这消除了观察中间态的窗口，是本修复的核心。
2. **截止时间加宽**：`ProcessTestWait.UntilAsync` 增加可选超时参数（默认仍 5 秒），
   本测试文件用 10 秒，防线程池饥饿下的误报。
3. **`changes` 列表读侧加锁**（用户审查补充）：写入侧本来就 `lock (changes)`，但断言处
   `changes[^1]`（`:52`）和 `Assert.All(changes, …)`（`:71`）是无锁读——修完第 1 条后这里会
   成为下一个偶发点。断言前先 `lock (changes)` 拷出快照再断言。
4. **`FakeLoopbackCapture` 的计数改原子访问**（用户审查补充）：`StopCount` / `DisposeCount` /
   `IsStarted` 是普通字段；等待条件改成跨线程轮询这些计数后，可见性成为新风险——
   计数改 `Interlocked`，`IsStarted` 改 `volatile bool`。
5. **不采纳 `[Collection]` 串行**：它只降低并行度、拖慢套件，且对本竞态无效——
   竞态在测试自身的等待条件与被测异步之间，与其它测试是否并发无关。
6. 待办 D17 条目更新：记录真实根因与修复提交号，状态改「已修复」。

### 1.3 验收（必须全量并行）

**不能用"单测该类循环 50 次"验收**（用户审查指出）：这个竞态由线程池饥饿触发，
单跑一个类不会饥饿，跑 50 次全绿证明不了修好。有效验收：

- **全量套件连跑 3~5 次**全绿（只有全量并行才会复现；可加 `--blame-hang` 收集万一的挂起）；
- `git diff` 确认生产代码零改动（只含测试文件与文档）。

## 二、D16：长音频（>12 s）识别被截断（待排期）

### 2.1 现状与待验证点

- 原实验是**绕过 VAD 直喂识别器**暴露的截断（18.4 s 三语连说只剩末段韩语）；软件真实路径
  先过 `SileroVadSegmenter`（`MaxSpeechDuration = 12 s` 强切）再进识别器，
  **真实路径是否丢内容从未验证过**——这是 D16 一直挂着的原因。
- 本次核对真实路径，先排除两个嫌疑：
  - **段间乱序**：`RecognizeSegmentAsync` 经 `_recognitionGate` 信号量串行
    （`LocalSpeechCaptureSession.cs:281`），强切出的第二段不会抢在第一段前上屏；
  - **跨源串音**：换源 `Reset()` 丢弃残留段（设计如此），与长音频无关。
- 剩两个待验证点（措辞已按设计修正：**段间静音本来就不进段，不算丢**——要验的是语音有没有被吃）：
  1. 12 s 强切边界处有没有把**语音**吃掉（sherpa-onnx native 实现细节，未证）；
  2. 识别器单段上限是否 ≥ 12 s（18.4 s 丢内容说明上限 ≤ 18.4 s，12 s 段是否安全未证）。

### 2.2 方案（先验证、后修复）

**B1 仓库内属性测试（必做，复用现成条件写法）**：加进**已存在的**
`tests/VrcTranslate.Infrastructure.Tests/SileroVadSegmenterTests.cs`，直接复用其
`TryCreate()` 模式（模型缺失或无原生运行库时返回 null → 用例直接 return，CI 天然安全）。

- **输入信号（规格写死）**：16 kHz、幅度约 0.3 的正弦或白噪声、**连续 18 s、不含任何静音间隙**。
  注释写明：「这是为了逼出 12 s 强切，不代表真实语音」。
- **先试跑一次**确认该信号能产出段（detector 对纯正弦/白噪声的判定未实测）；
  产不出段就退回条件测试写法：喂 `artifacts/probe/*.wav`，音频或模型缺失时跳过。
- **断言（验「没有一段被吃掉」，不是「每个样本都有着落」）**：
  原断言「各段样本之和 == 喂入样本数」**作废**——包装层 `DrainCompleted`
  （`SileroVadSegmenter.cs:104-108`）会主动丢弃 < 0.24 s 的段，且段间静音按设计不进段，
  该等式在真实音频上永远不可能成立。改为：

  1. 返回段是原始波形的**切片拷贝**（样本逐点相等），用前 **32 个**样本的序列匹配把每段
     **定位回原始波形**，得到每段的 [起点, 终点]；匹配必须用**单调前移的游标**
     （从上一段起点 +1 往后找，绝不回头）。**只匹配 8 个样本会在周期性信号里定位到错误位置**——
     本轮实测踩到过，表现是「段间缺口 1344 样本」这种不合常理的数；改成 32 样本 + 单调游标后稳定。
  2. **相邻段缺口 ≤ 1536 样本（3 个分析窗）**：`起点_{i+1} − 终点_i ≤ 1536`
     ——实测 1280~1344 样本（2.5~2.6 窗，见下表），所以第二版写的「≤ 512」会**假失败**。
     这条就是「12 s 强切边界没有吃掉大段语音」的形式化表达。
  3. **首段起点距喂入起点 ≤ 1920 样本（0.12 s）**——实测 1280 样本（80 ms，检测器预热）。
  4. 每段长度 ≤ **12 s + 2 窗（192000 + 1024 = 193024 样本）**——实测最长 192704（超出 704 样本 = 1.38 窗）。
  5. **末尾缺口只记录、不断言**：实测 18 s 输入 256 样本、24 s 输入 0 样本、30 s 输入 **30848 样本（1.93 s）**。
     波动这么大（取决于最后一窗的语音概率），写成断言只会变成随机红灯。把它作为 B2 的观测项，
     在真实音频上判断「尾巴被吃掉」是否可感知。


#### B1 前置实测（本轮已跑，2026-09-16，本机）

信号：16 kHz、`0.3 × sin(2π·440t) + 0.05 × 白噪声`、**连续无静音**；
参数：`threshold = 0`、`minSpeech = 0.24 s`、`minSilence = 0.6 s`、`maxSpeech = 12 s`；
喂入方式：每次 512 样本（与生产同块长），末尾 `Flush()`。

| 输入 | 段数 | 各段长度（样本） | 各段时长 | 超 12 s | 段间缺口 | 末尾缺口 |
| --- | ---: | --- | --- | ---: | ---: | ---: |
| 18 s | 2 | 192704, 92416 | 12.04 s, 5.78 s | +704 | 1344 | 256 |
| 24 s | 2 | 192704, 188672 | 12.04 s, 11.79 s | +704 | 1344 | 0 |
| 30 s | 3 | 192704, 192704, 59776 | 12.04 s, 12.04 s, 3.74 s | +704 | 1344, 1344 | 30848（1.93 s） |
| 18 s（`threshold` 取 0 / 0.1 / 0.3 / 0.5） | 2 | 同上 | 同上 | +704 | 同上 | 同上 |

**结论（都已写进断言）**：

1. 合成信号**确实能被切成段**，不需要真实语音文件——`threshold` 从 0 到 0.5 结果完全一致（该信号在模型眼里就是语音）；
2. 强切**超出 12 s 704 样本（1.38 个分析窗）**，容差必须 ≥ 2 窗；
3. 每次强切**丢掉约 1280~1344 样本（80~84 ms）音频**——这是「强切边界吃语音」的**实测量级**，
   不是 0；B3 判断「要不要修」时按这个数算（每 12 秒连续语音丢 80 ms）；
4. 检测器**预热约 1280 样本（80 ms）**：首段起点不在 0；
5. **末尾缺口波动极大**（0 ~ 1.93 s），不能写成断言。

复现脚本：`artifacts/vad-probe3.ps1` + `artifacts/vad-probe3.py`（生成 18/24/30 s 合成音频）。
**B2 真实路径复测（必做，本机素材都在）**：bench 增加"走 VAD"模式——probe 音频先过
`SileroVadSegmenter` 切段、逐段进 SenseVoice，与直喂结果对照。
验收线（已放宽）：**输出逐段列出**（段号 + 时长 + 段间缺口 + 识别文本），判定「**三种语言都出现**
（允许拆成多条字幕、允许首段末尾被强切在词中间）」——不要求任何单条识别结果里三语齐全。
另需记录：真实音频上段间缺口是否也在 80 ms 量级（合成信号实测值），以及听感上「每 12 秒丢 80 ms」是否可感知。

**B3 按结果分支**：

| B1/B2 结果 | 动作 |
| --- | --- |
| 真实路径不吃语音 | D16 关闭为「直喂实验的假象」，结论写回待办；B1 测试留作回归防线 |
| 丢在 VAD 强切边界 | 修 `SileroVadSegmenter` 包装层（边界样本补偿/重切），B1 作验收。**注意**：合成信号上每次切分固定丢约 80 ms，若真实音频同量级，需先确认这 80 ms 是否会切掉半个音节——不一定要修 |
| 丢在识别器单段上限 | 识别请求按 12 s 内的静音窗二次切分，B2 作验收 |

### 2.3 验收

- B1 测试并入套件全绿；B2 复测结果（无论哪个分支）写回待办 D16 条目；
- 走修复分支时，新增/修改的生产代码各配单测。
