# D22 方案：早切 + 文本回退（把 600 ms 等待压掉）

> **状态：设计稿，待审核（未改代码）**。
> 目标：把「说完话 → 中文字幕出现」的**大头 600 ms** 降下来，同时**不牺牲断句准确度**。

## 1. 要解决什么（一句话）

现在必须等 **600 ms 静音**才敢断定「你说完了」；D22 改成 **250 ms 就先动手**，用**识别出来的文本**（SenseVoice 带标点）反过来判断你说完没有——**没说完就撤回重做**。

## 2. 为什么不能只把 600 调成 250

因为「句内停顿」和「句间停顿」**区间重叠**（想词型的人句内停顿比连说型的人句间停顿还长），任何**固定的**静音阈值都会切错一部分人。

**但文本能提供静音提供不了的信息**：

| 语音特征 | 文本特征 |
| --- | --- |
| 静音 250 ms → 可能是句末，也可能是换气 | 末尾「。」 → **说完了** |
| 静音 700 ms → 可能是句末，也可能在想词 | 末尾「，」 → **还没说完** |

所以：**用短的静音阈值抢时间，用文本判断补救。**

## 3. 目标流程

```
VAD（早切阈值 250 ms）吐出一段
   ↓
① 立刻识别（约 140 ms），同时把这段音频留在缓冲里
   ↓
② 看识别文本的结尾：
   · 以 。？！ 结尾        → 判定说完 → 直接上屏   ⇒ 延迟 ≈ 250+32+140+翻译
   · 以 ，、 或无标点结尾 → 判定没说完 → 【挂起】不上屏，等下一段
   ↓
③ 挂起状态：
   · 200 ms 内又收到新段 → 把【挂起段 + 新段】拼起来重新识别一次
        · 拼完结尾是句号 → 上屏一条完整的
        · 拼完还是逗号   → 继续挂起（设 3 段上限）
   · 200 ms 内没有新段   → 确认上屏（他说完了，只是说了个短句）
```

**关键**：**字幕一旦上屏就不再修改**。所有判定都发生在「上屏之前」。

## 4. 延迟收益（用实测数字算）

| 组成 | 现在 | D22 |
| --- | ---: | ---: |
| VAD 等待 | 600 ms | **250 ms** |
| VAD 块粒度 | ~32 ms | ~32 ms |
| 识别 | 140 ms | 140 ms |
| 翻译（腾讯/阿里，实测中位） | 220 ms | 220 ms |
| **首条字幕合计** | **≈ 990 ms** | **≈ 640 ms** |

| 说话类型 | 现在的体验 | D22 的体验 |
| --- | --- | --- |
| 正常（句末有句号） | 990 ms | **640 ms（省 350 ms）** |
| 想词型（句末是逗号） | 会被**切成两条字幕** | 挂起 + 重识别 → **一条完整的**，但慢 250 ms |
| 连说型（无停顿） | 两句**并成一条** | 早切生效 → **分成两条**（更准） |

**注意**：最坏情况（每句都挂起重做）首条字幕约 1.2 s，**比现在还慢**——这正是要靠 D22-0 先量清楚的：
**真实语音里句末带句号的比例有多高**。如果比例高，D22 全线变快；如果比例低，D22 只对少数句子变快。

## 5. 改动点（尽量小）

| 位置 | 改动 | 为什么这样改 |
| --- | --- | --- |
| **新增 `SilenceProbe`**（Application 层新类，一个独立的 `SileroVadSegmenter` 实例，阈值调成 250 ms） | 只负责「早切」，**不碰生产的主 segmenter** | 主切分（600 ms）保留 → **不影响任何现有行为**，D22 可随时关掉；两者输出取并集 |
| `LocalSpeechCaptureSession` | 接收两路段：主段（600 ms）与早切段（250 ms）。早切段进入「挂起/确认」状态机，主段作为**兜底确认**（早切没抓到的，主段一定抓到） | 避免重复上屏：同一段音频可能同时被早切和主切命中，需要按音频位置去重 |
| **新增 `CaptionCoalescer`**（状态机） | 持有挂起段（音频 + 文本），决定：上屏 / 拼接重识别 / 超时确认 / 丢弃 | 逻辑集中在一处，可单测 |
| `TextTranslationRequest` 调用方 | 不变 | 翻译只在上屏前调用一次 |

**并发**：识别器（`SenseVoice`）内部是否可并发调用**必须先确认**。目前靠 `_recognitionGate` 串行；D22 会并行跑「早切段识别」，**需要单独加一道门或复用同一道闸**——这是实现时要验证的第一件事。

## 6. 验证计划（先量数据，再动代码）

| 编号 | 事项 | 成本 | 输出 |
| --- | --- | ---: | --- |
| **D22-0** | **量「句末标点比例」**：用现有 4 段真人语音 + 你提供的一段真实多人对话，统计 SenseVoice 输出里以 `。？！` 结尾 vs 以 `，`/无标点结尾的比例 | 1 小时 | 一张表 → 决定 D22 值不值得做 |
| **D22-1** | `SilenceProbe` + `CaptionCoalescer` 单测（不接管线） | 半天 | 状态机正确性（挂起/拼接/超时/去重） |
| **D22-2** | 接入管线，**开关默认关闭** | 半天 | 可用开关 A/B 对比 |
| **D22-3** | 真机对比：同一段素材跑「现方案 vs D22」，比较首条字幕延迟与断句条数 | 2 小时 | 决定是否默认开启 |

**总计 1.5~2 天。**

## 7. 风险与失败模式

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| **标点识别错**（说完了但识别成逗号） | 白挂起一次，首条字幕慢 250 ms | 挂起上限 3 段；超时 200 ms 必确认 |
| **标点识别错**（没说完但识别成句号） | 句子被切成两条（**和现在一样**，不会更差） | 无（这是可接受的退化） |
| **挂起期间用户看不到反馈** | 以为软件卡了 | 字幕区显示「识别中…」（或复用现有状态行） |
| **频繁早切** | 短段识别次数变多 → CPU 上升 | 识别 140 ms/段；早切仅在静音 ≥250 ms 时触发，正常语速下不会爆炸 |
| **与 D20 的声纹切分互相干扰** | 两处都在改「分段」逻辑 | **先把 D22 做完**（D20 只是实验、不动代码），或先拿 D20 结论再动 D22 |
| **播放中的字幕被撤回** | 用户看到内容跳变 | **不做撤回**：只允许「未上屏的挂起段」被合并，已上屏的一律不动 |

## 8. 不做的事

| 不做 | 原因 |
| --- | --- |
| 单纯把 600 改成 250 | §2：固定阈值无法区分句内/句间停顿 |
| 让已上屏的字幕撤回/改写 | 用户会看到内容跳变，比慢一点更糟 |
| 用语言模型判断句子完整性 | 成本高（要么上云、要么带本地小模型），而标点已经够用 |
| 改流式识别 | 要换掉整条识别管线，另一个量级 |
