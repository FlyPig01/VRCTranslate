## 4. 已修复的方案全文（D28/D29，实施记录含内）

### D28 · 他人语音的识别原文进入 OSC → 已修复（`16ebd2a`）

**实施记录**：方案全部落地——Application 层新增 `OtherPlayerCaptionPipeline`（依赖翻译端口、`IOtherPlayerSubtitleSurface`、`IChatboxOutput`，不引用 AppState/OverlayWindowHost/OscChatboxClient）；桌面组合根等 `AppState.Ready` 后取路由快照；译文来源分级为 真实成功/测试回显/失败/取消，echo 档案直接短路不调用翻译；OSC 只发"真实成功 + 非空 + 规范化后与原文不同"的译文（TrimForOsc，144 UTF-16）。验收矩阵的四条路径由 `OtherPlayerCaptionPipelineTests` 的 echo/同文/失败/裁剪用例逐条断言。

#### 已确认根因

`SubtitleSpeechSession` 没有直接把 `result.Text` 传给 OSC，但会无条件发送 `translated.TranslatedText`。以下三条路径会让所谓“译文”实际等于识别原文：

1. 全新安装默认使用 `local-test / echo`，该档案按设计原样返回输入；
2. 他人语音链路没有等待 `AppState.Ready`，启动初期可能在真实档案恢复前读到临时 echo 路由；
3. 真实服务在中文到中文、未翻译成功但返回 200，或只含专有名词时也可能返回原文。

D11 的“OSC 消息带原文”只适用于**手动输入和自身语音**。他人语音的既有契约仍是：本地字幕可先显示识别原文，VRChat Chatbox 只接收有效译文。不新增用户开关。

#### 修复方案

1. 将他人语音结果处理从 `VoiceSessionHost` 抽到 Application 层的 `OtherPlayerCaptionPipeline`；桌面层只负责采集、窗口和事件绑定。管线显式依赖翻译端口、字幕端口和可替换的 `IChatboxOutput`，不能引用 `AppState`、`OverlayWindowHost` 或具体 `OscChatboxClient`。
2. Desktop 组合根在提交工作项前等待 `AppState.Ready`，一次性取得本句的路由快照并交给管线；Application 层不反向依赖 Desktop。运行中切换默认档案只影响下一句。
3. 给翻译结果增加可判定的来源/状态，区分真实成功、测试回显、未配置、失败和取消，禁止用“失败后回退原文”作为他人语音的 OSC 载荷。
4. 只有“真实服务成功、译文非空、规范化后与原文不同”时才发送 OSC；发送内容固定为单条简体中文译文，并继续受 144 个 UTF-16 单元限制。
5. echo、未配置、失败、空译文、同文返回时，本地字幕保留已识别原文并结束等待，OSC 为零报文。不能为了避免空消息而回退发送原文。
6. 手动输入和自身语音继续走 `SelfMessagePipeline`，保留第一译文/第二译文/原文格式及“OSC 消息带原文”开关，不受本次修改影响。

#### 验收矩阵

| 输入结果 | 本地字幕 | OSC |
| --- | --- | --- |
| 真实译文且不同于原文 | 原文先出现，随后补译文 | 仅译文，恰好 1 次 |
| `local-test / echo` 或未配置真实服务 | 显示原文 | 0 次 |
| 翻译失败、超时、取消或空译文 | 保留原文并结束等待态 | 0 次 |
| 服务返回与原文相同 | 显示一份文本，不重复 | 0 次 |

### D29 · 多人轮流/快速接话时字幕被静默丢弃 → 已修复（`16ebd2a`）

**实施记录**：`_processingResult` 丢弃规则已删除；每句分配单调 `captionId` 并同步发布 Pending 字幕；`Channel` 工作队列 + 会话 worker，翻译并发 2、按 `captionId` 顺序提交（先完成的后句不会越过前句上屏/外发）；单句失败只终态该句；队列满载给终态 + 诊断事件；每次 Start 新 generation+CTS+队列，Stop/Restart/音源边界（VRChat 进程切换）结束写端、取消并等待 worker，旧 generation 不回填不发 OSC。`SpeechCaptureProcessingOptions` 把 `SplitAtSpeakerChanges` 与 `AttachSpeakerLabels` 解绑：他人语音固定切分、标签开关只控制命名、自身语音两者全关，切分模型不可用/抛错降级整段。自动测试要求 1~7 全部落地（管线 9 条 + 会话 4 条；校验脚本的 TrimForOsc 静态断言改为管线闸门断言 + 禁止 `_processingResult` 回潮）。验证：全量 400 条通过，`Invoke-V2Validation` 5/5 通过。

#### 已确认根因

这不是一个问题，而是两个会叠加的实现错误：

1. `VoiceSessionHost.OnResultReady` 在 `_processingResult == true` 时直接 `return`。上一句翻译的 195~700 ms 内，下一句不会进入 `_processingGate`，而是被静默丢弃。pyannote 将一个 VAD 段切成 A/B/C 三片时，第一片开始翻译后，后两片尤其容易命中这个分支。
2. `LocalSpeechCaptureSession.PlanSpeakerSpans` 用 `SpeakerLabelsEnabled` 同时控制“按换人点切音频”和“显示说话人名字”。用户关闭标签时，已经由真实双人录音证明有效的换人切分也被关闭；默认行为因此最不适合多人对话。

#### 修复方案

1. 删除结果入口的 `_processingResult` 丢弃规则。每个识别结果先分配单调递增的 `captionId` 并立即发布 Pending 字幕，再写入该次会话专属的有序工作队列。
2. 用 `Channel` 和会话 worker 取代“事件里启动未跟踪任务 + 布尔锁”。翻译最多并发 2 条，提交阶段按 `captionId` 排序；慢请求不会阻塞识别，快请求也不会越过前一句发送 OSC。
3. 单条失败只将对应字幕结束为“无译文”，随后条目继续处理。队列若达到内部上限，必须把对应字幕明确结束为不可用并记录诊断，禁止静默丢句；不增加用户配置。
4. 每次 Start 创建新的 generation、`CancellationTokenSource` 和队列；Stop、Restart、音源 generation 变化时完成写端、取消并等待 worker。旧 generation 的翻译返回后不得回填字幕或发送 OSC。
5. 增加会话级 `SpeechCaptureProcessingOptions`，至少拆成 `SplitAtSpeakerChanges` 和 `AttachSpeakerLabels`：他人语音固定开启前者，后者仍跟随用户的标签开关；自身语音两者均关闭。
6. 换人切分模型不可用或执行失败时降级为整段识别。它只改善先后说话，不承诺恢复真正同时重叠的第二路声音。

#### 自动测试要求

1. 人为阻塞 A 的翻译后连续送入 A/B/C：三条 Pending 字幕必须立即出现，最终一条不少；翻译按 C/B/A 完成时，字幕与 OSC 仍按 A/B/C 提交。
2. B 翻译失败不能阻塞 A/C；队列满载时每个已发布字幕都有明确终态。
3. Stop、Restart 和音源切换后，旧任务不得回填新会话、发通知或发送 OSC。
4. 标签关闭时仍调用换人切分，但不调用声纹命名；标签开启时，两个测试说话人必须得到不同身份，文本、身份和 `captionId` 一一对应。
5. 自身语音不调用多人切分；切分模型不可用或抛错时仍产生整段字幕。
6. D28 的四种他人语音路径分别断言 OSC 次数和载荷；自身输入、自身语音各保留一条端到端 OSC 回归测试。
7. 修正 `Invoke-V2Validation.ps1` 中“源码存在 `TrimForOsc` 即算字幕 OSC 正确”的静态断言，改为运行 Application 层管线测试和 UDP 载荷测试。

### D23 · 当前随包技术栈能否用音源分离救「重叠丢一路」→ ❌ 不可行（实验已完成）

| 检查项 | 结果 |
| --- | --- |
| sherpa-onnx 自带分离模型能拆两个人声吗 | ❌ 不能。只提供 **Spleeter / UVR**，都是**音乐伴奏分离**；两路都是人声时不会拆开 |
| sherpa-onnx 分离接口本机可用吗 | ❌ 用官方 `spleeter-2stems` 模型报 `ComputeStft: Invalid channel 1. Max 1`（1.13.8） |
| 换人声专用模型（SepFormer） | ⚠️ 需 Python + PyTorch 栈（与「纯 .NET + onnxruntime」冲突），无 ONNX 版本可嵌入 |
| 就算能分离，延迟可接受吗 | ❌ 按训练块推理（块长 4 s）⇒ 字幕至少晚**数秒** |

**结论：当前版本不做**，维持「保一路」；这不是“所有未来技术路线永久不可行”。重启条件见 [能力边界与决策记录.md](能力边界与决策记录.md) §6.3、§9。

### D24 · 是否引入流式识别 → ❌ 已否决（代价超过收益）

它是 `[批式固有]` 两条（字幕疏、文本大块）**唯一**的解法，但**代价超过收益**，决定不做。

| 常见误解 | 核查结果 |
| --- | --- |
| 「流式只能走云端」 | ❌ 本机 sherpa-onnx 1.13.8 已导出 `OnlineRecognizer` / `OnlineStream`；模型侧有日语 ReazonSpeech 流式、中英双语 streaming zipformer |
| 「本地流式要换技术栈」 | ❌ 用 sherpa-onnx 自家流式，C# + onnxruntime 一行都不用改 |

**真理由**：① 流式模型**一模型一语种或双语**（未发现中英日韩四语合一），而场景是「语种不确定、随时换」；② 准确率先退一步；③ 切成短句**反而丢掉翻译上下文**；④ CAM++ 说话人标签要按时间轴重做；⑤ 出字即最终，无法二次修订。
**成本账**：识别上云按音频时长计费，典型 **≈110 元/月**（每天 2 小时），是翻译费（≈3 元/月）的 **13~143 倍**。

完整记录（含实价表与三条重启前置条件：隐私 / 计费上限 / 国内可选性）见 [能力边界与决策记录.md](能力边界与决策记录.md) §7。
